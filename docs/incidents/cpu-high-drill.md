# 障害対応演習シナリオ: CPU 高負荷

> これは実運用障害の記録ではなく、監視と切り分け手順を検証するための模擬シナリオである。
> 実行日時、出力、通知到達時間を含む実測証跡はまだ収録していない。

## シナリオ

| 項目 | 内容 |
| --- | --- |
| 対象 | Linux 検証ホスト |
| 検知 | `LinuxNodeHighCpuUsage` |
| 条件 | CPU 使用率 85% 超が10分継続 |
| 想定原因 | バッチ処理の異常ループ |
| 目的 | 検知、影響確認、原因プロセス特定、復旧、再発防止の流れを確認 |

## 再現手順

検証ホストだけで実施し、本番や共有端末では実行しない。

```bash
sudo apt-get install -y stress-ng
stress-ng --cpu 0 --timeout 12m
```

## 確認手順

1. Grafana で Linux Host CPU の上昇開始時刻を確認する。
2. Prometheus の Alerts で `LinuxNodeHighCpuUsage` が pending から firing になることを確認する。
3. ホストで `uptime`、`top -b -n 1 | head -30`、`journalctl --since "-15 min"` を取得する。
4. 実行中の `stress-ng` を原因プロセスとして特定する。

## 復旧

```bash
pkill stress-ng
```

CPU 使用率が通常値へ下がり、アラートが resolved になることを確認する。

## 記録テンプレート

以下は期待する流れのテンプレートであり、実行結果ではない。実行後は
`docs/evidence/README.md` の規則に従って実測結果を保存する。

| 時刻 | 観測・判断 | 操作 |
| --- | --- | --- |
| T+0 | CPU 上昇を Grafana で確認 | 調査開始 |
| T+10m | アラート firing | プロセス一覧とログ取得 |
| T+12m | 高負荷プロセスを特定 | プロセス停止 |
| T+13m | CPU 正常化 | resolved 確認 |

## 再発防止の検討

- バッチには実行時間上限とログを設定する。
- CPU アラートに直近変更やジョブ名へ辿る運用リンクを付ける。
- 誤検知が多い場合は閾値ではなく継続時間を調整し、変更理由を記録する。
