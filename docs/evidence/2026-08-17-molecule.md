## 実行コマンド

各ロールのディレクトリで、以下を実行している（ワークフローの matrix により 4 ロール並列）。

```bash
ansible-galaxy collection install -r ansible/requirements.yml
cd ansible/roles/<role>
ANSIBLE_ROLES_PATH=<repo>/ansible/roles molecule test
```

`molecule test` は `dependency → cleanup → destroy → syntax → create → prepare → converge → idempotence → side_effect → verify → cleanup → destroy` を通しで実行する。

## 到達までの経緯（run #1 → #7）

このワークフローは定義されてから一度も実行されていなかった。初回実行から成功まで 6 回失敗している。**失敗の原因は 4 種類に分かれ、対処もそれぞれ異なった。**

| run | 停止段階 | 原因 | 種別 | 対処 |
| --- | --- | --- | --- | --- |
| #1 | `destroy`（初手） | `stdout_callback: yaml` が指す `community.general.yaml` が cg 12.0.0 で削除済み | 設定の陳腐化 | `ansible.builtin.default` + `callback_result_format: yaml` へ移行（[#49](https://github.com/ns7jp/server-monitor/pull/49)） |
| #2 | versions 表示 | `ansible-galaxy collection list` に collection を 3 つ渡した（位置引数は最大 1 つ） | 記述ミス | 引数なしへ修正（[#50](https://github.com/ns7jp/server-monitor/pull/50)） |
| #3 | `converge` | `common`: `tzdata` 未導入かつ timezone 設定がパッケージ導入より前<br>`docker`: daemon 起動不可 | **ロールの欠陥** ／ 環境制約 | tzdata 追加とタスク順の入れ替え／`docker_manage_service` 追加（[#51](https://github.com/ns7jp/server-monitor/pull/51)） |
| #4 | `converge` | `common`: chrony 起動不可 | 環境制約（**誤診**） | `common_manage_services` で無効化（[#52](https://github.com/ns7jp/server-monitor/pull/52)） |
| #5 | `idempotence` | 同一 port 22 に `ufw allow` と `ufw limit` を適用しており、毎回互いを上書き | **ロールの欠陥** | limit 対象を allow から除外（[#53](https://github.com/ns7jp/server-monitor/pull/53)） |
| #6 | `verify` | `timedatectl` が動かない。**systemd が PID 1 で起動していなかった** | **検証環境の設定不備** | 全 scenario に `command: /lib/systemd/systemd` を追加（[#54](https://github.com/ns7jp/server-monitor/pull/54)） |
| #7 | — | — | — | **全ロール成功** |

### 特に記録しておくべき 2 件

**1. UFW の allow と limit が同じ port を奪い合っていた（run #5）**

`ansible-lint` も `--syntax-check` も検出できなかった。文法は正しく、個々のタスクも妥当で、**2 回適用して初めて矛盾が現れる**種類の欠陥だったため。冪等性テストでしか見つからない。

冪等性が壊れるだけの問題ではない。実ホストでも毎回 SSH のルールが `ALLOW` と `LIMIT` の間で書き換わるため、総当たり攻撃の抑止が意図した状態で維持されない。設定の見た目と実際の防御状態が一致しないという点で、セキュリティ上の欠陥でもあった。

**2. run #4 の診断が誤りだった（run #6 で判明）**

chrony が起動しなかった際、原因を「コンテナはホストの時計を共有するため NTP デーモンを動かせない」と判断して無効化した。しかし実際の原因は **systemd が PID 1 として起動していなかった**ことであり、権限や能力の問題ではなかった。

4 つの scenario はいずれも `privileged: true`、`cgroupns_mode: host`、`/sys/fs/cgroup` のマウントという systemd 稼働の前提を揃えていたが、molecule の docker driver が既定で `bash -c "while true; do sleep 10000; done"` を command に流し込みイメージの `CMD` を上書きするため、その準備が全て無効化されていた。

この 1 点が、run #3 の docker daemon、run #4 の chrony、run #6 の `timedatectl` という**別々に見えた 3 件すべての共通原因**だった。`nginx` と `monitoring` がサービス操作を持たず早くから完走していたことも、この説明と整合する。

判明後、run #4 の無効化は取り消し、chrony 起動と sshd 再起動を実際に検証する構成へ戻している。

## 所見

- **良かった点**: `converge` だけでなく `idempotence` まで通したことで、実際の欠陥を 2 件検出できた。特に UFW の件は静的検査では検出できない種類だった。
- **見つかった課題**: 「コンテナだからできない」と早期に結論づけると、設定不備を環境制約と取り違える。同じ症状（`Service is in unknown state`）でも原因が同じとは限らない。
- **次の対応**:
  - `ansible/requirements.yml` の `community.general` 制約が `">=8.0.0,<11.0.0"` のままで、`pip install ansible`（12.x）が同梱する 12.0.0 より 2 メジャー古い。見直す。
  - Linux ホストでの全 stack 起動と D-1 復旧演習を採録する（[ローカル証跡採録ガイド](local-evidence-quickstart.md)）。
  - `docker_manage_service` を有効にした状態での daemon 起動確認は、実ホストでの構築試験で行う。
