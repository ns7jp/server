# 案件パック 初心者ガイド（Zabbix版）

> **対象**: 「要件定義書」「非機能要件」「Gate」などの言葉を初めて見る人。[Linux版初心者ガイド](../build-package/beginner-guide.md)は読んだが Zabbix 版は初めて、という人も対象
> **ゴール**: 12 個の文書を読む前に、案件パック全体の地図と、Zabbix 特有の言い回しを頭に入れる
> **所要時間の目安**: 20〜30 分（暗記ではなく、地図を持つことが目的）

このディレクトリ（[`docs/build-package-zabbix/`](README.md)）には、文書が 12 個並んでいます。
「新しいZabbixサーバーホストを構築する」案件に見立てた、要件定義から引き渡しまでの一式です。

既存の中央監視基盤（Prometheus + Grafana + Loki + Alertmanager）は置き換えません。
そこから独立した2本目の監視経路として、Zabbixを足すという位置づけです。

構成も呼び方も、[Linux版案件パック](../build-package/README.md)・[Windows版案件パック](../build-package-windows/README.md)・[AD版案件パック](../build-package-ad/README.md)と同じです。
いずれかを読んだ人には、見覚えのある文書が多いはずです。

ただしZabbix版には、この案件パックにしか出てこない言葉もたくさん出てきます。
「Host（監視する対象1台を表す登録名）」「Template（設定のひな形）」
「Trigger（異常だと宣言する条件）」「active check（監視される側から値を送る方式）」などです。
いきなり[00-requirements.md](00-requirements.md)から読み始めると、そこでつまずきやすくなっています。

この文書は案件パック本体（成果物）には含まれません。初めて読む人のための
**地図と用語辞典**です。読んだらすぐ本編の
[最短レビュー順](README.md#最短レビュー順)へ進んでください。

1. 最初に「[1. そもそも案件パックとは](#1-そもそも案件パックとは)」で、このパックが

5. 一度に全部を覚えようとしない。困ったらこの文書へ戻ってくればよい

## 1. そもそも案件パックとは

**一言でいうと**: 案件パックとは1つの案件の文書一式のことで、これはこのリポジトリで4本目にあたります。

実際のサーバー構築の受託案件では、発注者（依頼する側）と受注者（構築する側）の間で、

- 何を作るか（要件）
- どう作るか（設計）
- 具体的にどんな値で作るか（パラメータ）
- 実際にどう手を動かすか（構築手順）
- 本当にできているかをどう確かめるか（試験）
- 何を、いつ、どう渡すか（引き渡し）

を、口約束ではなく**文書として残す**のが普通です。これは「面倒な形式」ではなく、
担当者が変わっても同じ基準で仕事を続けられるようにするための仕組みです。

このリポジトリには、すでに 3 本の案件パックがあります。

- 1 本目: [Linux版案件パック](../build-package/README.md)（案件ID `SM-LAB-001`）。
  監視基盤そのものを Ubuntu Server 1 台へ構築する案件
- 2 本目・3 本目: [Windows版](../build-package-windows/README.md)（`SM-WIN-001`）と
  [AD版](../build-package-ad/README.md)（`SM-AD-001`）。
  その基盤へ監視対象や土台を追加する案件

`docs/build-package-zabbix/`は**4 本目**の案件パックで、案件 ID は `SM-ZBX-001` です。

前の 3 本との一番大きな違いは、**置き換えではない**という点です。
既存の監視スタック（Prometheus / Grafana / Loki / Alertmanager）はそのまま残します。
同じ監視対象ホスト`monitor-01`を、まったく別の監視ソフトウェアであるZabbixからも
監視できるようにする、という案件です。

では、なぜPrometheus/Grafanaがすでにあるのに、もう1つ別の監視ソフトを構築するのか。
日本のインフラ求人では「Prometheus/Grafanaの経験」だけでなく、
**「Zabbixの経験」を単独で求める求人が非常に多い**ためです。

このポートフォリオの狙いは、1つの監視ソフトの使い方を覚えることではありません。
**要件定義から引き渡しまでの一連の進め方そのもの**を、監視ソフトが変わっても
同じ厳格さで再現できると示すことです。

「既存スタックを学び直した」のではありません。
「別の監視ソフトでも同じ案件パックの型を最初から最後まで組み立てられる」ことを
見せるのがポイントです。

未経験者が最初につまずくのは、内容そのものではありません。
「なぜこの文書が 12 個も要るのか」でつまずきます。
「Prometheus版と同じ構成なのに、なぜHostやTemplate、activeチェックのような
新しい言葉が急に増えるのか」でもつまずきます。

次の章で、12 文書を 5 つの塊に圧縮して覚え方を作ります。

## 2. 全体の流れを1つの図で見る

**一言でいうと**: 12 個の文書は、「決める→描く→作る・変える→確かめる→渡す」の一本道に並びます。

```mermaid
flowchart LR
    A["決める\n00 要件定義書"] --> B["描く\n01-04 基本/詳細設計・パラメータ・NW"]
    B --> C["作る・変える\n05 構築手順・08 変更/ロールバック"]
    C --> D["確かめる\n06 試験・09 NW実機検証・10 立ち上げ受け入れ"]
    D --> E["渡す\n07 引き渡し・11 作業結果報告"]
```

この図は、[案件パックのREADME](README.md)にある工程ゲートの図をもとにしています。
元の図は「要件→設計→構築→試験→証跡→報告→引き渡し」の 7 段階です。
それを初心者向けに 5 語へ圧縮・再編成しました。
（Gate や証跡の意味は[5. 現場用語ブリッジ](#5-現場用語ブリッジ)で説明します）

7 段階と 5 語は 1 対 1 には対応しません。
例えば「試験」「証跡」の一部を④確かめるへ、「報告」「引き渡し」を⑤渡すへまとめています。

文書番号の 00〜11 は作られた順であって、実際に読む・使う順ではありません。
読む順は「[6. 読む順とかかる時間の目安](#6-読む順とかかる時間の目安)」を使ってください。

> **Windows版・AD版にある「フェーズ1／フェーズ2」の区切りは、このパックにはありません**
>
> [Windows版](../build-package-windows/00-requirements.md)や[AD版](../build-package-ad/00-requirements.md)は、
> 「ホスト単体で完結するフェーズ1」と「中央監視基盤への統合が必要なフェーズ2」に分かれます。
> そしてフェーズ2は、未実装3点の解消まで`BLOCKED`でした。
>
> Zabbix版は、中央監視基盤（Prometheus/Grafana）への統合をもともと必要としません。
> 独立した2本目の監視経路として設計しているためです。
> そのためこの区切りがなく、Linux版パックと同じ単一フェーズの工程ゲート（G0〜G5）で完結します。

## 3. 迷わないための5フェーズ

**一言でいうと**: 12 文書を 5 つの塊にまとめて覚えると、どの文書が何のためにあるか迷わなくなります。

**覚え方: 「決める → 描く → 作る・変える → 確かめる → 渡す」**

| フェーズ | 一言 | 含まれる文書 | この段階で答える問い |
| --- | --- | --- | --- |
| ① 決める | 何を作り、何をもって完成とするか決める | [00 要件定義書](#00-要件定義書) | 「利用者は何を求めているか」「既存のPrometheus/Grafanaとどう役割分担するか」 |
| ② 描く | 実現方法・具体値・接続範囲を描く | [01 基本設計書](#01-基本設計書)、[02 詳細設計書](#02-詳細設計書)、[03 パラメータシート](#03-パラメータシート)、[04 ネットワーク設計](#04-ネットワーク設計ipアドレス表) | 「どう作るか」「具体的な値は何か」「誰がどこから接続できるか」 |
| ③ 作る・変える | 実際に手を動かし、変更時の戻し方も決める | [05 構築手順書](#05-構築手順書)、[08 変更・ロールバック計画](#08-変更ロールバック計画兼記録票) | 「どう構築するか」「失敗したらどう戻すか」 |
| ④ 確かめる | 本当にできているかを事実で確認する | [06 試験仕様書・結果票](#06-試験仕様書結果票)、[09 ネットワーク実機検証手順](#09-ネットワーク実機検証手順)、[10 立ち上げと受け入れ試験](#10-立ち上げと受け入れ試験) | 「合否の基準は何か」「実際に検知・復旧できたか」 |
| ⑤ 渡す | 相手に説明し、記録を残して引き渡す | [07 引き渡しチェックリスト](#07-引き渡しチェックリスト)、[11 作業結果・引き渡し報告書](#11-作業結果引き渡し報告書) | 「渡す前に漏れはないか」「予定と実績の差は何か」 |

12 文書のうち 03・04 は②、05・08 は③のように、1 つのフェーズに複数の文書が
含まれることに注意してください。文書番号（00〜11）と、このフェーズの順番は一致しません。

[案件パックREADMEの工程図](README.md)は 10（立ち上げと受け入れ試験）を「構築・変更」の
グループ（05・08 と同じ）に置いていますが、この文書ではあえて④確かめるに分類しています。
10 の中身は「構築済みのホストで、まだ確認していない項目を試験する」ことが中心で、
初心者にとっては「作る」より「確かめる」の仲間として覚えるほうが実感に合うためです。

学習ガイドにも「見る → 動かす → 確認する → 壊して直す → 説明する」
（[初心者向け学習ガイド](../beginner-learning-guide.md)）という、形は似ているが中身は別の
5 語の覚え方があります。混同しないよう、覚えるときは今どちらの文書を読んでいるかを意識してください。

## 4. 12文書カード

**一言でいうと**: ここから先は通読する章ではなく、読みながら必要なカードだけ引く辞書です。

[未経験者向けサーバー構築キーワード集](../server-building-keywords.md)と同じ
「一言 → なぜ必要か → 読むポイント → このパックでの実例」の 4 点セットです。
先に一言だけ読み、必要になったときに残りを確認してください。

> 「実例」には Zabbix、Docker Compose、UFW のような個別の技術名がそのまま
> 出てきます。これらの技術そのものの説明はこの文書ではなく
> [サーバー構築キーワード集](../server-building-keywords.md)や、この文書の
> 「[5. 現場用語ブリッジ](#5-現場用語ブリッジ)」で行っています。

### 00 要件定義書

- **一言**: 「何を作るか」「完成の合格基準」を先に決める文書
- **なぜ必要か**: 作ってから「思っていたのと違う」を防ぐため。特に本パックは既存の
  監視基盤とどう役割分担するかを最初に合意しておくことが重要になる
- **読むポイント**: 機能要件（FR）表と非機能要件（NFR）表の「受け入れ確認」列。この列の ID が
  [06 試験仕様書](06-test-specification.md)の試験 ID と対応している
- **実例**: `FR-02`（`monitor-01`のホストメトリクスをactive checkで収集すること）が
  `ZIT-03`へ、`NFR-04`（既定パスワード変更）が`ZST-02`へつながる

### 01 基本設計書

- **一言**: 要件を「どう実現するか」の全体方針を描く文書
- **なぜ必要か**: 細部を決める前に、`zbx-01`・`monitor-01`の役割分担と、既存監視基盤との
  境界線を関係者で合意しておくため
- **読むポイント**: 論理構成図（mermaid）と、済(自動)/済(手動)/未実装の区分表
- **実例**: `zbx-01`上のZabbix Server / Frontend（ブラウザで開く管理画面）/ PostgreSQL の構成図。
  Ansible role化はせず、Docker Composeの手動実行を中心とする設計判断

### 02 詳細設計書

- **一言**: コンポーネントごとの実装と「正常性の見分け方」を描く文書
- **なぜ必要か**: 「動いているかどうかをどう判断するか」を部品単位で先に決めておくため
- **読むポイント**: 1つ目は、コンポーネント設計表の「正常性確認」列。
  2つ目は、`service_monitor.healthz` Item（Itemは、集める1つのデータ項目）の取り方の理由。
  Zabbixの「Web監視シナリオ」を使わず、Agent2（監視対象ホストに入れる収集ソフト）側の
  UserParameter（独自に追加する取得項目）で取るのはなぜか、という設計理由
- **実例**: 「zabbix-webは`/index.php`が200を返せば正常」「`service_monitor.healthz`
  Itemの値が`1`ならアプリ正常」

### 03 パラメータシート

- **一言**: OS・ネットワーク・Docker・Zabbix監視の具体的な設定値を一覧にした表
- **なぜ必要か**: 文章の設計書だけでは見落としやすい具体値を 1 か所にまとめ、実機の値と
  照合しやすくするため
- **読むポイント**: 「設計値」列と「実績値」列が分かれていること。実績欄の `NOT RUN` は
  「値がない」ではなく「まだ実機で確認していない」という意味
- **実例**: Zabbixイメージタグが`alpine-7.0.29`に固定されていること。
  Host group（Hostをまとめるフォルダーのようなもの）が
  `SM-ZBX-001 Lab Hosts`という案件ID紐づきの名前であること

### 04 ネットワーク設計・IPアドレス表

- **一言**: どの IP・ポートに、誰が、どこから接続できるかを決めた文書
- **なぜ必要か**: 「公開してよい範囲」を先に決めておかないと、管理UIをうっかり
  インターネットへ公開してしまう事故につながるため
- **読むポイント**: Frontendは、ループバック（`127.0.0.1`。そのサーバーの中からだけ届く）に
  限定して守ります。trapper（トラッパー。監視対象から送られてくる値の受け口）は、
  そうはできないので送信元を制限して守ります。この守り方の設計思想が違う理由を読みます。
  あわせて、trapperの送信元制限がUFWではなく`DOCKER-USER`chainである理由
- **実例**: Frontendは`127.0.0.1`限定にし、SSH tunnel（SSH越しに手元の端末へ通す通り道）経由で開く。
  trapper(`10051/tcp`)だけは外からの着信を受ける。
  ただし許可するのは、`monitor-01`のIPを送信元に指定した`DOCKER-USER` iptables chainのルールの分だけ
  (DockerがPublishしたportはUFWの`INPUT`chainを経由しないため)

### 05 構築手順書

- **一言**: 実際にZabbixサーバーを構築するとき、上から順に実行する手順書
- **なぜ必要か**: 手順書がないと特定の人にしか構築できなくなる（属人化）ため。Ansible role化を
  していない分、コマンドとUIクリック手順を1つずつ正確に書き残す必要がある
- **読むポイント**: 「0. 作業前確認」を飛ばさないこと。`compose.zabbix.yaml`による自動化部分と、
  Frontendの手動クリック部分の境界
- **実例**: `docker compose -f compose.zabbix.yaml up -d` → もう一度実行して不要な再作成が
  無いことを確認 → Frontendへログインし`Admin`初期パスワードを変更

### 06 試験仕様書・結果票

- **一言**: 完成したかどうかを判定する「試験問題と模範解答（期待結果）」
- **なぜ必要か**: 「たぶんできてる」ではなく、コマンドと期待結果を先に決めておくことで、
  誰が実行しても同じ基準で合否を判定できるため
- **読むポイント**: 冒頭の「この文書の読み方」を先に読む。原本は常に `NOT RUN` のまま
  保存され、実施結果は日付付きの証跡（evidence）へコピーして記録する運用になっている
- **実例**: `ZUT-xx`（単体・構成試験）、`ZIT-xx`（構築・結合試験）、`ZST-xx`
  （セキュリティ試験）の 3 系統。`ZIT-07`はD-Z1（Agent2停止演習）のRTO記録

### 07 引き渡しチェックリスト

- **一言**: 作業を依頼者に引き渡す前の最終確認リスト
- **なぜ必要か**: 「試験は全部 `PASS` したが、DBパスワードの引き継ぎ方法を伝え忘れた」
  のような漏れを防ぐため
- **読むポイント**: 冒頭の引き渡し判定表と、秘密値（DBパスワード・Slack bot token）の
  受け渡し確認項目
- **実例**: 秘密値そのものではなく「安全な受け渡し・再発行方法」を共有したか、という
  チェック項目

### 08 変更・ロールバック計画兼記録票

- **一言**: 完成後に設定を変更するとき、「失敗したらどう戻すか」を先に決めておく文書
- **なぜ必要か**: 問題が起きてから戻し方を考えるのでは遅いためです。
  Trigger/Action（異常を宣言する条件と、その知らせ方）の設定変更のようなFrontend上の変更も、
  始める前にGo / No-Go（進めてよいか、やめるか）の判断基準を決めておきます
- **読むポイント**: 「Go / No-Go 条件」チェックリストと、「ロールバック開始条件」の一覧
- **実例**: commit のハッシュ値（SHA）を指定して`compose.zabbix.yaml`側の変更前状態へ戻す手順

### 09 ネットワーク実機検証手順

- **一言**: 実機のネットワークが設計どおりに動いているかを、1 項目ずつ確認する手順書
- **なぜ必要か**: 「たぶんつながっている」ではなく、名前解決 → 経路 → 待受 → 通信 → firewall
  の順に事実を積み上げて確認するため
- **読むポイント**: `ZNW-01`〜`ZNW-09`の番号順と、「管理端末→zbx-01」「monitor-01→zbx-01:10051」
  という2方向を確認する構成
- **実例**: `ss -lntup`でFrontendが`127.0.0.1`だけに待ち受けていることを確認する`ZNW-05`相当

### 10 立ち上げと受け入れ試験

- **一言**: 「まだ確認していない項目」を、1 台の実サーバーで一気に埋めるための手順書
- **なぜ必要か**: 使い捨ての検証環境では確認できない「再起動後も動くか」「動き続けるか」を
  確かめるため
- **読むポイント**: 「この手順で埋まらないもの」の表。1 台の実サーバーで埋まることと埋まらないことを、
  はっきり区別している
- **実例**: 立ち上げ環境の選択肢（クラウドVM/オンプレVM/VirtualBox）と、再起動後にZabbix Server・
  PostgreSQLのコンテナが自動復帰するかの確認

### 11 作業結果・引き渡し報告書

- **一言**: 予定と実績の差、トラブル、残課題をまとめて報告する文書
- **なぜ必要か**: 試験結果がバラバラのファイルに散らばったままだと、依頼者は「結局終わったのか」が
  分からないため
- **読むポイント**: 「試験集計」で、個別の結果票の件数と合計が一致しているかを確認する部分
- **実例**: 案件 ID `SM-ZBX-001` に対する完了判定欄（`NOT READY` のまま残っていれば未完了）

## 5. 現場用語ブリッジ

**一言でいうと**: 意味の取れない言葉に出会ったら、本編を読む手を止めてこの表を引いてください。

12 文書のあちこちで説明なしに出てくる言い回しです。意味が分かれば読む速度が大きく変わります。
まず[Linux版初心者ガイド](../build-package/beginner-guide.md#5-現場用語ブリッジ)と共通の言葉、
続けてZabbix版だけに出てくる言葉の順に並べます。

| 用語 | 意味 |
| --- | --- |
| 正本（せいほん） | 「本当の値はどこにあるか」を 1 か所に決めておく考え方。本パックの構築設定値の正本は`compose.zabbix.yaml`と本パックの手順書であり、パラメータシートの表はそれを見やすくした「索引」に過ぎない |
| 原本（げんぽん） | 06・08・11 のような「空欄のひな形」文書そのものを指す言葉。実際に実行した結果はこの原本へ直接書き込まず、日付付きの別ファイル（証跡 / evidence）へコピーして記録する |
| 案件 ID | 案件を一意に識別する番号。この案件パックでは `SM-ZBX-001`。Linux 版は `SM-LAB-001`、Windows 版は `SM-WIN-001`、AD 版は `SM-AD-001` |
| 設計値 / 実績値 | 設計値はコード・文書から確認できる「決めた値」。実績値は対象ホストで実際にコマンドを実行して得た「実測した値」。設計値から実績値を推測して埋めない |
| `FR` / `NFR` | Functional Requirement（機能要件）/ Non-Functional Requirement（非機能要件）の略。FR は「何ができるか」、NFR は「どのくらいの品質・安全性で」を表す |
| Gate（ゲート） `G0`〜`G5` | 各工程が完了したと認めるための関門。前のゲートを満たさないまま次の工程へ進まない、という約束事 |
| `ZUT` / `ZIT` / `ZST` / `ZNW` | 試験 ID の頭文字。Zabbix Unit Test（単体・構成試験）/ Zabbix Integration Test（構築・結合試験）/ Zabbix Security Test（セキュリティ試験）/ Zabbix Network（ネットワーク実機検証）。Linux 版の`UT`/`IT`/`ST`/`NW`と役割は同じで、頭に付く文字だけが違う |
| `PASS` / `FAIL` / `BLOCKED` / `NOT RUN` | 結果の 4 状態。`PASS` は実測して期待どおり、`FAIL` は実測して不一致、`BLOCKED` は前提が整わず実行できない、`NOT RUN` は単に未実行 |
| `NOT SET` | 値そのものがまだ決まっていない（`NOT RUN` は「実行していない」、`NOT SET` は「値を決めていない」という違い） |
| `NOT READY` | 完了と判定するための条件が、まだ揃っていない状態 |
| commit SHA | Git の変更履歴を一意に指す 40 桁の ID。「どのブランチか」ではなく「どの時点のコードか」を正確に指すために使う |
| 日付付き evidence（証跡） | 06・08・11 などの文書は「空欄のひな形（原本）」として保存され、実際に実行した結果は上書きせず、日付の付いた別ファイルへコピーして記録する |

### Zabbix固有の用語

Zabbix を初めて触る人が、専門用語を専門用語のまま覚えようとしてつまずく言葉です。
まず日常語で言い換え、そのあとに正式な役割を添えています。

| 用語 | 一言で言うと |
| --- | --- |
| Host（ホスト） | 一言で言うと、Zabbixが監視する対象1台を表すオブジェクトの名前。本パックでは`monitor-01`というHostを1つ作る。OSのホスト名と紛らわしいが、Zabbix内部の「登録簿の1行」だと考えるとよい |
| Host group（ホストグループ） | 一言で言うと、Hostをまとめるフォルダーのようなもの。本パックでは`SM-ZBX-001 Lab Hosts`という専用グループを作り、案件IDで束ねる |
| Template（テンプレート） | 一言で言うと、「このHostにはこのItem/Triggerの束を適用する」という設定のひな形。本パックは組み込みの「Linux by Zabbix agent active」テンプレートをそのままリンクし、自作しない |
| Item（アイテム） | 一言で言うと、実際に集める1つの数値・データ項目。「CPU使用率」「`service_monitor.healthz`の値」のように1項目=1 Item |
| Trigger（トリガー） | 一言で言うと、Itemの値が条件を満たしたときに「異常（Problem）」を宣言するルール。「healthzが3分間1以外」のような条件を書く |
| Action / Media type | 一言で言うと、Triggerが発火したときに「誰に・どうやって」知らせるかの設定。本パックは組み込みSlack media type(Bot Token方式)を登録する |
| Severity（重要度） | 一言で言うと、Triggerの深刻さのランク。本パックはAverage（Agent自体unreachable）/High（healthz異常）/Warning（閾値超過）の3段階を使う |
| active check（アクティブチェック） | 一言で言うと、監視対象（`monitor-01`）側のAgent2が、自分からZabbix Server（`zbx-01`）へ値を**push**する方式。本パックの主方式 |
| passive check（パッシブチェック） | 一言で言うと、Zabbix Server側から監視対象へ値を**取りに行く（pull）**方式。本パックは既定で未使用、将来拡張として設計のみ示す |
| trapper（トラッパー） | 一言で言うと、active checkのpushを受け取るZabbix Serverの受け口（`10051/tcp`）。他ホストからの着信を受ける唯一の監視系ポートなので、Frontendとは異なりloopback限定にできない。送信元の制限はUFWではなく`DOCKER-USER`chainで行う（DockerがPublishしたportはUFWが見るhostの`INPUT`chainを経由しないため） |
| Agent2 | 一言で言うと、監視対象ホストにインストールする収集エージェントのソフトウェア本体。従来のZabbix Agentの後継 |
| UserParameter（ユーザーパラメータ） | 一言で言うと、組み込みのItemだけでは取れない値を、Agent2の設定ファイルに1行追加して独自に定義する仕組み。本パックは`service_monitor.healthz`をこれで取る |
| Frontend（フロントエンド） | 一言で言うと、ブラウザで操作するZabbixの管理画面（Web UI）。本パックは`zabbix-web`コンテナが提供する |

> **つまずきやすいポイント: なぜ「Web監視シナリオ」ではなくUserParameterでhealthzを取るのか**
>
> Zabbixには「Web監視シナリオ」という機能があります。
> ネットワーク越しにHTTPを叩いて、外から生死を確かめる機能です。
> server-monitorアプリの`/healthz`をZabbixで監視すると聞くと、これを使うのが自然に思えます。
>
> ところが`/healthz`は[Linux版パックの設計](../build-package/04-network-ip-plan.md)により
> `127.0.0.1`限定で外部非公開になっています。
> これは「管理UI・監視対象アプリを外部公開しない」という既存パック共通の方針です。
> Zabbixパックのために緩めることはしません。
>
> そこで本パックは、Zabbix Serverがネットワーク越しに直接probe（外から叩いて確かめること）
> することはしません。
> 代わりに、**`monitor-01`自身のAgent2にUserParameterを追加し、
> Agent2がホスト内部から`curl`する**設計を採っています。
>
> Agent2はもともと、active checkで`monitor-01`から`zbx-01`へpush（送りつける）する経路を
> 持っています。だから`/healthz`は、ループバック限定のまま外部公開せずに死活監視できます。
>
> 「監視のためだけに、既存の安全な設計を緩める」のではありません。
> 「監視対象ホスト自身に確認させて、結果だけを送る」という発想の転換だと理解してください。
>
> Zabbixの主方式にactive checkを選んでいるのも、同じ理由です。
> 単なる好みではなく、「監視対象が増えても、Zabbix Server側から新しいホストへ届く経路を
> 増やさなくてよい」という、双方向ルールを増やさずに済む設計判断です。

## 7. 覚えるための1分チェック

**一言でいうと**: 「読んだ」と「自分の言葉で説明できる」の差を、ここで確かめます。

すべて、この文書を読み返さずに答えられるかを確認する設問です。

1. 12 文書を 5 つの動詞に圧縮すると何になりますか。
2. `NOT RUN` と `NOT SET` の違いは何ですか。
3. パラメータシートの「設計値」と「実績値」はどう違いますか。
4. 06 試験仕様書の原本が、実行後もずっと `NOT RUN` のままなのはなぜですか。
5. FR と NFR の違いを一言で言うと何ですか。
6. active check と passive check の違いは何ですか。本パックがactive checkを主方式にする理由も言えますか。
7. `service_monitor.healthz` Itemの値を、Zabbixの「Web監視シナリオ」ではなくUserParameterで取るのはなぜですか。

<details>
<summary>解答例</summary>

1. 決める → 描く → 作る・変える → 確かめる → 渡す
2. `NOT RUN` は「まだ実行していない」、`NOT SET` は「値そのものをまだ決めていない」
3. 設計値はコードや文書から確認できる「決めた値」、実績値は対象ホストで実際にコマンドを実行して得た「実測した値」
4. 原本は空欄のひな形として保存し続け、実際の実行結果は日付付きの証跡（evidence）へコピーして記録する運用のため
5. FR は「何ができるか（機能）」、NFR は「どのくらいの品質・安全性でできるか（非機能）」
6. active checkは監視対象側のAgent2がZabbix Serverへpushする方式、passive checkはZabbix Server側が監視対象へ取りに行く（pull）方式。本パックは、監視対象ホストが増えてもZabbix Server側から新しいホストへ届く経路を増やさずに済むという理由でactive checkを主方式にしている
7. `/healthz`はloopback限定で外部非公開という既存パックの設計方針を崩さないため。ネットワーク越しに直接probeするのではなく、監視対象ホスト自身のAgent2にUserParameterを追加してホスト内部から`curl`させ、その結果だけをactive checkで送る設計にしている

</details>

## 9. よくある誤解

**一言でいうと**: 初めて読む人がつまずきやすい思い込みを、先に外しておきます。

| 誤解 | 実際 |
| --- | --- |
| 12 文書が揃えば構築完了 | 文書が「作成済み」であることと、実ホストで試験が `PASS` して引き渡しが完了したことは別の状態です。[案件パックREADME](README.md)冒頭の引き渡し判定を参照 |
| `NOT RUN` は失敗の印 | `NOT RUN` は「まだ実行していない」であって `FAIL`（実行して不一致）ではありません。ただし必須試験が `NOT RUN` のままでは完了と判定しません |
| このパックは既存のPrometheus/Grafanaを置き換える案件 | 既存の中央監視基盤（`SM-LAB-001`）は変更しません。同じ監視対象ホストを、独立した2本目の経路であるZabbixからも監視できるようにするだけで、置き換えではありません |
| 「済(自動)」と書いてあるのでAnsibleで全自動構築されている | 本パックの「済(自動)」は`compose.zabbix.yaml`による`docker compose up -d`のような、コード化された非対話コマンド一発で完結するものを指します。既存の`site.yml`のようなAnsibleロールによる全自動構築ではありません |
| このパックは実案件の実績 | `SM-ZBX-001` は、現場と同じ形式で作った練習用の文書一式であり、実機でZabbixを構築した実績ではありません。`compose.zabbix.yaml`はCIで構文検証済みですが、実機への適用は[06 試験仕様書](06-test-specification.md)の結果欄がすべて `NOT RUN` のとおり未実施です |
