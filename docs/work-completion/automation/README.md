# 作業の区切り方を整理するローカル判定サンプル

これは、サーバー構築の作業記録から「次の 1 手」を提示する読み取り専用 CLI です。Node.js の標準モジュールだけで動作し、追加パッケージは不要です。GitHub、サーバー、ネットワークへ接続せず、ファイルの変更・削除、コミット、通知、スケジュール登録を行いません。

**機械が返すのは参考判定です。デプロイ許可、作業終了の承認、実環境の安全性の証明にはなりません。** 根拠がそろった後の際限のない確認を区切り、根拠が足りない場合は仮説の更新や引継ぎへ進めるための試作品です。気持ちや「執着」を診断・消去するものではありません。

## 使い方

PowerShell でこの `automation` フォルダーを開き、次を実行します。

```powershell
node .\gate.mjs --help
node .\gate.mjs .\examples\ready-lab.json
node .\gate.mjs .\examples\repeat-lab.json
node .\gate.mjs .\examples\incident.json
node --test .\gate.test.mjs
```

期待する判定は順に `READY_TO_CLOSE`、`CHANGE_APPROACH`、`COORDINATE` です。examples の全入力と証跡参照は架空です。実環境の測定、学習者の理解、レビューの完了を示しません。`fictional:` を含む例が終了準備と判定されるのは、このコードが参照の真実性を検証していないためです。

自分の作業に使う際は例を別の JSON ファイルへコピーし、実際に観測した値と確認可能な証跡参照に差し替えます。**未実施は NOT_RUN のまま記録します。** 証跡参照には公開してよい識別子や適切な権限で管理する記録の場所を使い、秘密値を入れないでください。

引数なし・`--help`・`-h` はヘルプ表示で終了コード 0 です。有効な入力から判定できた場合も 0、JSON の読込・構文・型・必須情報の不備は 2 です。判定自体が `COORDINATE` でも入力不備が併存すれば 2 です。**終了コード 0 は「PASS」や実行許可を意味しません。CI のデプロイ条件に流用しないでください。**

## 入力の意味

入力は UTF-8 の JSON オブジェクトで、256 KiB 以下の通常ファイルにします。UTF-8 BOM は除去して読み込みます。

| 項目 | 型・条件 | 記録すること |
|---|---|---|
| `task_id` | 空でない 200 文字以内の 1 行文字列 | 対象作業の識別子。出力にも掲載するので秘密情報を含めない |
| `mode` | `lab` / `planned` / `incident` | 学習・検証、計画作業、インシデント対応の別 |
| `revision` | 空でない 200 文字以内の 1 行文字列 | 今回評価するコード・設定一式の版。Gitを使う場合は完全なコミットSHAなど、曖昧でない識別子 |
| `elapsed_minutes` | 0 以上の有限数 | この作業枠の経過分数。小数可 |
| `budget_minutes` | 0 より大きい有限数 | 作業開始前に決めた見直し時刻までの分数。小数可 |
| `rechecks_without_change` | 0 以上の安全な整数 | 最初の確認後、対象の変更も新しい事実もないまま同じ確認を追加した連続回数 |
| `attempts_without_new_hypothesis` | 0 以上の安全な整数 | 前回から仮説を更新せずに追加試行した連続回数 |
| `critical_risk` | 真偽値 | 重大な影響・進行中の危険があると把握しているか。文字列 `"true"` は不可 |
| `new_evidence` | 真偽値 | 新しい観測があり、ゲート記録への反映・影響確認が未完了か |
| `gates` | オブジェクト | 必須の `security`、`functional`、`recovery`、`handover` の 4 項目 |

カウンターを下げるのは、対象の変更、新しい証拠、仮説の更新など、その定義に対応する事実が生じたときです。作業を続けたいという理由で予算やカウンターを後から書き換えず、必要な延長は元の値・延長理由と判断者を別の記録に残します。この CLI に履歴の改ざん検知機能はありません。

`revision` は文字列の完全一致だけを検査します。コードの版が一致しても、未コミット変更、対象環境、依存関係や設定、試験条件の変化を自動検出できません。対象一式や試験条件が変わった場合は、その事実を証跡へ残し、必要なゲートを NOT_RUN に戻すなど、人が有効性を再評価してください。

`new_evidence=true` の間は全ゲートが PASS でも終了を保留します。新しい証拠を記録し、影響するゲートを更新し、影響確認が済んだ時点で人が false に戻します。重大リスクが見つかった場合は、併せて `critical_risk=true` または `mode=incident` を申告して対応の連携へ移ります。

## ゲートの形式と判定

| 項目 | 条件 |
|---|---|
| `status` | `PASS` / `FAIL` / `NOT_RUN` / `NA` のいずれか |
| `revision` | PASS / NA では必須。対象 revision と完全一致した場合だけ有効 |
| `evidence_ref` | PASS / NA では空でない 2,048 文字以内の 1 行文字列が必須 |
| `rationale` | NA では空でない 4,000 文字以内の 1 行文字列が必須 |

FAIL / NOT_RUN では `revision`、`evidence_ref`、`rationale` を省略または空文字にできます。未実施なのに証跡を要求して虚偽の PASS を誘発しないためです。記載する場合は文字列である必要があり、null、数値、空白だけの値などは入力不備です。

必須ゲートの目的は次のとおりです。どの試験を必要とするか、合格基準、責任者、証跡形式は作業前に定義し、現場の運用規則に従います。

| ゲート | 人が確認する内容の例 |
|---|---|
| `security` | 不要な公開・権限・秘密情報の混入がないか。対象範囲に必要なセキュリティ確認の結果 |
| `functional` | 合意した要求と期待する応答・認証・処理が満たされるか |
| `recovery` | 安全な検証環境での復旧・再起動・ロールバック等の結果と適用限界 |
| `handover` | 対象、変更点、確認結果、残件、次の行動を説明する記録 |

lab の handover は「自分の言葉で説明した記録」で構いません。その内容が正しいかはコードが判断できず、本番作業のレビュー・責任者の承認・他者への引継ぎの代替ではありません。

NA は「不要だから飛ばす」ための値ではありません。対象外とする理由とその判断の記録を残し、人が適用範囲を確認します。意味のあるセキュリティや復旧の確認を、作業を終える都合で NA にしないでください。コードは NA の妥当性を審査できません。

1 つのゲートに複数の試験をまとめる場合、適用する必須試験がすべて合格したときだけ PASS を入力します。1 件でも FAIL・NOT_RUN・証跡不足があれば PASS にしません。FAIL があればゲートは FAIL、それ以外の未実施・証跡不足は NOT_RUN とし、内訳を参照先に残します。ゲート全体の NA は、含まれる必要確認がすべて適用外と根拠付きで判断された場合だけ使います。コードは試験の内訳や集約の正しさを読みません。

空の gates、不足するゲート、未定義のゲート名、認識できない status、PASS / NA の証跡参照欠測は NEEDS_INPUT です。FAIL、NOT_RUN、古い revision の PASS / NA は入力形式が正しければ「未達」と判定します。

トップレベルの補足項目は判定に使わず、出力へ転載しません。ゲート名はこの版では 4 項目固定です。ゲートを増やすときは仕様・実装・テストを合わせて更新してください。

## 優先順位

上から最初に一致した判定を返します。重大リスクの申告があるときは、他の入力不備よりも対応の連携が優先です。

| 優先 | 条件 | 判定と人の次の行動 |
|---|---|---|
| 1 | `mode=incident` または `critical_risk=true` | `COORDINATE`：責任者・対応継続者と連携する。サービスを放置・自動停止しない |
| 2 | 必須情報欠測・型不正・形式不正 | `NEEDS_INPUT`：実際の事実と参照を補う |
| 3 | 全ゲート有効、かつ新しい証拠の反映待ちなし | `READY_TO_CLOSE`：人が証跡・適用範囲・必要な承認を確認し、終了を記録する |
| 4 | 終了未確定で、経過時間が予算以上 | `PAUSE_AND_RECORD`：安全状態と対応継続者を確認し、通常の追加作業を区切り、残件・再開条件を残す |
| 5 | 終了未確定、同じ確認の追加が 2 回以上、新しい証拠なし | `CHANGE_APPROACH`：別の仮説・小さい切り分け・相談へ進む |
| 6 | 終了未確定、新しい仮説なしの追加試行が 2 回以上 | `CHANGE_APPROACH`：新しい証拠があれば反映し、仮説を更新する |
| 7 | 上記以外 | `CONTINUE`：未達の 1 項目を小さく検証する。または新しい証拠の反映・再評価を行う |

「終了未確定」にはゲート未達と `new_evidence=true` を含みます。経過時間が予算と同じになった時点で到達とします。全ゲートが有効かつ新しい証拠がなければ、予算や反復回数が超過していても READY_TO_CLOSE です。この区別によって、合格しているのに同じ確認だけを延々と続ける状態を区切ります。

閾値の 2 回や例の 45 分は、普遍的な正解ではなく試行用の仮値です。失敗率、影響、相談までの時間、やり直しなどの記録を見て調整してください。重大事故の対応を時間だけで打ち切るためには使いません。

## 出力と限界

JSON 出力には `task_id`、`result`、`reasons`、`next_action`、`validation_errors`、必要時の `unmet_gates`、`limits` を含みます。常に `assessment_only=true`、`approval=NOT_GRANTED`、`service_action=NONE` です。証跡参照、理由の原文、余分な入力、OS の例外詳細は転載しません。

このサンプルは、次のことを実施・保証していません。

- 実サーバーや GitHub の変更・テスト・監視、証跡ファイルの読込、証跡参照先へのアクセス。
- 入力した PASS / NA、revision、重大リスク有無の真実性・網羅性の検証。
- セキュリティの専門レビュー、変更管理上の承認、現在の実環境の確認。
- 人の心理状態の判定、学習理解や感情変化の測定、反復回数の自動取得。
- 判定履歴の保存、定期実行、通知、入力の収集・更新。

自動化済みなのは **入力から次の行動候補を計算する部分** です。実作業に採用するには、事実の記録と証跡の確認を人が行います。

## 検証

リポジトリ直下では `node --test docs/work-completion/automation/gate.test.mjs` を実行します。GitHub Actions の `Work completion check` は Node.js 24で同じテストを実行します。実環境の合格やマージ許可を判定するworkflowではありません。

`node --test gate.test.mjs` は、重大リスクと入力不備の優先順位、空ゲート、欠測、型、版の不一致、NA の根拠、予算と反復の境界、新しい証拠による終了保留、出力への不要な入力転載防止、実 CLI と架空入力 3 件を確認します。

テストの成功はこのローカル判定コードの挙動に関する証拠です。サーバーの動作確認や、手放す行動の有効性の実測を行ったという意味ではありません。
