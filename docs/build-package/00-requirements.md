# 要件定義書

## 1. 文書の位置づけ

`server-monitor` を「Ubuntu Server 1 台へ監視対象アプリと監視・ログ基盤を構築し、運用担当者へ引き渡す」小規模案件として扱います。本書は要求と受け入れ条件を定義し、設計値の正本は後続資料と構成コード、実行結果の正本は [`docs/evidence/`](../evidence/README.md) に分離します。

本書に `実装済み` と書いてあっても、実ホストでの構築・試験完了を意味しません。受け入れ可否は [試験仕様書・結果票](06-test-specification.md)の結果で判定します。

## 2. 案件概要

| 項目 | 内容 |
| --- | --- |
| 利用者 | Linux サーバーを構築・運用する担当者 |
| 対象環境 | Ubuntu Server 24.04 LTS、検証用 VM 1 台 |
| 構築方式 | Ansible による OS 設定、Docker Compose によるアプリ・監視基盤配備 |
| 提供機能 | 監視ダッシュボード、メトリクス、ログ検索、アラート、バックアップ、復旧手順 |
| 引き渡し単位 | 構成コード、設計書、パラメータシート、構築手順、試験結果、運用・変更手順 |
| 完了判定 | 必須試験がすべて `PASS`、未解決事項と残存リスクが受領記録に記載済み |

## 3. 機能要件

| ID | 要件 | 受け入れ確認 | 実装・設計先 |
| --- | --- | --- | --- |
| FR-01 | 運用者が Nginx 経由で Server Monitor UI を利用できること | IT-04 | `compose.yaml`、`deploy/nginx/local.conf` |
| FR-02 | CPU、memory、disk、アプリのメトリクスを Prometheus で収集できること | IT-03、IT-05 | `deploy/prometheus/` |
| FR-03 | ホスト・コンテナのログを Loki へ集約し、Grafana から検索できること | IT-07 | `deploy/alloy/`、`deploy/loki/` |
| FR-04 | 監視ルールの異常を Alertmanager へ送り、設定した経路で確認できること | IT-08 | `deploy/prometheus/rules.yml`、`deploy/alertmanager/` |
| FR-05 | 監視データを日次バックアップし、別 volume へ復元できること | IT-10 | `ansible/roles/backup/`、[`docs/backup-restore.md`](../backup-restore.md) |
| FR-06 | プロセス停止を検知し、復旧と正常性確認までの時間を記録できること | IT-09 | `scripts/drills/`、`docs/drills/` |
| FR-07 | 管理端末からサービスまでの名前解決、経路、待受、HTTP、FW を確認できること | IT-12、ST-01、ST-04 | [ネットワーク実機検証手順](09-network-validation-procedure.md) |

## 4. 非機能要件

| ID | 分類 | 要件 | 受け入れ確認 |
| --- | --- | --- | --- |
| NFR-01 | 再現性 | 未構築の対象 VM に `site.yml` を適用し、`failed=0` で完了すること | IT-01 |
| NFR-02 | 冪等性 | 同じ構成を 2 回目に適用したとき、不要な変更が発生しないこと | IT-02 |
| NFR-03 | セキュリティ | 管理 UI は loopback だけに bind し、外部から直接公開しないこと | ST-01 |
| NFR-04 | セキュリティ | UI と metrics の認証を分離し、実秘密値を Git で追跡しないこと | IT-04、IT-05、ST-03、ST-05 |
| NFR-05 | 最小権限 | アプリコンテナを非 root で動かすこと | ST-02 |
| NFR-06 | ネットワーク | UFW は default deny incoming とし、管理用 SSH だけを許可すること | ST-04 |
| NFR-07 | 可観測性 | メトリクス、外形監視、ログを関連付けて一次切り分けできること | IT-03、IT-06、IT-07 |
| NFR-08 | 復旧性 | D-1 プロセス停止演習で検知から復旧までの RTO を記録すること | IT-09 |
| NFR-09 | 保守性 | 変更前後の commit、検証、ロールバック条件と結果を記録すること | [変更・ロールバック計画](08-change-rollback-plan.md) |
| NFR-10 | 追跡性 | 実行日時、環境、commit SHA、コマンド、実出力、判定を証跡へ残すこと | 全必須試験 |

## 5. 制約と対象外

- 単一ホストの学習用構成であり、ホスト障害時の無停止継続は提供しません。
- 24 時間有人監視、複数拠点、SSO、商用 SLA、実組織の個人情報は対象外です。
- AWS Terraform は発展構成です。`apply / destroy` の実行証跡がない限り、本案件の構築実績には含めません。
- Ubuntu 22.04 LTS は構成コードの対応対象ですが、本案件の基準 VM は 24.04 LTS です。OS ごとの実測は個別の証跡が必要です。
- Slack 実通知は webhook と受信先を用意した場合だけ試験します。UI 上の FIRING 表示を実通知成功として扱いません。

## 6. 前提条件

- 管理端末から対象 VM へ公開鍵 SSH で接続でき、接続ユーザーが sudo を利用できること。
- 対象 IP、管理元 CIDR、DNS 名、作業時間帯、費用上限が作業前に確定していること。
- Vault の秘密値と Vault パスワードを Git 管理外で受け渡せること。
- 対象 commit SHA と、直前の正常な commit SHA を変更記録へ残すこと。

## 7. 要件トレーサビリティと判定

詳細な操作・期待結果は [試験仕様書・結果票](06-test-specification.md)を正本とします。結果はその原本へ直接記入せず、日付付きの evidence へコピーして保存します。

| 判定 | 意味 |
| --- | --- |
| `PASS` | 期待結果を実出力で確認し、証跡への参照がある |
| `FAIL` | 実行したが期待結果と一致しない |
| `BLOCKED` | 前提不足で実行できず、理由と解除条件がある |
| `NOT RUN` | 未実行。成功実績として数えない |

現時点の結果は [検証証跡台帳](../evidence/README.md)を参照してください。資料が揃ったことと、構築案件が完了したことは別の状態です。
