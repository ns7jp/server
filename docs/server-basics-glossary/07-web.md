# 7. Web とアプリケーション

[用語集の入口](README.md) / [さくいん](index.md) / [前: 通信のしくみと名前解決・リモート接続](06-network-protocols.md) / [次: データベース・ストレージ・バックアップ](08-data-storage.md)

ブラウザに URL を入れてからページが出るまでには、いくつものサーバーとソフトが順番に仕事をしています。この章では、その道すじを言葉にして「今どこで止まっているのか」を人に説明できるようにします。

> **この章で最初に押さえる 3 語**: HTTP ／ HTTP ステータスコード ／ 3 層構成

<a id="g-web-web-server"></a>
## Web サーバー（ウェブ サーバー）

- **一言**: ブラウザからの要求を受け取り、ページのデータを返す係のソフトです。
- **たとえ**: レストランのホール係です。注文を受け取り、出来上がった料理をテーブルへ運びますが、自分では調理しません。
- **くわしく**: ブラウザが送ってきた HTTP の要求を受け取り、HTML や画像のファイルをそのまま返します。プログラムで作る必要があるページは、後ろの AP サーバーに渡し、返ってきた結果を利用者へ届けます。代表的なソフトは Nginx と Apache です。小さなシステムでは、1 台のマシンの中で Web サーバーと AP サーバーが同居していることもよくあります。
- **覚え方**: 「受付は Web、調理は AP」とレストランの分業で覚えます。
- **まちがえやすい**: 「サーバー」は機械を指すこともソフトを指すこともあります。Web サーバーと言うときは、たいていソフトのほうを指しています。
- **関連語**: [AP サーバー](#g-web-ap-server) ／ [静的コンテンツと動的コンテンツ](#g-web-static-dynamic) ／ [Nginx と Apache](#g-web-nginx-apache)
- **確かめかた**: `curl -I http://localhost/` で応答のヘッダーだけを見ます。動いているかは `systemctl status nginx` で確認します（サービス名は環境によって異なります）。

<a id="g-web-ap-server"></a>
## AP サーバー（エー・ピー サーバー）

- **一言**: アプリケーションサーバーの略で、その場でページやデータを作る係です。
- **たとえ**: レストランの厨房です。ホール係から注文票を受け取り、注文に合わせてその場で料理を作ります。
- **くわしく**: 会員ごとに違うマイページや、毎回変わる検索結果のような中身を組み立てます。必要なデータは DB サーバーに問い合わせ、受け取った結果を HTML や JSON の形にします。Java、PHP、Python、Node.js など、アプリを書いた言語ごとに動かし方や設定の場所が変わります。
- **覚え方**: AP は Application（アプリ）の頭 2 文字で、注文を受けて中身を考えて作る係だと覚えます。
- **まちがえやすい**: 「ページが真っ白」のとき、Web サーバーだけを見ても原因が出ないことがあります。中身を作っているのは AP サーバーなので、そちらのログも必ず見ます。
- **関連語**: [Web サーバー](#g-web-web-server) ／ [DB サーバー](#g-web-db-server) ／ [静的コンテンツと動的コンテンツ](#g-web-static-dynamic)
- **確かめかた**: `ps aux | grep -i -E 'java|php-fpm|node|python'` のように動いているプロセスを探します。ログの置き場所は環境によって異なるので、構成資料で確認します。

<a id="g-web-db-server"></a>
## DB サーバー（ディー・ビー サーバー）

- **一言**: データを溜めておき、頼まれた条件のものだけ探して渡す専門役です。
- **たとえ**: 図書館の書庫と司書です。本（データ）を整理して並べておき、「この条件の本を出して」と頼まれた分だけ取り出します。
- **くわしく**: 会員情報や注文履歴など、消えては困るデータを保存します。AP サーバーから SQL（データベースへの命令文）を受け取り、条件に合うデータを返します。MySQL や PostgreSQL がよく使われます。3 層構成では一番奥に置き、インターネットから直接つながらないようにするのが基本です。
- **覚え方**: DB は DataBase（データの基地）の略で、一番奥にある書庫だと覚えます。
- **まちがえやすい**: DB が詰まっているのに Web サーバーだけ増やしても速くなりません。「ページが遅い」の原因は、奥のデータ取り出しにあることが多いです。
- **関連語**: [AP サーバー](#g-web-ap-server) ／ [3 層構成](#g-web-three-tier) ／ [タイムアウト](#g-web-timeout)
- **確かめかた**: 待ち受けているポートを `ss -lntp` で確認します（MySQL は 3306、PostgreSQL は 5432 が既定ですが、環境によって異なります）。

<a id="g-web-three-tier"></a>
## 3 層構成（サンソウコウセイ）

- **一言**: Web・AP・DB の 3 つに役割を分けてシステムを組む、定番の形です。
- **たとえ**: レストランの分業と同じです。ホール（Web）、厨房（AP）、書庫（DB）に分けておくと、混んだときに足りない持ち場だけ人を増やせます。
- **くわしく**: 役割を分けると、足りないところだけを増やしたり作り直したりできます。障害のときも「どの層で止まったか」で切り分けができます。外向きの Web だけをインターネットに向け、AP と DB は内側に隠すのが安全です。
- **覚え方**: 「受付・厨房・書庫」の順に並べると、外から内への流れがそのまま図になります。
- **まちがえやすい**: 3 層は「サーバーが 3 台」という意味ではありません。役割の分け方の話なので、1 台に同居していても 3 層構成と呼びます。
- **関連語**: [Web サーバー](#g-web-web-server) ／ [AP サーバー](#g-web-ap-server) ／ [DB サーバー](#g-web-db-server)
- **確かめかた**: 担当システムの構成図を開き、自分が触るサーバーがどの層かを指させるようにします。

<a id="g-web-http"></a>
## HTTP（エイチ・ティー・ティー・ピー）

- **一言**: ブラウザとサーバーがページをやり取りするための共通の約束事です。
- **たとえ**: 決まった書式の注文票です。「これをください」と書いて送ると、「はい、これです」と品物と伝票が返ってきます。
- **くわしく**: 要求（リクエスト）と応答（レスポンス）の 1 往復で 1 セットです。要求にはメソッドと URL とヘッダー、応答にはステータスコードとヘッダーと本文が入ります。もともとは人が読める文字の形式で、HTTP/2 以降は機械向けの形式になりました。暗号化しない HTTP の既定のポート番号は 80 です。
- **覚え方**: HyperText Transfer Protocol の頭文字で、「文書を運ぶ約束」と読み下せます。
- **まちがえやすい**: HTTP は 1 往復ごとに前回のことを覚えていないつくりです。ログイン状態が続くのは、Cookie とセッションで後から補っているからです。
- **関連語**: [HTTPS](#g-web-https) ／ [HTTP メソッド](#g-web-http-method) ／ [Cookie とセッション](#g-web-cookie-session)
- **確かめかた**: `curl -v http://example.com/` を実行すると、送った要求と返ってきた応答が行ごとに見えます。

<a id="g-web-https"></a>
## HTTPS（エイチ・ティー・ティー・ピー・エス）

- **一言**: 通信を暗号化して、盗み見と書き換えを防げるようにした HTTP です。
- **たとえ**: ハガキと封書の違いです。HTTP は途中の配達員に中身が読めるハガキ、HTTPS は封をした手紙にあたります。
- **くわしく**: TLS（通信を暗号化する仕組み）を HTTP と組み合わせたもので、SSL という古い呼び名で語られることもあります。サーバーは証明書を示し、ブラウザは「本当にその相手か」を確かめてから通信を始めます。既定のポート番号は 443 です。証明書には期限があり、切れるとブラウザが警告を出し、そのままでは開けなくなります。
- **覚え方**: 最後の S は Secure（安全）の S で、「S 付きは封書」と覚えます。
- **まちがえやすい**: 鍵マークが付いていても「安全なサイト」という意味ではありません。守られているのは通信の経路だけで、相手が信用できるかどうかは別の話です。
- **関連語**: [HTTP](#g-web-http) ／ [URL と URI](#g-web-url-uri) ／ [リバースプロキシ](#g-web-reverse-proxy)
- **確かめかた**: `curl -vI https://example.com/` で証明書のやり取りが見えます。ブラウザなら鍵マークをクリックして有効期限を確認します。

<a id="g-web-url-uri"></a>
## URL と URI（ユー・アール・エルとユー・アール・アイ）

- **一言**: URI は識別する名前の総称、URL はその中で場所を示すものです。
- **たとえ**: URI が「その人を指す呼び名」全体で、URL は「住所」です。住所も呼び名の一種ですが、呼び名がすべて住所とは限りません。
- **くわしく**: 実務では、ほとんどの場面で URL と言えば通じます。URL は `https://` の部分（スキーム）とホスト名、ポート、パスに分かれます。そのあとにクエリ（`?` のあと）とフラグメント（`#` のあと）が続きます。不具合を相談するとき、この部品の名前で場所を指せると話が早く進みます。
- **覚え方**: L は Location（場所）、I は Identifier（識別子）で、I が広く L はその一種だと覚えます。
- **まちがえやすい**: `#` から後ろのフラグメントはサーバーへ送られません。アクセスログにその部分が残らないのは、そのためです。
- **関連語**: [HTTP](#g-web-http) ／ [エンドポイント](#g-web-endpoint) ／ [ドキュメントルート](#g-web-document-root)
- **確かめかた**: ブラウザのアドレス欄を、スキーム・ホスト名・パス・クエリに口で分解してみます。

<a id="g-web-http-method"></a>
## HTTP メソッド（エイチ・ティー・ティー・ピー メソッド）

- **一言**: 取る・送る・置き換える・消すという、要求の種類を表す言葉です。
- **たとえ**: 宅配便の伝票の種類です。GET は「持ってきて」、POST は「預けます」、PUT は「取り替えて」、DELETE は「引き取って」にあたります。
- **くわしく**: GET はデータを取り出すだけで、サーバーの中身を変えないのが決まりです。POST は登録や送信に使い、同じ内容を 2 回送ると 2 件登録されることがあります。PUT は指定した場所の中身を丸ごと置き換え、DELETE は消します。GET・PUT・DELETE は、同じ要求を何度送っても結果が変わらないように作ります。
- **覚え方**: 「GET は読むだけ、POST は増える」と、中身が変わるかどうかで分けて覚えます。
- **まちがえやすい**: 「再読み込みしたら二重に注文された」は、POST の送り直しが原因です。GET と POST の違いが分かると、利用者にも説明できます。
- **関連語**: [HTTP](#g-web-http) ／ [REST API](#g-web-rest-api) ／ [HTTP ステータスコード](#g-web-status-code)
- **確かめかた**: ブラウザの開発者ツールの Network タブを開くと、通信ごとの Method 列に GET や POST が並びます。`curl -sI https://example.com/` は本文を持たない HEAD メソッドで送っています。

<a id="g-web-status-code"></a>
## HTTP ステータスコード（エイチ・ティー・ティー・ピー ステータスコード）

- **一言**: 要求がどうなったかを、サーバーが 3 桁の数字で返す返事です。
- **たとえ**: 窓口の返事の定型文です。「はい、どうぞ（2xx）」「隣の窓口へ（3xx）」「その頼み方では無理（4xx）」「今はこちらの都合で無理（5xx）」の 4 通りです。
- **くわしく**: 百の位を見るだけで大まかな意味が分かります。2xx は成功、3xx は別の場所への案内、4xx は要求した側の問題、5xx はサーバー側の問題です。4xx なら URL や権限を、5xx ならサーバーのログを先に見る、という切り分けの入り口になります。
- **覚え方**: 「4 は自分（クライアント）のせい、5 はサーバーのせい」と、4 と 5 の間を責任の境目にして覚えます。
- **まちがえやすい**: 「画面が真っ白＝サーバー障害」とは限りません。ステータスが 200 でも中身が空のことがあるので、まず数字を確認します。
- **関連語**: [200 や 404 などの具体例](#g-web-status-examples) ／ [HTTP](#g-web-http) ／ [リバースプロキシ](#g-web-reverse-proxy)
- **確かめかた**: `curl -o /dev/null -s -w '%{http_code}\n' https://example.com/` で数字だけを取り出せます。

<a id="g-web-status-examples"></a>
## 200 と 301 と 401 と 403 と 404 と 500 と 502 と 503

- **一言**: 現場でよく出会う 8 つの返事で、原因を切り分ける最初の手がかりです。
- **たとえ**: 病院の受付での断られ方の違いです。「名乗っていない（401）」「名乗っても入れない区画（403）」「そんな科は無い（404）」と、次に動く相手が変わります。
- **くわしく**: 200 は成功、301 は「引っ越したので新しい URL へ」という恒久的な案内です。401 は認証が済んでいない状態、403 は誰であってもその要求を許可しない状態です。404 は指定されたものが見つからないとき、500 はサーバー内部で処理が失敗したときに返る汎用のエラーです。502 は前に立つプロキシが後ろから正しい返事をもらえないとき、503 は混雑やメンテナンスで受け付けられないときに返ります。
- **覚え方**: 「401 は名乗っていない、403 は名乗っても入れない、404 はそもそも無い」と 3 点セットで覚えます。
- **まちがえやすい**: 502 と 503 はどちらも 5xx ですが、見る場所が違います。502 は後ろの AP サーバーが落ちている疑い、503 は受け止めきれない量が来ている疑いから調べます。
- **関連語**: [HTTP ステータスコード](#g-web-status-code) ／ [リダイレクト](#g-web-redirect) ／ [アップストリーム](#g-web-upstream)
- **確かめかた**: `curl -I https://example.com/` の 1 行目に数字が出ます。サーバー側では `tail -n 50 /var/log/nginx/access.log` で並びを眺めます（ログの場所は環境によって異なります）。

<a id="g-web-redirect"></a>
## リダイレクト

- **一言**: 別の URL へ行き先を案内し、ブラウザを自動で移動させる指示です。
- **たとえ**: 郵便の転送届です。旧住所に届いた手紙がそのまま新住所へ回されるので、差出人は住所を書き直さずに済みます。
- **くわしく**: 3xx のステータスコードと、移動先を書く Location というヘッダーの組で行います。301 は恒久的な引っ越し、302 は一時的な案内で、ブラウザや検索エンジンの覚え方が変わります。`http://` で来たアクセスを `https://` に寄せる設定でも、よく使います。
- **覚え方**: 「301 は引っ越し、302 は仮住まい」と覚えます。
- **まちがえやすい**: 301 はブラウザに強く記憶されます。間違えたまま公開すると、直したあとも古い転送先へ飛ばされ続けて見えることがあります。
- **関連語**: [200 や 404 などの具体例](#g-web-status-examples) ／ [HTTP ヘッダー](#g-web-http-header) ／ [HTTPS](#g-web-https)
- **確かめかた**: `curl -sIL https://example.com/` を実行すると、転送をたどった順にステータス行と移動先が並びます。

<a id="g-web-http-header"></a>
## HTTP ヘッダー（エイチ・ティー・ティー・ピー ヘッダー）

- **一言**: 本文の前に付ける、通信の条件や中身の説明を書いた送り状です。
- **たとえ**: 宅配便の送り状です。品名や大きさや送り主が書いてあるので、荷物（本文）を開けなくても外から条件が読めます。
- **くわしく**: 要求にも応答にも付き、要求側には Host（どのサイト宛てか）や User-Agent（ブラウザの種類）が入ります。応答側には Content-Type（中身の種類）や Set-Cookie などが入ります。キャッシュするか、圧縮するか、どの言語で返すかも、ヘッダーのやり取りで決まります。
- **覚え方**: 「荷物の中身が本文、貼ってある送り状がヘッダー」と覚えます。
- **まちがえやすい**: ヘッダーの中身は暗号化されていません。HTTPS なら経路上では守られますが、ブラウザやサーバーの中ではそのまま見えるので、秘密の値を入れないようにします。
- **関連語**: [HTTP](#g-web-http) ／ [Content-Type](#g-web-content-type) ／ [Cookie とセッション](#g-web-cookie-session)
- **確かめかた**: `curl -sD - -o /dev/null https://example.com/` で、本文を捨てて応答ヘッダーだけを表示できます。

<a id="g-web-content-type"></a>
## Content-Type（コンテント タイプ）

- **一言**: 返している中身が HTML か画像か JSON かを相手に伝えるヘッダーです。
- **たとえ**: 食品のラベルです。「これは牛乳です」と書いてあるから、中を見なくてもコップに注いでよいと分かります。
- **くわしく**: `text/html` や `application/json` のような形式名（MIME タイプ）を書きます。ブラウザはこの値を見て、画面に表示するか、ダウンロードするか、文字をどう解釈するかを決めます。API では `application/json` が付いていないと、受け取る側のプログラムが読み取りに失敗することがあります。
- **覚え方**: Content（中身）の Type（種類）で、そのまま「中身のラベル」だと覚えます。
- **まちがえやすい**: 文字化けの原因が、ファイルではなくこのヘッダーの文字コード指定にあることがあります。ファイルを作り直す前に、ヘッダーを確認します。
- **関連語**: [HTTP ヘッダー](#g-web-http-header) ／ [JSON](#g-web-json) ／ [静的コンテンツと動的コンテンツ](#g-web-static-dynamic)
- **確かめかた**: `curl -sI https://example.com/ | grep -i content-type` で、今どう名乗っているかが分かります。

<a id="g-web-cookie-session"></a>
## Cookie とセッション（クッキーとセッション）

- **一言**: Cookie はブラウザに預ける番号札、セッションはサーバー側の控えです。
- **たとえ**: 温泉旅館の下駄箱です。利用者が持つ番号札が Cookie、旅館側の「◯番の靴はこれ」という控えがセッションです。
- **くわしく**: サーバーは Set-Cookie ヘッダーで値をブラウザに渡し、ブラウザは次から Cookie ヘッダーで送り返します。ログイン状態は、セッション ID という番号札だけを Cookie に入れ、中身はサーバー側に置く作りが一般的です。そのため複数台に振り分けると、控えを持っていないサーバーに当たってログアウトすることがあります。
- **覚え方**: 「札はブラウザ、控えはサーバー」と、持ち主で分けて覚えます。
- **まちがえやすい**: 「Cookie を消したらログアウトした」は正常な動きです。Cookie が本体だと思っていると、サーバー側のセッション切れとの区別が付かなくなります。
- **関連語**: [スティッキーセッション](#g-web-sticky-session) ／ [HTTP ヘッダー](#g-web-http-header) ／ [HTTP](#g-web-http)
- **確かめかた**: ブラウザの開発者ツールの Application（またはストレージ）タブで、保存されている Cookie を一覧できます。

<a id="g-web-reverse-proxy"></a>
## リバースプロキシ

- **一言**: 利用者の前に立ち、後ろのサーバーへ要求を取り次ぐ受付役です。
- **たとえ**: マンションのコンシェルジュです。訪問者は必ず受付を通るので、住人の部屋番号は外から見えません。
- **くわしく**: 外からの通信をいったん受け、内側の AP サーバーへ渡して、返事を利用者に返します。HTTPS の暗号を解く役、複数サーバーへの振り分け、静的ファイルの肩代わりも、ここでまとめて受け持つことが多いです。内側のサーバーをインターネットに直接出さずに済むので、安全面でも有利です。
- **覚え方**: Reverse はサーバー側に立つ代理という意味で、守っているのはサーバーだと覚えます。
- **まちがえやすい**: 前にリバースプロキシがあると、アプリのログには利用者ではなくプロキシの IP アドレスが残ります。元の IP を残すには、X-Forwarded-For というヘッダーで引き継ぐ設定が要ります。
- **関連語**: [フォワードプロキシ](#g-web-forward-proxy) ／ [アップストリーム](#g-web-upstream) ／ [ロードバランサー](#g-web-load-balancer)
- **確かめかた**: `curl -sI https://example.com/ | grep -i server` で、前に立っているソフトの名前が見えることがあります（隠している場合もあります）。

<a id="g-web-upstream"></a>
## アップストリーム

- **一言**: プロキシから見て、要求を渡す先にいる後ろ側のサーバーのことです。
- **たとえ**: 受付の奥にいる担当部署です。来客は受付としか話しませんが、実際に手を動かしているのは奥の部署です。
- **くわしく**: Nginx の設定では、振り分け先のサーバー群を `upstream` という名前でまとめて書きます。バックエンドやオリジンと呼ぶこともあり、指しているものはほぼ同じです。502 が出たときは、このアップストリームが止まっているか、宛先の指定が違う可能性が高いです。
- **覚え方**: 「手前が利用者、奥がアップストリーム」と、立ち位置で覚えます。
- **まちがえやすい**: 「Nginx は動いているのに 502」はよくある形です。前に立つプロキシが生きていることと、後ろが生きていることは別なので、両方のログを見ます。
- **関連語**: [リバースプロキシ](#g-web-reverse-proxy) ／ [ロードバランサー](#g-web-load-balancer) ／ [200 や 404 などの具体例](#g-web-status-examples)
- **確かめかた**: サーバー上から `curl -sI http://127.0.0.1:8080/` のようにプロキシを通さず直接呼び、後ろ側だけで応答が返るか確かめます（ポートは環境によって異なります）。

<a id="g-web-forward-proxy"></a>
## フォワードプロキシ

- **一言**: 社内から外へ出る通信を代わりに行う、出口側の代理サーバーです。
- **たとえ**: 会社の郵便室です。社員は自分で投函せず郵便室に渡し、郵便室がまとめて出して、危ない宛先は止めます。
- **くわしく**: 利用者（クライアント）の側に立つ代理です。社内から外部サイトへ出るときに通し、見てよいサイトを制限したり、通信の記録を残したりします。外の相手から見ると、社員全員が同じ IP アドレスから来ているように見えます。
- **覚え方**: 「フォワードは自分の前、リバースはサーバーの前」と、守る相手が逆だと覚えます。
- **まちがえやすい**: 名前が似ているので混同しがちです。社内用のプロキシ設定を入れたまま持ち出した PC が、外でつながらなくなるのもよくあるトラブルです。
- **関連語**: [リバースプロキシ](#g-web-reverse-proxy) ／ [キャッシュ](#g-web-cache)
- **確かめかた**: `env | grep -i proxy` で、その端末に設定されているプロキシの宛先を確認できます。

<a id="g-web-load-balancer"></a>
## ロードバランサー

- **一言**: 同じ役割のサーバーへ要求を振り分け、負荷と故障に備える仕組みです。
- **たとえ**: スーパーのレジ整理係です。「3 番が空きました」と順に案内し、1 台のレジが閉まっても残りへ案内し直せます。
- **くわしく**: 利用者は代表の宛先 1 つにアクセスし、その後ろに同じ構成のサーバーが複数並びます。1 台が壊れても残りで受けられるので、止まらない作りの基本になります。振り分け方は負荷分散方式で決め、ヘルスチェックで生きているサーバーだけに送ります。LB と略され、専用の機器のこともソフトやクラウドのサービスのこともあります。
- **覚え方**: Load（荷物）を Balance（釣り合わせる）もので、レジの整理係だと覚えます。
- **まちがえやすい**: 台数を増やせば必ず速くなるわけではありません。奥の DB が 1 台で詰まっていれば、前を増やしても待ち時間は変わりません。
- **関連語**: [負荷分散方式](#g-web-balancing-method) ／ [ヘルスチェック](#g-web-health-check) ／ [リバースプロキシ](#g-web-reverse-proxy)
- **確かめかた**: 同じ URL に `curl -sI https://example.com/` を何度か実行し、応答ヘッダーに入るサーバー識別用の値が入れ替わるか見ます（設定によっては出ません）。

<a id="g-web-balancing-method"></a>
## 負荷分散方式（フカブンサンホウシキ）

- **一言**: どのサーバーへ振り分けるかの決め方で、順番か空き具合かで選びます。
- **たとえ**: ラウンドロビンは「はい次、はい次」と順に案内する係、最少接続は今いちばん空いているレジへ通す係です。
- **くわしく**: ラウンドロビンは 1 台目、2 台目、3 台目と順に回す単純な方式で、処理時間が似ている場合に向きます。最少接続は、その時点で抱えている接続の数が最も少ないサーバーへ送ります。処理時間にばらつきがある場合は、最少接続のほうが偏りにくくなります。ほかに、性能の高い機械へ多く送る重み付けの方式もあります。
- **覚え方**: 「順番で回すか、空き具合を見るか」の二択にして覚えます。
- **まちがえやすい**: ラウンドロビンは要求の数を均等に配るだけで、負荷まで均等になる保証はありません。重い処理が偏ると、1 台だけ苦しくなります。
- **関連語**: [ロードバランサー](#g-web-load-balancer) ／ [スティッキーセッション](#g-web-sticky-session) ／ [ヘルスチェック](#g-web-health-check)
- **確かめかた**: ロードバランサーの設定画面、または Nginx の `upstream` ブロックに `least_conn;` のような行があるかを見ます。

<a id="g-web-sticky-session"></a>
## スティッキーセッション

- **一言**: 同じ利用者の要求を、いつも同じサーバーへ送り続ける仕組みです。
- **たとえ**: 美容院の指名です。前回と同じ担当者に当たれば話が早いですが、別の人に当たると一から説明し直しになります。
- **くわしく**: セッションの控えを各サーバーが自分の中だけに持っていると、別のサーバーへ振られたときにログインし直しになります。それを避けるため、Cookie や送信元 IP アドレスを目印にして、同じサーバーへ固定します。ただし固定すると負荷が偏りやすく、そのサーバーが落ちるとセッションも失われます。根本的には、セッションを共有の保存先に置くほうが強い作りです。
- **覚え方**: Sticky は「くっつく」で、担当者を指名して離さない仕組みだと覚えます。
- **まちがえやすい**: スティッキーにすれば安心、ではありません。1 台落ちたときに「一部の利用者だけログアウトする」という形で障害が出ます。
- **関連語**: [Cookie とセッション](#g-web-cookie-session) ／ [ロードバランサー](#g-web-load-balancer) ／ [負荷分散方式](#g-web-balancing-method)
- **確かめかた**: 同じブラウザで操作を続け、ログイン状態が保たれるか確認します。設定項目の呼び名（セッション維持、セッションアフィニティなど）は製品によって異なります。

<a id="g-web-health-check"></a>
## ヘルスチェック

- **一言**: サーバーが元気かを定期的に確かめ、駄目なら振り分けから外す見張りです。
- **たとえ**: 朝礼の点呼です。「はい」と返事がない人には仕事を回さず、返事が戻ればまた回し始めます。
- **くわしく**: ロードバランサーや監視ソフトが、決まった間隔で決まった URL を呼びます。返ってきたステータスコードや応答時間が条件を満たさなければ異常とみなし、振り分け先から外します。ポートにつながるかだけを見る方式と、アプリの動きまで確かめる専用ページを用意する方式があります。後者のほうが「動いてはいるが中身が壊れている」状態を拾えます。
- **覚え方**: 「点呼に返事がなければ仕事を回さない」と覚えます。
- **まちがえやすい**: 確認先をトップページにすると、DB が壊れていても静的な部分だけ返って「正常」に見えることがあります。確かめたい範囲に合わせて、確認用のページを用意します。
- **関連語**: [ロードバランサー](#g-web-load-balancer) ／ [200 や 404 などの具体例](#g-web-status-examples) ／ [タイムアウト](#g-web-timeout)
- **確かめかた**: `curl -s -o /dev/null -w '%{http_code} %{time_total}\n' https://example.com/health` で、ステータスと応答時間を一度に見ます（パスは環境によって異なります）。

<a id="g-web-api"></a>
## API（エー・ピー・アイ）

- **一言**: プログラム同士がやり取りするために用意された、決まった形の窓口です。
- **たとえ**: 自動販売機です。中の仕組みを知らなくても、お金を入れてボタンを押せば飲み物が出てきます。
- **くわしく**: 人がブラウザで見る画面ではなく、プログラムが呼び出して使う入口です。「この宛先に、この形で送れば、この形で返す」という取り決めがあり、それを守れば別の会社のソフトともつながります。地図や決済や天気の機能を自分で作らずに済むのは、API のおかげです。
- **覚え方**: Application Programming Interface の略で、自販機のボタンのようなアプリ同士の接点だと覚えます。
- **まちがえやすい**: 「API が落ちている」と言われたら、相手側なのか自分の呼び出し方なのかを切り分けます。4xx なら呼び方、5xx なら相手側を先に疑います。
- **関連語**: [REST API](#g-web-rest-api) ／ [エンドポイント](#g-web-endpoint) ／ [JSON](#g-web-json)
- **確かめかた**: 提供元の仕様書を開き、宛先・メソッド・必要な項目の 3 点を突き合わせます。

<a id="g-web-rest-api"></a>
## REST API（レスト エー・ピー・アイ）

- **一言**: URL でモノを指し、HTTP メソッドで操作する、API の設計の作法です。
- **たとえ**: 図書館の請求番号と手続きの組み合わせです。棚の場所（URL）で本を指し、借りるか返すかの手続き（メソッド）を選びます。
- **くわしく**: `/users/123` のように対象を URL で表し、GET で取得、POST で作成、PUT で更新、DELETE で削除を行います。やり取りするデータは JSON で書くことが多いです。URL には動詞を入れず名詞で表すのが作法で、`/getUser` ではなく `/users/123` と書きます。
- **覚え方**: 「名詞は URL、動詞はメソッド」と覚えます。
- **まちがえやすい**: REST は厳密な規格ではないので、現場ごとに解釈の幅があります。似て非なる作りも多いので、最後は仕様書を読むのが確実です。
- **関連語**: [API](#g-web-api) ／ [HTTP メソッド](#g-web-http-method) ／ [エンドポイント](#g-web-endpoint)
- **確かめかた**: `curl -s https://example.com/api/users/1` のように GET だけを試し、返ってくるデータの形を確認します。

<a id="g-web-endpoint"></a>
## エンドポイント

- **一言**: API で「ここに送ってください」と決められた、個別の宛先 URL です。
- **たとえ**: 会社の部署ごとの窓口です。「返品は 3 番、契約は 5 番」と決まっていて、間違えると受け付けてもらえません。
- **くわしく**: `https://example.com/api/v1/users` のように、機能ごとに 1 本ずつ用意されます。同じ URL でもメソッドが違えば別の動きになることが多いので、宛先とメソッドはセットで覚えます。監視やヘルスチェックの宛先としても指定します。
- **覚え方**: 端（エンド）にある受け取り口（ポイント）で、窓口の番号札だと覚えます。
- **まちがえやすい**: 末尾のスラッシュの有無や `/v1` のようなバージョン部分の違いで、別物として扱われます。つながらないときは、1 文字ずつ突き合わせます。
- **関連語**: [API](#g-web-api) ／ [URL と URI](#g-web-url-uri) ／ [REST API](#g-web-rest-api)
- **確かめかた**: `curl -s -o /dev/null -w '%{http_code}\n' https://example.com/api/v1/users` で、宛先が生きているかを数字で確かめます。

<a id="g-web-json"></a>
## JSON（ジェイソン）

- **一言**: 名前と値の組でデータを書き表す、人も機械も読める文字の形式です。
- **たとえ**: 送り状の記入欄です。「氏名」「電話」と項目名と値が並ぶので、誰が読んでも同じ理解になります。
- **くわしく**: `{"name": "yamada", "age": 30}` のように波括弧で書きます。API のやり取りや設定ファイルで広く使われます。文字列は必ずダブルクォートで囲み、最後の項目の後ろにカンマを置けません。コメントも書けないので、設定ファイルとして扱うときにつまずきやすいところです。
- **覚え方**: 「名前と値の並び」で、カンマとクォートに厳しい形式だと覚えます。
- **まちがえやすい**: 全角のダブルクォートや、末尾の余計なカンマで読み込みに失敗します。エラーが出たら、中身を疑う前に書式を検査します。
- **関連語**: [API](#g-web-api) ／ [Content-Type](#g-web-content-type) ／ [REST API](#g-web-rest-api)
- **確かめかた**: `python3 -m json.tool < data.json` で書式が正しいか検査できます（`jq` が入っていれば `jq . data.json` でも見られます）。

<a id="g-web-static-dynamic"></a>
## 静的コンテンツと動的コンテンツ（セイテキコンテンツとドウテキコンテンツ）

- **一言**: 置いたファイルをそのまま返すか、その場で作って返すかの違いです。
- **たとえ**: 作り置きの惣菜と、注文を受けてからの調理です。作り置きはすぐ出せますが誰にでも同じ物、調理は待ちますが注文どおりの中身になります。
- **くわしく**: 画像、CSS、JavaScript のファイルなどは静的で、誰が見ても同じ物を返せます。マイページや検索結果は利用者ごとに違うので、AP サーバーが毎回組み立てます。静的なものは Web サーバーや CDN に任せると、表示が速くなりサーバーの負担も減ります。
- **覚え方**: 「作り置きは静的、注文調理は動的」と覚えます。
- **まちがえやすい**: 「画面が動くから動的」ではありません。アニメーションしていても、返しているファイルが毎回同じなら静的です。
- **関連語**: [Web サーバー](#g-web-web-server) ／ [AP サーバー](#g-web-ap-server) ／ [CDN](#g-web-cdn)
- **確かめかた**: `curl -sI https://example.com/style.css | grep -iE 'content-type|last-modified'` を見ます。静的なファイルには更新日時が付きやすく、動的なページでは付かないことが多いです（環境によって異なります）。

<a id="g-web-cdn"></a>
## CDN（シー・ディー・エヌ）

- **一言**: 各地に置いた配信拠点から、利用者に近い場所で中身を届ける仕組みです。
- **たとえ**: 全国のコンビニに商品を置いておく形です。本社の倉庫まで行かなくても近所の店で受け取れるので、早く手に入ります。
- **くわしく**: 画像や動画などの静的コンテンツを、各地のキャッシュサーバーに複製して配ります。近い拠点が返すので表示が速くなり、元のサーバー（オリジン）への負担も減ります。急なアクセス集中を受け止める役割もあります。
- **覚え方**: Content Delivery Network の略で、中身を配る全国のコンビニ網だと覚えます。
- **まちがえやすい**: ファイルを差し替えても、CDN に古いものが残っていれば新しく見えません。反映には、取り置きの期限が切れるのを待つか、消す手続きが必要です。
- **関連語**: [キャッシュ](#g-web-cache) ／ [静的コンテンツと動的コンテンツ](#g-web-static-dynamic) ／ [リバースプロキシ](#g-web-reverse-proxy)
- **確かめかた**: `curl -sI https://example.com/logo.png` の応答ヘッダーに、配信事業者の名前や取り置きに当たったかを示す行が出ることがあります。

<a id="g-web-cache"></a>
## キャッシュ

- **一言**: 一度取り出した結果を手元に取り置きし、次を速くする仕組みです。
- **たとえ**: よく使う調味料を、倉庫ではなく調理台に出しておくのと同じです。取りに行く手間が消えるので、次から早く出せます。
- **くわしく**: ブラウザの中、CDN、リバースプロキシ、アプリの中など、いろいろな場所に置かれます。どれくらい取り置きしてよいかは、Cache-Control などのヘッダーで指示します。速くなる代わりに、古い内容を返してしまう危険と隣り合わせです。
- **覚え方**: 「速さと新しさは引き換え」と覚えます。
- **まちがえやすい**: 「直したのに反映されない」の多くはキャッシュです。サーバーを疑う前に、別のブラウザや読み込み直しで同じに見えるかを確認します。
- **関連語**: [CDN](#g-web-cdn) ／ [HTTP ヘッダー](#g-web-http-header) ／ [静的コンテンツと動的コンテンツ](#g-web-static-dynamic)
- **確かめかた**: `curl -sI https://example.com/style.css | grep -i cache-control` で取り置きの指示を見ます。ブラウザの開発者ツールでも、キャッシュから返ったかどうかが Size 欄に出ます。

<a id="g-web-websocket"></a>
## WebSocket（ウェブソケット）

- **一言**: 一度つないだ通信路で、双方向にやり取りを続けられる仕組みです。
- **たとえ**: HTTP がその都度かけ直す電話なら、WebSocket はつなぎっぱなしの内線です。相手からも好きなときに話しかけられます。
- **くわしく**: 最初は HTTP でつなぎ、そこから専用の通信へ切り替えます。チャット、通知、価格や対戦画面の更新など、サーバー側から送りたい場面で使います。URL は `ws://`、暗号化する場合は `wss://` で始まります。つなぎっぱなしなので、途中のプロキシやロードバランサーのタイムアウト設定に注意が要ります。
- **覚え方**: 「HTTP は毎回かけ直す電話、WebSocket は内線つなぎっぱなし」と覚えます。
- **まちがえやすい**: 前にリバースプロキシがあると、専用の設定を入れないと接続が切れます。「手元では動くのに本番で切れる」ときは、まずここを疑います。
- **関連語**: [HTTP](#g-web-http) ／ [タイムアウト](#g-web-timeout) ／ [リバースプロキシ](#g-web-reverse-proxy)
- **確かめかた**: ブラウザの開発者ツールの Network タブで WS（または WebSocket）に絞ると、接続とやり取りが見られます。

<a id="g-web-timeout"></a>
## タイムアウト

- **一言**: 返事を待つ上限の時間で、過ぎたら諦めてエラーにする決まりです。
- **たとえ**: 電話の呼び出しです。何回コールして出なければ切る、と決めておくのと同じで、いつまでも受話器を持ち続けません。
- **くわしく**: つなぎに行く時間、返事を待つ時間、接続を保つ時間など、種類ごとに別々の設定があります。短すぎると重い処理が途中で切れ、長すぎると詰まった接続がサーバーに溜まります。プロキシとアプリで値がずれていると、片方だけ先に切れて 502 や 504 として表に出ます。
- **覚え方**: 「待つのをやめる線引き」で、短すぎても長すぎても困ると覚えます。
- **まちがえやすい**: タイムアウトは原因ではなく症状です。値を伸ばす前に、なぜ遅いのかを先に調べます。
- **関連語**: [ヘルスチェック](#g-web-health-check) ／ [リバースプロキシ](#g-web-reverse-proxy) ／ [WebSocket](#g-web-websocket)
- **確かめかた**: `curl -s -o /dev/null -w '%{time_total}\n' https://example.com/` で、実際にかかっている秒数を測ります。

<a id="g-web-nginx-apache"></a>
## Nginx と Apache（エンジンエックスとアパッチ）

- **一言**: どちらも定番の Web サーバーソフトで、得意なところが少し違います。
- **たとえ**: 同じ受付でも、大勢の来客を手早くさばくのが得意な人と、細かい要望に個別に応えるのが得意な人がいるのと同じです。
- **くわしく**: Nginx は多数の接続を少ない資源でさばく作りで、リバースプロキシやロードバランサーとしてもよく使われます。Apache は歴史が長く、機能を後から足すモジュールが豊富です。Apache は `.htaccess` というファイルでディレクトリごとに設定を上書きでき、Nginx にその仕組みはありません。どちらを使うかは、既存の構成や運用ルールで決まることが多いです。
- **覚え方**: 「Nginx はさばく、Apache は細かく効かせる」と覚えます。
- **まちがえやすい**: 設定ファイルを直しただけでは反映されません。書式に誤りがあると再起動で起動に失敗し、サイトが落ちることがあるので、必ず先に書式検査をします。
- **関連語**: [Web サーバー](#g-web-web-server) ／ [バーチャルホスト](#g-web-virtual-host) ／ [ドキュメントルート](#g-web-document-root)
- **確かめかた**: 書式検査は Nginx が `nginx -t`、Apache が `apachectl configtest` です。版数は `nginx -v` や `httpd -v` で見られます（コマンド名は環境によって異なります）。

<a id="g-web-virtual-host"></a>
## バーチャルホスト

- **一言**: 1 台のサーバーで、複数のドメインのサイトを出し分ける設定です。
- **たとえ**: 1 棟のビルに複数の会社が入っているのと同じです。住所は同じでも、受付が社名を見て別のフロアへ案内します。
- **くわしく**: ブラウザは要求の Host ヘッダーに「どのドメイン宛てか」を書いて送ります。Web サーバーはその名前を見て、対応する設定とドキュメントルートを選びます。HTTPS では、暗号化を始める段階で SNI という仕組みを使って名前を伝えます。Apache では `<VirtualHost>`、Nginx では `server` ブロックとして書きます。
- **覚え方**: 「1 棟のビルに複数の表札」で、表札の名前で行き先が決まると覚えます。
- **まちがえやすい**: どの表札にも当てはまらない要求は、既定の設定に流れます。「別のサイトの画面が出た」ときは、DNS ではなくこの振り分けが原因のことがあります。
- **関連語**: [ドキュメントルート](#g-web-document-root) ／ [Nginx と Apache](#g-web-nginx-apache) ／ [HTTP ヘッダー](#g-web-http-header)
- **確かめかた**: `curl -sI -H 'Host: example.com' http://127.0.0.1/` のように名前を指定して、どの設定に当たるかを確かめます。

<a id="g-web-document-root"></a>
## ドキュメントルート

- **一言**: 公開するファイルの置き場所で、URL のパスの起点になる場所です。
- **たとえ**: 店の陳列棚です。棚に出した物だけがお客さんに見え、倉庫に置いたままの物は買えません。
- **くわしく**: ドキュメントルートが `/var/www/html` だとします。このとき `https://example.com/logo.png` は `/var/www/html/logo.png` を指します。ここに置いていないファイルは、URL を呼んでも見つかりません。逆に、置いてはいけない設定ファイルやバックアップを置くと、誰でも読めてしまう危険があります。
- **覚え方**: 「URL の `/` がドキュメントルート」で、ここが基準点だと覚えます。
- **まちがえやすい**: 見えないと URL を疑いがちですが、置き場所は合っていて権限が足りず 403 になることもあります。まず数字で切り分け、置き場所と権限の両方を見ます。
- **関連語**: [バーチャルホスト](#g-web-virtual-host) ／ [Web サーバー](#g-web-web-server) ／ [URL と URI](#g-web-url-uri)
- **確かめかた**: `grep -rniE 'root|documentroot' /etc/nginx/` のように設定から場所を探し、`ls -l` で実際のファイルの有無と権限を見ます（パスは環境によって異なります）。
