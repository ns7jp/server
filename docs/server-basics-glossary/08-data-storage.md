# 8. データベース・ストレージ・バックアップ

[用語集の入口](README.md) / [さくいん](index.md) / [前: Web とアプリケーション](07-web.md) / [次: 仮想化・コンテナ・クラウド](09-virtualization-cloud.md)

この章では、データそのものを扱う言葉と、そのデータを失わないための言葉をまとめます。障害対応の最後に効いてくるのは、ここの理解です。

> **この章で最初に押さえる 3 語**: バックアップ ／ リストアとリカバリ ／ トランザクション

<a id="g-data-database"></a>
## データベース

- **一言**: 大量のデータを決まった形でしまい、すぐ探し出せるようにした仕組みです。
- **たとえ**: 図書館の書庫です。本を積み上げず、棚と番号を決めて並べるので、1 冊を数秒で取り出せます。
- **くわしく**: アプリはデータを自分で抱え込まず、データベースに預けます。同時に何人が読み書きしても壊れないよう、順番の調整や記録はデータベース側が引き受けます。Web サーバーとデータベースを別の機械に分けて立てることもよくあります。
- **覚え方**: 倉庫（データ本体）と倉庫番（管理ソフト）がセットになったもの、と覚えます。
- **まちがえやすい**: データが入ったファイルと、それを管理するソフト（DBMS）を混同しがちです。起動や停止の対象になるのはソフトのほうです。
- **関連語**: [RDBMS](#g-data-rdbms) ／ [NoSQL](#g-data-nosql) ／ [SQL](#g-data-sql)
- **確かめかた**: 動いているかは `systemctl status mariadb` や `systemctl status postgresql` で見ます。サービス名は環境によって異なります。

<a id="g-data-rdbms"></a>
## RDBMS（アール・ディー・ビー・エム・エス）

- **一言**: 表の形でデータを持ち、表どうしをつないで扱えるデータベースのソフトです。
- **たとえ**: 表を何枚も置いた事務所です。「社員表」と「部署表」を社員番号でつなげば、部署名まで一度に引けます。
- **くわしく**: MySQL、PostgreSQL、Oracle Database、SQL Server などが代表です。列の型（数値か文字か）や重複禁止といったルールを先に決め、そこから外れるデータは受け付けません。ルールが厳しいぶん、売上や在庫のような間違えられないデータに向きます。
- **覚え方**: R は Relational（関係）の R で、表と表の関係をたどれるデータベースだと覚えます。
- **まちがえやすい**: SQL は操作を頼むための言葉、RDBMS はその言葉を受け取って動くソフトの種類です。「SQL を入れる」と言うときも、実際に導入するのは MySQL などの製品です。
- **関連語**: [データベース](#g-data-database) ／ [SQL](#g-data-sql) ／ [テーブル・レコード・カラム](#g-data-table-record-column)
- **確かめかた**: `mysql --version` や `psql --version` で分かるのは、操作する側（クライアント）の版です。サーバー側の版は接続して `SELECT version();` で確認します。

<a id="g-data-nosql"></a>
## NoSQL（ノー・エス・キュー・エル）

- **一言**: 表の形にこだわらず、用途に合った入れ物でデータを持つデータベースです。
- **たとえ**: 何でも放り込める大きな引き出しです。書類の様式が案件ごとに違っても、そのまま入れておけます。
- **くわしく**: 鍵と値の組で持つもの、JSON（データを書き表す形式のひとつ）のような文書の形で持つもの、列を柔軟に増やせるものなどがあります。項目が案件ごとに変わるデータや、大量のアクセスを何台にも分けて捌きたい場合に選ばれます。ただし表どうしの結合や厳密な整合性は、製品によって得意不得意が分かれます。
- **覚え方**: 「SQL を使わない」ではなく「Not only SQL（SQL だけではない）」と広げて読むと、役割がつかめます。
- **まちがえやすい**: NoSQL は RDBMS の新しい上位版ではありません。集計や整合性が要る業務データは、今も RDBMS が向いています。
- **関連語**: [RDBMS](#g-data-rdbms) ／ [データベース](#g-data-database) ／ [オブジェクトストレージ](#g-data-object-storage)
- **確かめかた**: 何が動いているかは `systemctl status redis` などで見ます。待ち受け中のポートは `ss -lntp` で一覧できます（プロセス名の表示には管理者権限が要ります）。

<a id="g-data-table-record-column"></a>
## テーブル・レコード・カラム

- **一言**: 表と、その 1 行と、1 列。データの置き場所を指す 3 点セットです。
- **たとえ**: クラスの名簿です。名簿全体がテーブル、生徒 1 人ぶんの横 1 行がレコード、「氏名」「組」といった縦の並びがカラムです。
- **くわしく**: テーブルは扱う種類ごとに分けて作ります。レコードは 1 件ぶんのデータ、カラムはその項目名と型です。障害調査では「どのテーブルの、どのレコードの、どのカラムがおかしいか」を言えると、話が早く進みます。
- **覚え方**: カラム（column）は柱と同じ語だから縦、レコード（記録）は横 1 行、と結び付けます。
- **まちがえやすい**: 同じものが、人や製品によってフィールド、行、属性とも呼ばれます。呼び名が違うだけで別物だと思い込み、話が食い違うことがあります。
- **関連語**: [主キー](#g-data-primary-key) ／ [RDBMS](#g-data-rdbms) ／ [SQL](#g-data-sql)
- **確かめかた**: 列の並びは `DESCRIBE users;`（MySQL）や `\d users`（PostgreSQL）で見られます。

<a id="g-data-primary-key"></a>
## 主キー（シュキー）

- **一言**: 表の中の 1 行をただ 1 つに特定できる、重複しない目印の列です。
- **たとえ**: 社員番号です。同姓同名の田中さんが 2 人いても、番号が違えば別人だと分かります。
- **くわしく**: 主キーは空にできず、同じ値を 2 件持てません。この決まりのおかげで、更新や削除がよその行に及ぶ事故を防げます。多くの RDBMS では主キーに索引（インデックス）が自動で作られ、その列での検索も速くなります。
- **覚え方**: 名前は重なるが番号は重ならない、だから番号で呼ぶ、と覚えます。
- **まちがえやすい**: メールアドレスや電話番号を主キーにすると、変更されたときに困ります。あとから変わらない値を選びます。
- **関連語**: [テーブル・レコード・カラム](#g-data-table-record-column) ／ [インデックス](#g-data-index) ／ [RDBMS](#g-data-rdbms)
- **確かめかた**: MySQL なら `SHOW KEYS FROM users;` を実行し、PRIMARY と書かれた行を探します。

<a id="g-data-normalization"></a>
## 正規化（セイキカ）

- **一言**: 同じデータの重複をなくすように、表を分けて整理する設計の手順です。
- **たとえ**: 会社の住所録です。全員の行に会社の住所を書くのをやめ、会社の表を別に作って番号でつなぎます。
- **くわしく**: 同じ値をあちこちの行に書くと、片方だけ直して食い違う事故が起きます。正規化では、繰り返し出てくる項目を別の表へ切り出し、主キーでつなぎ直します。分け方には段階があり、第 1 から第 3 正規形（どこまで分けたかを表す段階の呼び名）まで進めるのが業務システムの目安です。
- **覚え方**: 同じことは 1 か所にだけ書く、が合言葉だと覚えます。
- **まちがえやすい**: 分ければ分けるほどよい、ではありません。表をつなぎ合わせる手間が増えるので、集計を速くしたい場面ではあえて重複を残すこともあります。
- **関連語**: [テーブル・レコード・カラム](#g-data-table-record-column) ／ [主キー](#g-data-primary-key) ／ [RDBMS](#g-data-rdbms)
- **確かめかた**: 表の一覧を `SHOW TABLES;`（MySQL）や `\dt`（PostgreSQL）で見て、同じ項目が複数の表で重複していないか確かめます。

<a id="g-data-index"></a>
## インデックス

- **一言**: 目的の行を速く見つけるために、別に作っておく検索用の索引です。
- **たとえ**: 本の巻末の索引です。全ページをめくらなくても、「ネットワーク…120 ページ」と一発で飛べます。
- **くわしく**: 索引がないと、データベースは表を先頭から最後まで読みます。件数が増えるほど遅くなるので、検索条件によく使う列に索引を付けます。ただし索引は書き込みのたびに更新が要るため、付けすぎると登録や更新が遅くなります。
- **覚え方**: 読みが速くなる代わりに、書きが少し重くなる、と対で覚えます。
- **まちがえやすい**: 索引を足しても、条件の書き方によっては使われません。列を関数で加工した条件が代表で、遅いときは実行計画（データベースが選んだ探し方の説明）を見て確かめます。
- **関連語**: [主キー](#g-data-primary-key) ／ [SQL](#g-data-sql) ／ [テーブル・レコード・カラム](#g-data-table-record-column)
- **確かめかた**: `EXPLAIN SELECT * FROM users WHERE id = 1;` で索引が使われるか見ます。EXPLAIN だけなら文は実行されません（`EXPLAIN ANALYZE` は実際に実行するので使い分けます）。

<a id="g-data-sql"></a>
## SQL（エス・キュー・エル）

- **一言**: データベースに「取って」「入れて」と頼むための共通の言葉です。
- **たとえ**: 図書館のカウンターで使う決まり文句です。「この条件に合う本を出してください」という言い方が決まっています。
- **くわしく**: SELECT で取り出し、INSERT で追加、UPDATE で書き換え、DELETE で消します。製品ごとに方言はありますが、基本の文はどの RDBMS でもほぼ同じです。本番では、まず SELECT で対象の件数を数えてから更新すると安全です。
- **覚え方**: 取る SELECT、足す INSERT、直す UPDATE、消す DELETE の 4 つが土台だと覚えます。
- **まちがえやすい**: WHERE を付け忘れた UPDATE や DELETE は全行に効きます。本番では条件と件数を先に確かめ、トランザクションの中で実行します。
- **関連語**: [RDBMS](#g-data-rdbms) ／ [トランザクション](#g-data-transaction) ／ [インデックス](#g-data-index)
- **確かめかた**: 件数の確認は `SELECT COUNT(*) FROM users;` です。読み取りだけなので、データは変わりません。

<a id="g-data-slow-query"></a>
## スロークエリ

- **一言**: 実行に時間がかかりすぎている、データベースへの問い合わせのことです。
- **たとえ**: 窓口の行列です。1 人だけ手続きに 10 分かかる客がいると、後ろの全員が待たされます。
- **くわしく**: 「Web が重い」と言われたとき、原因が 1 本の遅い問い合わせに集まっていることはよくあります。データベースには、決めた秒数を超えた問い合わせだけを書き出す記録（スロークエリログ）があります。そこで見つけた文を実行計画（データベースが選んだ探し方の説明）と突き合わせ、索引の追加や文の書き直しを検討します。遅い文は接続を長く握るため、ほかの利用者まで待たされます。
- **覚え方**: 重いのはサーバー全体ではなく、たいてい特定の 1 本だと覚えます。
- **まちがえやすい**: 記録に出た秒数は、その 1 本にかかった時間です。ほかの処理の順番待ちで遅く見えることもあるので、文の書き方だけを疑うと原因を外します。
- **関連語**: [インデックス](#g-data-index) ／ [SQL](#g-data-sql) ／ [コネクションプール](#g-data-connection-pool)
- **確かめかた**: MySQL なら `SHOW VARIABLES LIKE 'slow_query%';` で記録の設定と出力先が分かります。PostgreSQL では `SHOW log_min_duration_statement;` を見ます。

<a id="g-data-transaction"></a>
## トランザクション

- **一言**: いくつかの処理を「全部成功か、全部なかったこと」にまとめる単位です。
- **たとえ**: 銀行の振込です。「A から引く」「B に足す」の片方だけ成功したら大事故なので、2 つで 1 セットにします。
- **くわしく**: 開始してから複数の操作を行い、最後にまとめて確定します。途中で失敗すれば、開始前の状態へまとめて戻せます。在庫の引き当てと注文の登録のように、片方だけ残ると困る処理はこの単位でくくります。
- **覚え方**: 中途半端を許さない「全部か、ゼロか」の箱だと覚えます。
- **まちがえやすい**: 開いたまま放置すると、ほかの処理が順番待ちになり、システム全体が止まって見えます。短く終わらせるのが鉄則です。
- **関連語**: [コミットとロールバック](#g-data-commit-rollback) ／ [ACID](#g-data-acid) ／ [デッドロック](#g-data-deadlock)
- **確かめかた**: MySQL なら `SHOW ENGINE INNODB STATUS\G` の TRANSACTIONS 欄を見ます。PostgreSQL なら `SELECT * FROM pg_stat_activity;` で、長く開いたままの処理を探します。

<a id="g-data-commit-rollback"></a>
## コミットとロールバック

- **一言**: 変更を確定させるのがコミット、なかったことに戻すのがロールバックです。
- **たとえ**: 書類の清書です。ハンコを押して提出するのがコミット、下書きを破って書き直すのがロールバックです。
- **くわしく**: トランザクションの中の変更は、ふつうの設定ではコミットするまでほかの利用者に見えません。どこまで見えるかは分離レベル（同時に動く処理どうしの見え方を決める設定）で変わります。自動コミット（1 文ごとに自動で確定する設定）が有効だと、実行したその場で確定します。手作業で流す前に `BEGIN` などでトランザクションを始めておけば、間違えても戻せます。
- **覚え方**: コミットは確定、ロールバックは巻き戻し（roll back）だと覚えます。
- **まちがえやすい**: コミットしたあとはロールバックできません。それでも戻したいときは、バックアップからのリストアなど別の手段が必要です。
- **関連語**: [トランザクション](#g-data-transaction) ／ [ACID](#g-data-acid) ／ [リストアとリカバリ](#g-data-restore-recovery)
- **確かめかた**: MySQL では `SELECT @@autocommit;` で自動コミットの状態が分かります。値が 1 なら有効です。

<a id="g-data-acid"></a>
## ACID（アシッド）

- **一言**: 壊れないデータベースが守る 4 つの約束の頭文字です。
- **たとえ**: 引っ越し業者の約束に似ています。荷物は全部運ぶか運ばないか、中身は壊さない、よその家の荷物と混ぜない、届いたら受領印が残る、の 4 つです。
- **くわしく**: A（原子性）は全部か無か、C（一貫性）は決めたルールを壊さないことです。I（分離性）は同時に動く処理どうしが混ざらないこと、D（永続性）は確定したら電源が落ちても消えないことです。I は独立性とも訳されます。多くの RDBMS はこれを守るため、変更をまず記録（ログ）に書いてからデータ本体を更新します。
- **覚え方**: 頭文字を「全部か無か・筋を通す・混ざらない・消えない」と並べて唱えます。
- **まちがえやすい**: ACID を守るからバックアップは不要、ではありません。人が誤った SQL を流せば、その誤りが確実に残るだけです。
- **関連語**: [トランザクション](#g-data-transaction) ／ [コミットとロールバック](#g-data-commit-rollback) ／ [トランザクションログ](#g-data-transaction-log)
- **確かめかた**: PostgreSQL なら `SHOW fsync;` で、書き込みを確実にディスクへ落とす設定かどうかを確認できます。

<a id="g-data-deadlock"></a>
## デッドロック

- **一言**: 2 つの処理が互いに相手待ちになり、どちらも先へ進めなくなる状態です。
- **たとえ**: 狭い廊下で向かい合った 2 人です。互いに「そっちが先にどいて」と待ち、どちらも動けません。
- **くわしく**: 片方が A の行を押さえて B の行を待ち、もう片方が B の行を押さえて A の行を待つと起こります。多くの RDBMS はこれを検知し、片方を強制的に打ち切ってアプリにエラーを返します。更新する順番をそろえる、トランザクションを短くする、で発生を減らせます。
- **覚え方**: 狭い廊下のにらみ合いで、どちらも譲らず永久待ち、と覚えます。
- **まちがえやすい**: 順番待ちしているだけの「ロック待ち」とは別物です。ロック待ちは時間切れまで待ちますが、デッドロックは検知されて片方がエラーになります。
- **関連語**: [トランザクション](#g-data-transaction) ／ [コミットとロールバック](#g-data-commit-rollback) ／ [コネクションプール](#g-data-connection-pool)
- **確かめかた**: MySQL なら `SHOW ENGINE INNODB STATUS\G` の LATEST DETECTED DEADLOCK 欄に、直近の記録が出ます。

<a id="g-data-replication"></a>
## レプリケーション

- **一言**: 片方のデータベースの更新を、もう 1 台へ自動で写し続ける仕組みです。
- **たとえ**: 複写式の伝票です。上の紙に書けば、下の紙にも同じ内容がそのまま写ります。
- **くわしく**: 更新の記録を渡し合い、別のサーバーに同じ状態を再現します。故障時の切り替え先を用意する、読み取りを分担して負荷を下げる、といった目的で使います。写しが少し遅れて届くことがあり、この遅れをレプリケーション遅延（ラグ）と呼びます。遅れをなくす同期方式もありますが、そのぶん書き込みは遅くなります。
- **覚え方**: replica は複製のことで、常にコピーし続ける係だと覚えます。
- **まちがえやすい**: レプリケーションはバックアップの代わりになりません。誤って消したデータは、写し先でも同じように消えます。
- **関連語**: [マスター（プライマリ）とレプリカ](#g-data-primary-replica) ／ [冗長化とバックアップの違い](#g-data-redundancy-vs-backup) ／ [トランザクションログ](#g-data-transaction-log)
- **確かめかた**: MySQL なら `SHOW REPLICA STATUS\G`（版によっては `SHOW SLAVE STATUS\G`）で見ます。PostgreSQL ならプライマリ側で `SELECT * FROM pg_stat_replication;` を実行します。

<a id="g-data-primary-replica"></a>
## マスター（プライマリ）とレプリカ（マスタートレプリカ）

- **一言**: 書き込みを受け付ける本番機と、その写しを持つ控えの機械のことです。
- **たとえ**: 手書きの原本と複写です。書き込んでよいのは原本だけで、複写は見るため、控えとして残すためにあります。
- **くわしく**: 更新はマスター（プライマリ）にだけ行い、レプリカは同じ内容を受け取って持ち続けます。読み取りをレプリカに振ると、本番機の負担を減らせます。マスターが壊れたときはレプリカを昇格させ、新しいマスターにします（フェイルオーバー）。
- **覚え方**: 書くのは 1 台だけ、読むのは何台でもよい、と覚えます。
- **まちがえやすい**: 呼び名はマスター／スレーブからプライマリ／レプリカへ言い換えが進みましたが、指すものは同じです。レプリカを読み取り専用にしておかないと、直接書き込まれて写しがずれます。
- **関連語**: [レプリケーション](#g-data-replication) ／ [冗長化とバックアップの違い](#g-data-redundancy-vs-backup) ／ [コネクションプール](#g-data-connection-pool)
- **確かめかた**: PostgreSQL では `SELECT pg_is_in_recovery();` の結果が t（true）なら、その機械はレプリカ側です。

<a id="g-data-connection-pool"></a>
## コネクションプール

- **一言**: データベースへの接続をあらかじめ作り置きし、使い回すための仕組みです。
- **たとえ**: レストランの取り皿です。客ごとに洗い場から出すのではなく、何枚か手元に用意し、返してもらってまた使います。
- **くわしく**: 接続は作るたびに時間と資源を使うので、処理のたびに開いていると遅くなります。プールに一定数を保持し、処理が終わったら閉じずに返却させます。数が少なすぎると順番待ちが出て、多すぎるとデータベース側の上限に当たります。
- **覚え方**: pool はため池のことで、借りたら返す貸し出しカウンターだと覚えます。
- **まちがえやすい**: 「接続が足りない」と見えても、遅いクエリが接続を握って返していないだけのことが多いです。数を増やす前に、何が握っているかを見ます。
- **関連語**: [トランザクション](#g-data-transaction) ／ [デッドロック](#g-data-deadlock) ／ タイムアウト
- **確かめかた**: MySQL なら `SHOW STATUS LIKE 'Threads_connected';` と `SHOW VARIABLES LIKE 'max_connections';` を見比べます。

<a id="g-data-das-nas-san"></a>
## DAS・NAS・SAN（ダス・ナス・サン）

- **一言**: ディスクのつなぎ方 3 種で、直結・ネットワーク経由・専用網の違いです。
- **たとえ**: DAS は机に置いた外付け HDD、NAS は事務所の共有書庫、SAN は倉庫と事務所を結ぶ専用のトラック便です。
- **くわしく**: DAS はサーバーに直結する方式で、速い代わりにそのサーバー専用です。NAS はネットワーク越しにファイル単位で共有し、複数のサーバーから使えます。SAN は主に専用のネットワークでディスク（ブロック）単位に見せるので、サーバーからは内蔵ディスクのように扱えます。
- **覚え方**: D は直結、N はネットワーク越しのファイル、S は専用網のブロック、と覚えます。
- **まちがえやすい**: NAS と SAN の違いは、速さよりも見え方です。ファイルとして見えるのが NAS、ディスクとして見えるのが SAN です。
- **関連語**: [オブジェクトストレージ](#g-data-object-storage) ／ [ファイルサーバーと共有プロトコル](#g-data-file-server-smb-nfs) ／ [スナップショット](#g-data-snapshot)
- **確かめかた**: `lsblk` でつながっているブロック装置を、`df -hT` でマウント中のファイルシステムの種類を確認します。

<a id="g-data-object-storage"></a>
## オブジェクトストレージ

- **一言**: ファイルを名前（鍵）で 1 個ずつ出し入れする、大容量向けの保管場所です。
- **たとえ**: 宅配ロッカーです。棚の位置を知らなくても、預かり番号を伝えれば荷物が出てきます。
- **くわしく**: 階層フォルダではなく、入れ物（バケット）と鍵（キー）の組で 1 個ずつ管理します。やり取りは HTTP や HTTPS で行い、容量をあまり気にせず増やせるのが利点です。画像やログ、バックアップの置き場に向く一方、一部だけを少しずつ書き換える用途には向きません。
- **覚え方**: フォルダをたどる倉庫ではなく、預かり番号で取り出す倉庫、と覚えます。
- **まちがえやすい**: 画面でフォルダのように見えるのは、名前に `/` を含めているだけのことが多いです。実体は平らな並びです。
- **関連語**: [DAS・NAS・SAN](#g-data-das-nas-san) ／ [アーカイブ](#g-data-archive) ／ [バックアップ](#g-data-backup)
- **確かめかた**: 対応するツールが入っていれば `aws s3 ls` のような一覧コマンドで中身を見ます。使えるコマンドは環境によって異なります。

<a id="g-data-file-server-smb-nfs"></a>
## ファイルサーバーと共有プロトコル（SMB・NFS）（ファイルサーバートキョウユウプロトコル）

- **一言**: 複数の機械で同じフォルダを共有する仕組みと、その通信の約束事です。
- **たとえ**: 事務所の共有キャビネットです。SMB と NFS は、その扉を開ける鍵の種類にあたります。
- **くわしく**: ファイルサーバーは、自分の持つフォルダをネットワークへ公開する役です。SMB（エス・エム・ビー）は Windows で標準的に使われ、NFS（エヌ・エフ・エス）は Linux や UNIX でよく使われます。どちらも相手側の OS でも利用でき、Linux から SMB の共有を使うこともできます。使う側はマウント（自分のフォルダとして見えるようにする操作）してから読み書きします。
- **覚え方**: SMB は Windows 生まれ、NFS は UNIX 生まれ、と出身で覚えます。
- **まちがえやすい**: 権限は共有側の設定とファイル自体の設定の両方が効きます。片方だけ直しても開けないことがあります。
- **関連語**: [DAS・NAS・SAN](#g-data-das-nas-san) ／ [オブジェクトストレージ](#g-data-object-storage) ／ マウント
- **確かめかた**: つながっているかは `mount | grep -E 'nfs|cifs'` で見ます。NFS の公開一覧は `showmount -e サーバー名` で確認できます（ツールの有無は環境によって異なります）。

<a id="g-data-backup"></a>
## バックアップ

- **一言**: 失っても戻せるように、データの控えを別の場所へ取っておくことです。
- **たとえ**: 家の合鍵です。作るだけでなく、実家など別の場所に預けてこそ意味があります。
- **くわしく**: 目的は「消えたときに戻せること」の一点です。何を、いつ、どこへ、何世代残すかを決め、取れたかどうかを毎回確認します。控えが元データと同じディスクや同じ建物にあると、一度の事故でまとめて失います。
- **覚え方**: 取ることが目的ではなく、戻せることが目的、と覚えます。
- **まちがえやすい**: バックアップがあることと、戻せることは別です。中身が壊れていても、実際に戻してみるまで気づけません。
- **関連語**: [リストアとリカバリ](#g-data-restore-recovery) ／ [3-2-1 ルール](#g-data-3-2-1-rule) ／ [復元試験（リストアテスト）](#g-data-restore-test)
- **確かめかた**: 保存先を `ls -lh /backup` のように一覧し、日付と大きさを見ます。0 バイトや古い日付は失敗の合図です。保存先の場所は環境によって異なります。

<a id="g-data-logical-physical-backup"></a>
## 論理バックアップと物理バックアップ（ロンリバックアップトブツリバックアップ）

- **一言**: 中身を文にして書き出す方式と、ファイルごと丸ごと写す方式の違いです。
- **たとえ**: レシピを書き写して持ち帰るのが論理、料理を器ごと運ぶのが物理です。
- **くわしく**: 論理バックアップはデータを SQL 文などのテキストとして書き出す方式で、版や環境が違っても戻しやすいのが利点です。ただし件数が多いと、取得にも復元にも時間がかかります。物理バックアップはデータファイルをそのまま複製する方式で、大きなデータベースでは短時間で済むことが多いです。
- **覚え方**: 論理は書き写す、物理はそのまま運ぶ、と覚えます。
- **まちがえやすい**: 物理バックアップは、同じ製品・近い構成へ戻すのが前提です。別の版へそのまま持っていけるとは限りません。
- **関連語**: [バックアップ](#g-data-backup) ／ [スナップショット](#g-data-snapshot) ／ [リストアとリカバリ](#g-data-restore-recovery)
- **確かめかた**: 論理バックアップのファイルなら `head -20 dump.sql` で先頭を見て、中身が SQL 文になっているか確かめます。

<a id="g-data-hot-cold-backup"></a>
## ホットバックアップとコールドバックアップ

- **一言**: 動かしたまま取るのがホット、止めてから取るのがコールドです。
- **たとえ**: 営業中に棚卸しをするか、閉店後にするかの違いです。閉店後は正確ですが、その間は売れません。
- **くわしく**: ホットバックアップはサービスを止めずに取れますが、整合性をそろえる仕組みが要ります。コールドバックアップは止めてから取るので確実な代わり、その時間はサービスが使えません。24 時間動かすシステムでは、ホットが基本になります。
- **覚え方**: 電源が入って熱いままがホット、止めて冷えた状態がコールド、と覚えます。
- **まちがえやすい**: 稼働中のデータファイルを単に `cp` で写しても、整合性のあるバックアップにはなりません。製品ごとの専用手順を使います。
- **関連語**: [バックアップ](#g-data-backup) ／ [論理バックアップと物理バックアップ](#g-data-logical-physical-backup) ／ [スナップショット](#g-data-snapshot)
- **確かめかた**: 取得中もサービスが応答しているかは、別の端末から `curl -I http://localhost/` などで確かめます。

<a id="g-data-full-differential-incremental"></a>
## フルバックアップ・差分バックアップ・増分バックアップ（フルバックアップ・サブンバックアップ・ゾウブンバックアップ）

- **一言**: 全部取る、前回フルとの差を取る、前回から増えた分だけ取る、の 3 方式です。
- **たとえ**: 日記です。全ページ写すのがフル、月初からの追記をまとめて写すのが差分、昨日からの 1 日ぶんだけ写すのが増分です。
- **くわしく**: フルは戻すのが簡単ですが、時間も容量も使います。差分は毎回「フル以降の全部」なので、戻すときはフルと最新の差分の 2 つで済みます。増分は取得がいちばん軽い代わり、戻すときはフルとその後の増分を順番に全部当てます。
- **覚え方**: 差分は 2 つで戻り、増分は全部そろえて戻る、と覚えます。
- **まちがえやすい**: 増分は途中の 1 本が欠けると、その先の状態に戻せません。取得が軽いぶん、保管の抜けに弱い方式です。
- **関連語**: [バックアップ](#g-data-backup) ／ [世代管理](#g-data-generation-rotation) ／ [RTO](#g-data-rto)
- **確かめかた**: 保存先を `ls -lh` で一覧し、毎回大きいならフル、小さい日が続くなら差分か増分だと当たりが付きます。

<a id="g-data-snapshot"></a>
## スナップショット

- **一言**: ある瞬間の状態を、すぐ戻せる形で記録しておく仕組みです。
- **たとえ**: ゲームのセーブポイントです。作業前に押しておけば、失敗しても直前の場面からやり直せます。
- **くわしく**: ストレージや仮想化基盤の機能で、その時点の姿を短い時間で記録します。作業前の保険にしたり、止まった状態からバックアップを取る土台にしたりします。多くは元のデータと同じ装置に置かれ、変わった分だけを差分として持ちます。
- **覚え方**: 写真を撮るというより、セーブして戻れる仕組み、と覚えます。
- **まちがえやすい**: スナップショットはバックアップの代わりになりません。元のディスクが壊れれば、記録ごと一緒に失われます。
- **関連語**: [バックアップ](#g-data-backup) ／ [冗長化とバックアップの違い](#g-data-redundancy-vs-backup) ／ [DAS・NAS・SAN](#g-data-das-nas-san)
- **確かめかた**: LVM を使う環境なら `sudo lvs` で、スナップショット領域の有無と使用率を確認できます。

<a id="g-data-generation-rotation"></a>
## 世代管理（ローテーション）（セダイカンリ）

- **一言**: 古い控えを何本残し、いつ捨てるかを決めて回していく運用のことです。
- **たとえ**: タオルの使い回しです。7 枚を順に使い、8 枚目のときは一番古いものを洗って戻します。
- **くわしく**: 日次・週次・月次といった間隔ごとに、残す本数を決めます。たとえば日次を 7 本残す形ですが、必要な本数は業務の要件によって異なります。世代が 1 つしかないと、壊れたデータで上書きしたときに戻せません。古いものを自動で消す仕組みと、必要な容量の見積もりをセットで用意します。
- **覚え方**: 上書きではなく、タオルのように順ぐりに回す、と覚えます。
- **まちがえやすい**: 毎日同じ場所へ上書きする運用は世代管理ではありません。異常に気づくのが数日後なら、その日の世代がないと戻せません。
- **関連語**: [バックアップ](#g-data-backup) ／ [RPO](#g-data-rpo) ／ [アーカイブ](#g-data-archive)
- **確かめかた**: `ls -lt /backup | head` で、日付の並びと残っている本数が想定どおりか確認します。

<a id="g-data-restore-recovery"></a>
## リストアとリカバリ

- **一言**: 控えを書き戻すのがリストア、使える状態まで立て直すのがリカバリです。
- **たとえ**: 引っ越しです。荷物を新居へ運び入れるのがリストア、家具を組み立てて住める状態にするのがリカバリです。
- **くわしく**: リストアはバックアップからデータを書き戻す作業そのものを指します。リカバリはそこから記録（ログ）を当てて障害の直前に近づけ、業務を再開できる状態にするところまで含みます。手順書には、戻す順番と終わったあとの確認方法まで書いておきます。
- **覚え方**: リストアは置き戻す、リカバリは立て直す、と覚えます。
- **まちがえやすい**: リストアが終わっただけでは、設定や権限が合わずアプリが動かないことがあります。復旧の完了は、業務が使えるかどうかで判断します。
- **関連語**: [バックアップ](#g-data-backup) ／ [RTO](#g-data-rto) ／ [復元試験（リストアテスト）](#g-data-restore-test)
- **確かめかた**: 戻したあとは `SELECT COUNT(*) FROM users;` などで件数を突き合わせます。所要時間は検証環境で実際に測って記録します。

<a id="g-data-transaction-log"></a>
## トランザクションログ

- **一言**: データを書き換える前に、変更内容を順番どおり書き残しておく記録です。
- **たとえ**: レジのジャーナル（記録用紙）です。売上が順に残るので、あとから 1 件ずつ追いかけて再現できます。
- **くわしく**: 多くの RDBMS は変更をまずログに書き、そのあとで本体に反映します。この順番のおかげで、電源が落ちても再起動時に続きから立て直せます。このログの呼び名は製品で違い、PostgreSQL では WAL、MySQL では InnoDB のリドゥログです。フルバックアップとその後のログ（MySQL ではバイナリログ）をそろえておけば、指定した時刻の状態まで戻せます。
- **覚え方**: 先に記録、あとで本体、と覚えます。
- **まちがえやすい**: ログを消すと、フルバックアップを取った時点までしか戻せなくなります。逆に、消さずに溜め続けてディスクが埋まる事故もよく起きます。
- **関連語**: [ACID](#g-data-acid) ／ [リストアとリカバリ](#g-data-restore-recovery) ／ [RPO](#g-data-rpo)
- **確かめかた**: MySQL なら `SHOW VARIABLES LIKE 'log_bin';`、PostgreSQL なら `SHOW wal_level;` で記録の設定を確認できます。

<a id="g-data-rpo"></a>
## RPO（アール・ピー・オー）

- **一言**: 障害のとき「どこまでのデータ消失を許すか」を決めた目標です。
- **たとえ**: 毎晩まとめて日記を書く人が、火事で失うのは最大 1 日ぶんだと割り切っているのと同じです。
- **くわしく**: Recovery Point Objective の略で、復旧できる時点の目標を指します。1 日 1 回しか取っていなければ、最悪で 1 日ぶんの更新が失われます。RPO を短くしたいなら、取得の間隔を詰めるか、ログを続けて別の場所へ退避します。
- **覚え方**: P は Point（時点）で、どの時点まで戻せるかの目標だと覚えます。
- **まちがえやすい**: RPO は復旧にかかる時間ではありません。時間のほうの目標は RTO です。
- **関連語**: [RTO](#g-data-rto) ／ [バックアップ](#g-data-backup) ／ [トランザクションログ](#g-data-transaction-log)
- **確かめかた**: 直近の取得時刻を `ls -l --time-style=full-iso /backup | tail` で見て、現在時刻との差を確かめます。

<a id="g-data-rto"></a>
## RTO（アール・ティー・オー）

- **一言**: 障害から「何時間で使える状態に戻すか」を決めた目標です。
- **たとえ**: 停電したお店が「2 時間以内に営業を再開する」と決めておくのと同じです。
- **くわしく**: Recovery Time Objective の略で、復旧までに許される時間です。データ量が多いほどリストアに時間がかかるため、この目標が方式選びに直結します。短くしたい場合は、待機系をあらかじめ用意する、復旧手順を自動化する、といった手を打ちます。
- **覚え方**: T は Time（時間）で、RPO は過去へどれだけ、RTO は未来へどれだけ、と覚えます。
- **まちがえやすい**: 目標を決めただけでは達成できません。実際に測って間に合うか確かめて、初めて数字に意味が出ます。
- **関連語**: [RPO](#g-data-rpo) ／ [リストアとリカバリ](#g-data-restore-recovery) ／ [復元試験（リストアテスト）](#g-data-restore-test)
- **確かめかた**: 検証環境で復旧を最初から最後まで行い、開始時と終了時に `date` を記録して所要時間を測ります。

<a id="g-data-archive"></a>
## アーカイブ

- **一言**: 使わなくなったデータを、長期保管用の場所へ移して残しておくことです。
- **たとえ**: 使わない資料を段ボールに詰めて倉庫へ送るのと同じです。事務所の棚は空きますが、資料自体は残ります。
- **くわしく**: 目的は、保存年限を守ることと、日々使う領域を軽くすることです。バックアップが「今あるデータの控え」なのに対し、アーカイブは「原本の置き場を移したもの」です。取り出しに時間がかかる代わりに、保管の費用を抑えられる置き場を選ぶことが多いです。
- **覚え方**: バックアップは控え、アーカイブは引っ越し、と覚えます。
- **まちがえやすい**: アーカイブしただけでは控えになりません。移した先のデータにも、別途バックアップが必要です。
- **関連語**: [バックアップ](#g-data-backup) ／ [オブジェクトストレージ](#g-data-object-storage) ／ [世代管理](#g-data-generation-rotation)
- **確かめかた**: 圧縮した保管ファイルの中身は `tar -tzf archive.tar.gz | head` で、取り出さずに一覧できます。

<a id="g-data-3-2-1-rule"></a>
## 3-2-1 ルール（スリー・ツー・ワン・ルール）

- **一言**: 原本を含めて 3 つ、2 種類の媒体、うち 1 つは別の場所に置く原則です。
- **たとえ**: 大事な写真を、パソコン本体と外付け HDD と離れた場所のクラウドに分けて置くのと同じです。
- **くわしく**: 数え方は、原本 1 つとその控え 2 つで合わせて 3 つです。同じ装置に置いた控えは、その装置が壊れれば一緒に失われます。種類の違う媒体に分けておけば、同じ原因でまとめて壊れる事態を避けられます。1 つを離れた場所に置くのは、火災や水害、建物ごとの停止に備えるためです。
- **覚え方**: 「3 コピー・2 メディア・1 オフサイト」と数字で唱えて覚えます。
- **まちがえやすい**: 同じサーバーの別フォルダに置いたものは、別の 1 つとは数えません。同じ壊れ方をするものは、まとめて 1 つと数えます。
- **関連語**: [バックアップ](#g-data-backup) ／ [冗長化とバックアップの違い](#g-data-redundancy-vs-backup) ／ [オブジェクトストレージ](#g-data-object-storage)
- **確かめかた**: 保管先を書き出したうえで、`df -h` や `mount` を見て、それぞれ別の装置・別の場所かを確かめます。

<a id="g-data-redundancy-vs-backup"></a>
## 冗長化とバックアップの違い（ジョウチョウカトバックアップノチガイ）

- **一言**: 冗長化は止めないための備え、バックアップは戻すための備えです。
- **たとえ**: コピー機を 2 台置くのが冗長化、書類の写しを別の建物の金庫へ預けるのがバックアップです。2 台あっても、書類そのものを破いてしまえば戻せません。
- **くわしく**: 冗長化は同じものを 2 つ以上用意し、片方が壊れても動き続ける構成です。ただし操作は両方へ同じように反映されるので、誤削除やウイルスの被害もそのまま伝わります。過去の状態に戻す役目は、バックアップだけが果たせます。
- **覚え方**: 冗長化は今を守り、バックアップは過去を守る、と覚えます。
- **まちがえやすい**: RAID（複数のディスクを束ねて壊れにくくする仕組み）やレプリケーションがあるからバックアップは不要、は典型的な事故のもとです。守れる障害の種類が違います。
- **関連語**: [レプリケーション](#g-data-replication) ／ [スナップショット](#g-data-snapshot) ／ [バックアップ](#g-data-backup)
- **確かめかた**: ソフトウェア RAID なら `cat /proc/mdstat` で構成と状態を見ます。確認方法は環境によって異なります。

<a id="g-data-logical-physical-failure"></a>
## 論理障害と物理障害（ロンリショウガイトブツリショウガイ）

- **一言**: 中身が壊れるのが論理障害、機器そのものが壊れるのが物理障害です。
- **たとえ**: ノートに間違った内容を書いてしまうのが論理障害、ノートを破ってしまうのが物理障害です。
- **くわしく**: 論理障害は誤削除、誤更新、ファイルの破損、ウイルスなどで、装置自体は正常に動きます。物理障害はディスクや電源の故障で、そもそも読めなくなります。冗長化が効くのは主に物理障害で、論理障害には過去のバックアップの世代が要ります。
- **覚え方**: 読めるのに中身が違えば論理、そもそも読めなければ物理、と覚えます。
- **まちがえやすい**: 物理障害を疑うときに何度も再試行すると、状態を悪くすることがあります。まず記録を残し、切り分けを優先します。
- **関連語**: [冗長化とバックアップの違い](#g-data-redundancy-vs-backup) ／ [世代管理](#g-data-generation-rotation) ／ [バックアップ](#g-data-backup)
- **確かめかた**: 装置側の異常は `dmesg -T | grep -i -E 'error|i/o'` で探します。ディスクの健康状態は `sudo smartctl -H /dev/sda` などで見ます（装置名や導入状況は環境によって異なります）。

<a id="g-data-restore-test"></a>
## 復元試験（リストアテスト）（フクゲンシケン）

- **一言**: 取ったバックアップから本当に戻せるかを、実際に試して確かめることです。
- **たとえ**: 消火器の点検です。置いてあるだけでは意味がなく、使えると確かめて初めて備えになります。
- **くわしく**: 検証環境へ実際にリストアし、件数や画面の表示まで確認します。あわせて所要時間を測れば、RTO に間に合うかどうかも分かります。手順書は試験のたびに直し、担当が代わっても同じ手順で戻せる状態にしておきます。
- **覚え方**: 「取れた」ではなく「戻せた」で完了だと覚えます。
- **まちがえやすい**: 成功のログが出ていても、中身が空だったり必要なファイルが抜けていたりします。試すまでは分かりません。
- **関連語**: [リストアとリカバリ](#g-data-restore-recovery) ／ [RTO](#g-data-rto) ／ [バックアップ](#g-data-backup)
- **確かめかた**: 本番ではなく検証環境で行います。戻したあとに `SELECT COUNT(*) FROM users;` や `ls -lR` で、件数とファイルの有無を突き合わせます。
