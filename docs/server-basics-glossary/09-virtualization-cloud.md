# 9. 仮想化・コンテナ・クラウド

[用語集の入口](README.md) / [さくいん](index.md) / [前: データベース・ストレージ・バックアップ](08-data-storage.md) / [次: 可用性・性能・設計の考え方](10-availability.md)

サーバーは物理の箱だけではありません。この章では、1 台を分ける仮想化、アプリだけを運ぶコンテナ、借りて使うクラウドを順に整理します。

> **この章で最初に押さえる 3 語**: 仮想化 ／ コンテナ ／ クラウド

<a id="g-virt-virtualization"></a>
## 仮想化（カソウカ）

- **一言**: 1 台の物理サーバーを、ソフトで複数台分に分けて使う技術です。
- **たとえ**: 一軒の建物を壁で仕切り、鍵つきの部屋として何世帯にも貸すイメージです。住人は同じ建物にいますが、隣の部屋には入れません。
- **くわしく**: 物理サーバーは性能が余りがちで、1 台に 1 つの用途だけだと無駄が出ます。仮想化を使うと、CPU（計算を担当する部品）やメモリを分け合い、用途ごとに独立したサーバーを作れます。1 つの区画の OS が止まっても、ほかの区画は動き続けます。
- **覚え方**: 「1 台を仕切って何台にも」と、部屋割りの図で覚えます。
- **まちがえやすい**: 仮想化しても物理サーバーは 1 台のままです。土台のハードが壊れれば、上の仮想サーバーはまとめて止まります。
- **関連語**: [ハイパーバイザー](#g-virt-hypervisor)、[VM（仮想マシン）](#g-virt-vm)、[コンテナ](#g-virt-container)
- **確かめかた**: `systemd-detect-virt` を実行し、`kvm` などと出れば仮想環境、`none` なら物理機です。systemd を使わない環境では、この方法は使えません。

<a id="g-virt-hypervisor"></a>
## ハイパーバイザー（Type 1・Type 2）

- **一言**: 物理サーバーの資源を分け、仮想マシンを動かす土台のソフトです。
- **たとえ**: マンションの管理人です。部屋の広さを決め、電気や水道をどの部屋にどれだけ回すかを差配します。
- **くわしく**: Type 1 はハードの上で直接動く方式で、専用機として性能を出しやすい作りです。Type 2 は Windows や macOS などの普段使いの OS の上に、アプリとして入れる方式です。本番のサーバーは Type 1、手元の検証は Type 2 が多い、と考えると使い分けが見えます。
- **覚え方**: 「Type 1 はハードに直付け、Type 2 は OS の上に後付け」と位置で覚えます。
- **まちがえやすい**: Type 2 は下に普段使いの OS がいる分、その OS が止まると仮想マシンも道連れです。KVM のように OS の一部として動く方式もあり、どちらに分類するかは製品によって分かれます。
- **関連語**: [仮想化](#g-virt-virtualization)、[ホスト OS とゲスト OS](#g-virt-host-guest-os)、[VM（仮想マシン）](#g-virt-vm)
- **確かめかた**: Linux なら `lsmod | grep kvm` で仮想化の部品が読み込まれているかを確認できます。`virsh version` でも版が分かります（導入状況は環境によって異なります）。

<a id="g-virt-host-guest-os"></a>
## ホスト OS とゲスト OS（ホスト オー・エス ト ゲスト オー・エス）

- **一言**: 土台側で動く OS がホスト、その上の仮想マシンの OS がゲストです。
- **たとえ**: 母屋に住む家主がホスト、間借りしている下宿人がゲストです。台所（ハード）は母屋のものを借りて使います。
- **くわしく**: Type 2 では、物理マシンに入れた普段使いの OS がホストにあたります。ゲスト OS は仮想マシンの中に入れる OS で、土台から見ると 1 つのプログラムにすぎません。Type 1 にはホスト OS がなく、ハイパーバイザー自体が土台になります。トラブルのときは、土台側の問題かゲスト側の問題かを最初に切り分けます。
- **覚え方**: 「招く側がホスト、招かれる側がゲスト」とパーティーで覚えます。
- **まちがえやすい**: ゲスト OS の再起動はホストに影響しませんが、ホスト OS の再起動は全ゲストを巻き込みます。作業前に、自分が今どちら側にログインしているか必ず確認します。
- **関連語**: [ハイパーバイザー](#g-virt-hypervisor)、[VM（仮想マシン）](#g-virt-vm)、[コンテナ](#g-virt-container)
- **確かめかた**: `hostnamectl` を実行し、`Virtualization` の行が出ればゲスト側です。物理側では、この行そのものが表示されません。

<a id="g-virt-vm"></a>
## VM（仮想マシン）（ブイ・エム）

- **一言**: OS ごと丸ごと 1 台分を再現した、ソフトでできたサーバーです。
- **たとえ**: 台所も風呂も自前でそろえた 1 世帯分の部屋です。設備が一式そろう分、場所（ディスク）はそれなりに取ります。
- **くわしく**: VM は仮想の CPU・メモリ・ディスク・ネットワーク機器を持ち、その上に OS を入れて使います。実体はディスクイメージと設定ファイルなので、コピーや移動が簡単です。起動には OS の起動が丸ごと必要で、数十秒かかることもあります（時間は環境によって異なります）。
- **覚え方**: 「VM は OS 入りのフルセット、コンテナはアプリだけ」と対で覚えます。
- **まちがえやすい**: VM を消すと、ひも付いたディスクも一緒に消える設定が既定のことがあります。逆にディスクだけ残り、使っていないのに容量や料金が減らない場合もあります。
- **関連語**: [ホスト OS とゲスト OS](#g-virt-host-guest-os)、[VM のスナップショット](#g-virt-snapshot)、[インスタンス](#g-virt-instance)
- **確かめかた**: `virsh list --all` で定義済みの仮想マシン一覧を見られます。中に入ってからは `systemd-detect-virt` で自分が VM かを確認します。

<a id="g-virt-snapshot"></a>
## VM のスナップショット（ブイ・エム ノ スナップショット）

- **一言**: ある瞬間の VM の状態を丸ごと記録し、後で戻せるようにする機能です。
- **たとえ**: ゲームのセーブポイントです。危ない場面の前にセーブしておき、失敗したらその地点からやり直します。
- **くわしく**: 設定変更や更新の直前に取っておくと、失敗しても短時間で元の状態に戻せます。ディスクだけでなく、メモリの中身まで残せる方式もあります。ただし取ったまま放置すると差分が膨らみ、ディスクを圧迫して性能も落ちます。
- **覚え方**: 「作業前にセーブ、終わったら消す」を 1 セットにして覚えます。
- **まちがえやすい**: スナップショットはバックアップの代わりになりません。元の VM やその置き場が壊れると、スナップショットごと失われるためです。
- **関連語**: [VM（仮想マシン）](#g-virt-vm)、[テンプレートとクローン](#g-virt-template-clone)
- **確かめかた**: `virsh snapshot-list 仮想マシン名` で取得済みの一覧と日時を確認できます。管理画面のスナップショット一覧でも同じことが見られます。

<a id="g-virt-template-clone"></a>
## テンプレートとクローン

- **一言**: 複製の元にする型がテンプレート、そこから作った実物がクローンです。
- **たとえ**: クッキーの型がテンプレート、型で抜いた 1 枚 1 枚がクローンです。型そのものは焼かずに取っておきます。
- **くわしく**: OS の初期設定や監視エージェント（常駐して見張るプログラム）まで入れた状態を、型として保存します。新しいサーバーが要るときは型から複製すれば、毎回同じ手順を踏まずに済みます。複製直後は、ホスト名や IP アドレスなど固有の情報の付け替えが必要です。
- **覚え方**: 「型（テンプレート）は使わず取っておく、使うのは抜いた方（クローン）」。
- **まちがえやすい**: クローンをそのまま起動すると、同じホスト名や SSH のホスト鍵まで複製されて重複します。名前と鍵の付け替えを済ませてからネットワークにつなぎます。
- **関連語**: [VM（仮想マシン）](#g-virt-vm)、[VM のスナップショット](#g-virt-snapshot)、[コンテナイメージ](#g-virt-container-image)
- **確かめかた**: 管理画面のテンプレート一覧で元の型を確認し、複製後は `hostnamectl` と `ip a` で名前と IP アドレスの重複を確かめます。

<a id="g-virt-live-migration"></a>
## ライブマイグレーション

- **一言**: 電源を切らずに、VM を別の物理サーバーへ移す仕組みです。
- **たとえ**: 営業中のレストランを、客が食事を続けたまま隣の建物へ移すようなものです。客は席が移ったことに気づきません。
- **くわしく**: メモリの中身を移動先へ写しながら、最後に残った差分だけを一瞬で切り替えます。ハードの保守や点検のとき、サービスを止めずに退避させる目的で使います。多くの方式では、移動元と移動先でネットワークと保存領域を共有しておく必要があります。
- **覚え方**: 「電源を切らない引っ越しがライブ、切ってからの移動はコールド」と対で覚えます。
- **まちがえやすい**: 無停止といっても、切り替えの瞬間にごく短い中断が入ります。わずかな応答遅れも許されない処理では影響が出ることがあります。
- **関連語**: [VM（仮想マシン）](#g-virt-vm)、[ハイパーバイザー](#g-virt-hypervisor)、[オーバーコミット](#g-virt-overcommit)
- **確かめかた**: 移動後に VM の中で `uptime` を見て、連続稼働時間が途切れていなければ止めずに移せています。

<a id="g-virt-overcommit"></a>
## オーバーコミット

- **一言**: 物理の量より多くの CPU やメモリを、仮想マシンに割り当てることです。
- **たとえ**: 飛行機の座席の超過予約です。全員が同時に来なければ回りますが、満席の日は誰かがあぶれます。
- **くわしく**: 仮想マシンは割り当てを常に使い切るわけではないので、合計が物理量を超えても普段は動きます。1 台に載せられる数が増え、台あたりの費用を下げられます。ただし全 VM が同時に本気を出すと取り合いになり、CPU なら待たされ、メモリが尽きればプログラムが強制終了されることもあります。
- **覚え方**: 「予約は多め、席は実数」と超過予約の光景で覚えます。
- **まちがえやすい**: VM の中で見える空きメモリは、その VM に見せている値です。ホストの実態とは別なので、遅さの原因を VM の中だけで探しても見つかりません。
- **関連語**: [仮想化](#g-virt-virtualization)、[ハイパーバイザー](#g-virt-hypervisor)、[VM（仮想マシン）](#g-virt-vm)
- **確かめかた**: ホスト側で `free -h` と `nproc` を見て物理量を確認し、管理画面の割り当て合計と見比べます。

<a id="g-virt-container"></a>
## コンテナ

- **一言**: アプリと必要な部品だけを箱に詰め、OS を共有して動かす仕組みです。
- **たとえ**: 具材と道具を詰めた弁当箱です。調理場（OS の中核部分）は共用で、箱ごと持ち運べます。
- **くわしく**: コンテナはホストのカーネル（OS の中核）を借りて動くので、OS を丸ごと起動しません。そのぶん起動が速く、容量も小さく済みます（実際の時間は環境によって異なります）。プロセス（動作中のプログラム）やファイルの置き場は Linux の仕切り機能で分けられ、互いに干渉しません。
- **覚え方**: 「VM は家ごと、コンテナは弁当箱ごと」で軽さの差を覚えます。
- **まちがえやすい**: コンテナは仮想マシンではありません。カーネルを共有するため、Linux のホストで Windows 用のコンテナはそのまま動きません。
- **関連語**: [VM（仮想マシン）](#g-virt-vm)、[コンテナイメージ](#g-virt-container-image)、[Docker](#g-virt-docker)
- **確かめかた**: `docker ps` で動作中のコンテナ一覧を見ます。`docker inspect コンテナ名` で、そのコンテナの設定やつながりを確認できます。

<a id="g-virt-container-image"></a>
## コンテナイメージ

- **一言**: コンテナの中身を固めた、読み取り専用の完成パックです。
- **たとえ**: 冷凍食品のパックです。工場で作った状態のまま固まっていて、温めれば（起動すれば）どこでも同じ味になります。
- **くわしく**: イメージにはアプリ、ライブラリ（部品の集まり）、OS の一部が層状に重なって入っています。カーネル（OS の中核）は含まず、動くときはホストのものを借ります。同じイメージから起動すれば、検証でも本番でも同じ中身が動きます。イメージ自体は書き換えず、変えたいときは作り直します。
- **覚え方**: 「イメージは冷凍パック、コンテナは温めた 1 食」で静と動を分けます。
- **まちがえやすい**: コンテナの中で書き換えたファイルは、そのコンテナを消すと消えます。元のイメージには反映されません。
- **関連語**: [コンテナ](#g-virt-container)、[Dockerfile](#g-virt-dockerfile)、[レジストリとタグ](#g-virt-registry-tag)
- **確かめかた**: `docker images` で手元のイメージ一覧、`docker history イメージ名` で層の重なりを確認できます。

<a id="g-virt-docker"></a>
## Docker（ドッカー）

- **一言**: コンテナを作る・動かす・配る作業をまとめて扱う代表的な道具です。
- **たとえ**: 弁当箱を作る調理器具と、それを運ぶ配送業者がひとそろいになった仕組みです。
- **くわしく**: 手元で `docker` コマンドを打つと、常駐している本体（デーモン、待機し続けるプログラム）が実際の作成や起動を行います。イメージの取得、コンテナの起動、ログの確認まで同じ道具でこなせます。コンテナの言葉を世に広めた立役者で、用語の多くは Docker 由来です。
- **覚え方**: 「港でコンテナを積み下ろしする作業員がドッカー」と語源で覚えます。
- **まちがえやすい**: Docker はコンテナそのものではありません。コンテナは仕組みの名前で、Docker はそれを扱う道具の 1 つです。
- **関連語**: [コンテナ](#g-virt-container)、[Dockerfile](#g-virt-dockerfile)、[Docker Compose](#g-virt-docker-compose)
- **確かめかた**: `docker version` で導入済みかを確認し、`docker info` で保存先や動作状況を確認します。

<a id="g-virt-dockerfile"></a>
## Dockerfile（ドッカーファイル）

- **一言**: コンテナイメージの作り方を、上から順に書いた手順書ファイルです。
- **たとえ**: 弁当のレシピカードです。「土台の米はこれ」「次にこのおかず」と順に書けば、誰が作っても同じ弁当になります。
- **くわしく**: `FROM` で土台のイメージを決め、`RUN` で導入作業、`COPY` でファイルの取り込み、`CMD` で起動時の命令を書きます。`RUN` や `COPY` などの命令ごとに層が積まれ、変更のない層は次回そのまま使い回されます。手順が文字で残るので、中に何が入っているかを後から追えます。
- **覚え方**: 「FROM で土台、RUN で仕込み、CMD で提供」と料理の流れで覚えます。
- **まちがえやすい**: 変えた行より下の層は毎回作り直しになります。頻繁に変わるファイルの取り込みを上の方に書くと、毎回時間がかかります。
- **関連語**: [コンテナイメージ](#g-virt-container-image)、[Docker](#g-virt-docker)、[IaC（Infrastructure as Code）](#g-virt-iac)
- **確かめかた**: `cat Dockerfile` で手順を読み、`docker image inspect イメージ名` で出来上がりの設定を確認します。

<a id="g-virt-registry-tag"></a>
## レジストリとタグ

- **一言**: イメージを保管する倉庫がレジストリ、版を示す名札がタグです。
- **たとえ**: レジストリは商品を並べるスーパーの棚、タグは「辛口」「大盛り」といった中身違いを示すラベルです。
- **くわしく**: 作ったイメージはレジストリに置き、各サーバーはそこから取ってきて動かします。名前は「レジストリ名/イメージ名:タグ」の形で、タグには版番号などを付けます。誰でも取得できる公開の置き場と、社内限定の置き場を使い分けるのが一般的です。
- **覚え方**: 「置き場がレジストリ、荷札がタグ」と倉庫の絵で覚えます。
- **まちがえやすい**: `latest` は「最新」という意味の固定の名札にすぎず、中身は後から差し替わることがあります。本番では版を明示したタグや、ダイジェスト（中身から計算した固有の値）で指定します。
- **関連語**: [コンテナイメージ](#g-virt-container-image)、[Docker](#g-virt-docker)、[Kubernetes](#g-virt-kubernetes)
- **確かめかた**: `docker images` の `REPOSITORY` と `TAG` の列で、どの倉庫のどの版かを確認できます。`docker images --digests` を使うとダイジェストも並びます。

<a id="g-virt-docker-compose"></a>
## Docker Compose（ドッカー コンポーズ）

- **一言**: 複数のコンテナの構成を 1 つのファイルにまとめて動かす道具です。
- **たとえ**: 定食のセット注文です。ごはん・味噌汁・おかずを、1 回の注文でまとめて出してもらう感覚です。
- **くわしく**: 使うイメージ、公開するポート（通信の出入口の番号）、つなぐ相手を `compose.yaml` に書きます。ファイル名は、従来からの `docker-compose.yml` でも動きます。Web とデータベースのように複数のコンテナが要る構成を、1 つのコマンドでまとめて起動できます。手元の検証や小規模な構成でよく使われます。
- **覚え方**: 「compose は『組み合わせる』」と、定食のセット注文で覚えます。
- **まちがえやすい**: これは 1 台のサーバーの中でまとめる道具で、複数台にまたがる管理は守備範囲の外です。台数が増えたら Kubernetes などの出番です。
- **関連語**: [Docker](#g-virt-docker)、[Kubernetes](#g-virt-kubernetes)、[オーケストレーション](#g-virt-orchestration)
- **確かめかた**: `docker compose config` で設定の解釈結果、`docker compose ps` で起動中のサービス一覧を確認できます。

<a id="g-virt-volume-bind-mount"></a>
## ボリュームとバインドマウント

- **一言**: 消えては困るデータをコンテナの外へ置く、2 通りの置き方です。
- **たとえ**: ボリュームは店が用意した貸し金庫、バインドマウントは自宅の棚をそのまま店に持ち込む形です。
- **くわしく**: コンテナは消えると中身も消えるので、データベースのファイルなどは外に出します。ボリュームは Docker が管理する領域で、置き場所を細かく気にせず使えます。バインドマウントはホストの指定した場所を直接見せる方式で、開発中のソース共有に向きます。
- **覚え方**: 「おまかせがボリューム、場所指定がバインド」で区別します。
- **まちがえやすい**: バインドマウントはホストのファイルを直接触ります。コンテナ側で書き換えれば、ホスト側の実物も変わる点に注意します。
- **関連語**: [コンテナ](#g-virt-container)、[Docker](#g-virt-docker)、[Docker Compose](#g-virt-docker-compose)
- **確かめかた**: `docker volume ls` でボリュームの一覧を見ます。`docker inspect コンテナ名` の `Mounts` で、何がどこにつながっているかを確認します。

<a id="g-virt-kubernetes"></a>
## Kubernetes（クバネティス）

- **一言**: 多数のコンテナを複数台のサーバーで動かし続ける管理システムです。
- **たとえ**: 港のコンテナ船をさばく管制室です。どの船にどの箱を積むかを決め、落ちた箱があれば積み直します。
- **くわしく**: 「望ましい状態」を書いて渡すと、実際の状態がそれに合うよう自動で調整し続けます。コンテナが落ちれば作り直し、サーバーが 1 台故障すれば別の台で立て直します。省略して K8s（ケーエイツ）とも書かれます。
- **覚え方**: 「K と s の間に 8 文字」で K8s という書き方の由来を覚えます。
- **まちがえやすい**: コンテナを作る道具ではありません。作るのは Docker などで、Kubernetes は動かし続ける側です。小規模な構成には重すぎることもあります。
- **関連語**: [コンテナ](#g-virt-container)、[Pod](#g-virt-pod)、[オーケストレーション](#g-virt-orchestration)
- **確かめかた**: `kubectl get nodes` で参加しているサーバー、`kubectl cluster-info` で接続先を確認できます。

<a id="g-virt-pod"></a>
## Pod（ポッド）

- **一言**: Kubernetes が扱う最小の単位で、1 つ以上のコンテナの組です。
- **たとえ**: 一緒に運ぶおかずを乗せた 1 枚のトレーです。トレーごと配られ、トレーごと下げられます。
- **くわしく**: Pod の中のコンテナは同じ IP アドレスを共有し、必ず同じサーバーに置かれます。指定すれば、同じ保存領域を一緒に使うこともできます。本体のコンテナと、ログ集めなどの補助コンテナを組にする使い方が典型です。Kubernetes はコンテナ単体ではなく、Pod の単位で増やしたり減らしたりします。
- **覚え方**: 「さや（pod）の中に豆（コンテナ）が入っている」と語源で覚えます。
- **まちがえやすい**: Pod は使い捨てで、作り直すたびに名前も IP アドレスも変わります。IP アドレスを控えて接続先に書くやり方は通用しません。
- **関連語**: [Kubernetes](#g-virt-kubernetes)、[コンテナ](#g-virt-container)、[オートスケール](#g-virt-autoscale)
- **確かめかた**: `kubectl get pods -A` で全体の一覧、`kubectl describe pod 名前` で中身と出来事を確認できます。

<a id="g-virt-orchestration"></a>
## オーケストレーション

- **一言**: 多数のコンテナやサーバーの配置と起動を、自動で束ねる考え方です。
- **たとえ**: オーケストラの指揮者です。演奏者一人ひとりに指示を出し、全体として 1 曲になるようそろえます。
- **くわしく**: 配置先の決定、起動と停止、故障時の入れ替え、台数の増減を人手ではなく仕組みに任せます。台数が増えるほど手作業では追いつかなくなるため、必要になります。Kubernetes はこれを担う代表格です。
- **覚え方**: 「指揮者がいるから 100 人でも 1 曲になる」と規模と自動化を結びつけます。
- **まちがえやすい**: 自動化は「勝手に良くしてくれる」ことではありません。望ましい状態を人が正しく書かなければ、間違った状態をそのまま保ち続けます。
- **関連語**: [Kubernetes](#g-virt-kubernetes)、[Docker Compose](#g-virt-docker-compose)、[オートスケール](#g-virt-autoscale)
- **確かめかた**: `kubectl get deployments` の `READY` 列で「動いている数／希望する数」を見比べると、調整の様子が分かります。

<a id="g-virt-on-premises"></a>
## オンプレミス

- **一言**: 自社で機器を持ち、自分たちの管理下で運用する形態です。
- **たとえ**: 電気を電力会社から買わず、自宅に発電機を置いて自分で回すやり方です。
- **くわしく**: 機器の購入、設置、配線、故障対応まで自分たちで行います。性能や設置場所を細かく決められ、外部にデータを預けたくない要件にも応えられます。反面、増設には調達の時間がかかり、費用も先に出ます。
- **覚え方**: on premises は「敷地の上に」という意味だと覚えます。
- **まちがえやすい**: 「自社ビルにあるか」ではなく「機器を自分で保有・管理するか」が線引きです。借りたデータセンターに自社の機器を置く形も、オンプレミスに含まれます。
- **関連語**: [クラウド](#g-virt-cloud)、[パブリック・プライベート・ハイブリッドクラウド](#g-virt-public-private-hybrid)、[責任共有モデル](#g-virt-shared-responsibility)
- **確かめかた**: 資産管理台帳と保守契約書を見て、その機器が自社の資産として載っているかを確認します。

<a id="g-virt-cloud"></a>
## クラウド

- **一言**: 事業者の資源をネット越しに借り、必要な分だけ使う形態です。
- **たとえ**: 自家発電せずに電力会社から電気を買うのと同じです。使う量は蛇口をひねる感覚で増やせます。
- **くわしく**: サーバー、保存領域、ネットワークを、画面やコマンドから短時間で用意できます。機器の調達や故障交換は事業者側の仕事になり、こちらは使う側に集中できます。その代わり細かい機器構成は選べず、事業者の仕様に合わせる場面が増えます。
- **覚え方**: 「持つ（オンプレミス）か、借りる（クラウド）か」の二択で覚えます。
- **まちがえやすい**: クラウドでも、中身は誰かの物理サーバーです。「壊れない」わけではなく、壊れる前提でゾーンを分ける設計が要ります。
- **関連語**: [オンプレミス](#g-virt-on-premises)、[IaaS・PaaS・SaaS](#g-virt-iaas-paas-saas)、[従量課金](#g-virt-pay-per-use)
- **確かめかた**: 契約中のクラウドの管理画面で、稼働中のサーバー一覧と課金対象の資源を見ます。CLI の名前や書式は事業者ごとに異なります。

<a id="g-virt-iaas-paas-saas"></a>
## IaaS・PaaS・SaaS（イアース・パース・サース）

- **一言**: 借りる範囲の違いで、土台だけ・実行環境まで・完成品まで、の 3 段です。
- **たとえ**: 住まいでたとえます。更地を借りて自分で建てるのが IaaS、建物付きで内装だけ自分がやるのが PaaS、家具付きホテルに泊まるのが SaaS です。
- **くわしく**: IaaS はサーバーやネットワークを借り、OS より上は自分で面倒を見ます。PaaS は OS やミドルウェア（アプリを支える土台のソフト）まで用意され、アプリを置けば動きます。SaaS はできあがったサービスを使うだけで、管理画面の設定が自分の仕事になります。
- **覚え方**: 「I はインフラ、P はプラットフォーム、S はソフトウェア」と頭文字で覚えます。
- **まちがえやすい**: 上の段ほど楽になりますが、自由も減ります。OS に入って設定を変える作業は、PaaS や SaaS では基本的にできません。
- **関連語**: [クラウド](#g-virt-cloud)、[マネージドサービス](#g-virt-managed-service)、[責任共有モデル](#g-virt-shared-responsibility)
- **確かめかた**: そのサービスの OS に自分で入れるか（`ssh` で入れるか）を確認します。入れれば IaaS 寄り、入れなければ PaaS や SaaS 寄りです。

<a id="g-virt-serverless"></a>
## サーバーレス

- **一言**: サーバーの用意を意識せず、処理が動いた分だけ課金される使い方です。
- **たとえ**: 洗濯機を家に置かず、コインランドリーへ行くやり方です。使う時だけ回し、置き場所や修理は考えません。
- **くわしく**: 短いプログラムを預けておき、リクエストや時刻をきっかけに実行させます。呼ばれていない間は資源を使わず、料金もかからない方式が一般的です（条件は事業者によって異なります）。混雑時の台数調整も事業者側が行いますが、同時に動かせる数には上限があります。
- **覚え方**: 「サーバーが無いのではなく、意識しなくてよい」と言い換えて覚えます。
- **まちがえやすい**: サーバーが消えるわけではなく、事業者側にあるだけです。しばらく呼ばれないと、次の 1 回目の応答が遅くなることがあります。
- **関連語**: [IaaS・PaaS・SaaS](#g-virt-iaas-paas-saas)、[マネージドサービス](#g-virt-managed-service)、[従量課金](#g-virt-pay-per-use)
- **確かめかた**: 管理画面の関数一覧と実行ログで、呼ばれた回数と 1 回あたりの実行時間を確認します。

<a id="g-virt-public-private-hybrid"></a>
## パブリック・プライベート・ハイブリッドクラウド

- **一言**: 誰でも借りる形、自社専用の形、両方を組み合わせる形の 3 分類です。
- **たとえ**: 大勢が入居する賃貸マンションがパブリック、自分たちだけの一戸建てがプライベート、両方に部屋を持つのがハイブリッドです。
- **くわしく**: パブリックは事業者の共用基盤を使い、初期費用を抑えて始められます。プライベートは自社専用に用意した基盤で、規制の厳しいデータを置く場合に選ばれます。ハイブリッドは、機微なデータは手元に、急増する処理はパブリックに、といった使い分けです。
- **覚え方**: 「みんなの・自分だけの・いいとこ取り」の 3 つで並べて覚えます。
- **まちがえやすい**: パブリックでも、他社から自社のデータが見えるわけではありません。基盤は共用でも、利用者ごとの区画は分けられています。
- **関連語**: [クラウド](#g-virt-cloud)、[オンプレミス](#g-virt-on-premises)、[責任共有モデル](#g-virt-shared-responsibility)
- **確かめかた**: 構成図で接続経路を確認し、`tracepath 相手のホスト名` で社内網を通るか外へ出るかを見ます（導入状況は環境によって異なります）。

<a id="g-virt-region-az"></a>
## リージョンとアベイラビリティゾーン

- **一言**: 地域のまとまりがリージョン、その中で設備を分けた区画がゾーンです。
- **たとえ**: リージョンは「東京」という街、ゾーンはその街にある別々のビルです。ビルごとに電源も回線も分かれています。
- **くわしく**: 同じリージョン内のゾーン同士は距離が近く、通信の遅れを小さく保ったまま分散できます。1 つのゾーンが停電しても、別のゾーンに同じ構成があれば動き続けます。リージョンをまたぐと距離が延びて通信が遅くなり、地域をまたぐ転送に料金がかかることもあります（条件は事業者によって異なります）。
- **覚え方**: 「リージョンは街、ゾーンはビル」と入れ子で覚えます。
- **まちがえやすい**: 2 台に増やしても同じゾーンなら、そのゾーンの障害で共倒れです。冗長化はゾーンを分けて初めて効きます。
- **関連語**: [クラウド](#g-virt-cloud)、[インスタンス](#g-virt-instance)、[オートスケール](#g-virt-autoscale)
- **確かめかた**: 管理画面で各サーバーのリージョン名とゾーン名を一覧します。`ping -c 4 相手のホスト名` でも往復時間の差を見られます（応答を止めている環境では返りません）。

<a id="g-virt-instance"></a>
## インスタンス

- **一言**: クラウドで起動した 1 台分のサーバーを指す呼び名です。
- **たとえ**: レンタカー 1 台です。同じ車種（イメージ）から必要な台数だけ借りて、返せば料金は止まります。
- **くわしく**: CPU やメモリの組み合わせは「タイプ」として選び、後から変更できることもあります。イメージから起動するので、同じ構成の台を何台でも並べられます。壊れたら直すより作り直す、という前提で扱うのがクラウドでの基本姿勢です。
- **覚え方**: 「型（イメージ）から作った実体 1 つがインスタンス」と覚えます。
- **まちがえやすい**: 停止中でも、保存領域や確保した IP アドレスの料金は続くことがあります。不要になったら関連する資源もまとめて片づけます。
- **関連語**: [VM（仮想マシン）](#g-virt-vm)、[クラウド](#g-virt-cloud)、[従量課金](#g-virt-pay-per-use)
- **確かめかた**: 管理画面のインスタンス一覧で状態とタイプを確認し、中では `nproc` と `free -h` で実際の量を見ます。

<a id="g-virt-autoscale"></a>
## オートスケール

- **一言**: 負荷に応じて、サーバーやコンテナの台数を自動で増減する仕組みです。
- **たとえ**: 行列ができたらレジを開け、空いたら閉じるスーパーです。店員は待機所から呼ばれてきます。
- **くわしく**: CPU 使用率やリクエスト数などのしきい値を決め、超えたら増やし、下回ったら減らします。混雑に合わせて増えるので、待たせる損失と無駄な待機の両方を抑えられます。増やす側は速く、減らす側はゆっくりにするのが安全側の設定です。
- **覚え方**: 「混んだら開ける、空いたら閉じる」をレジの数で覚えます。
- **まちがえやすい**: 台数を増やせば何でも速くなるわけではありません。データベース 1 台が詰まっているなら、前段を増やしても行列が伸びるだけです。
- **関連語**: [インスタンス](#g-virt-instance)、[オーケストレーション](#g-virt-orchestration)、[従量課金](#g-virt-pay-per-use)
- **確かめかた**: 管理画面のスケーリング設定と増減の履歴を見ます。Kubernetes なら `kubectl get hpa` で現在の台数としきい値が分かります。

<a id="g-virt-pay-per-use"></a>
## 従量課金（ジュウリョウカキン）

- **一言**: 使った量と時間の分だけ料金がかかる、クラウドの課金方式です。
- **たとえ**: 水道や電気の料金です。蛇口を開けた分だけ請求が来るので、閉め忘れが翌月に響きます。
- **くわしく**: 起動していた時間、保存した容量、外向きの通信量などが課金の対象になります。少しずつ試すには向きますが、消し忘れがあると気づかないうちに積み上がります。上限額の警告を設定し、月ごとに棚卸しするのが基本です。
- **覚え方**: 「メーターが回っている」と考え、起動と停止を 1 セットで扱います。
- **まちがえやすい**: 試しに作った資源ほど消し忘れます。検証用に作るときは、作った人と消す予定日を名札（タグ）として付けておきます。
- **関連語**: [クラウド](#g-virt-cloud)、[インスタンス](#g-virt-instance)、[オートスケール](#g-virt-autoscale)
- **確かめかた**: 管理画面の請求ダッシュボードで、資源ごとの内訳と前月との差を見ます。

<a id="g-virt-managed-service"></a>
## マネージドサービス

- **一言**: 事業者が運用まで面倒を見てくれる、お任せ型のサービスです。
- **たとえ**: 賄い付きの下宿です。食事の支度と後片づけは大家さんの仕事で、住人は自分の生活に集中できます。
- **くわしく**: データベースやメール配信などを、構築済みの状態で借ります。更新の適用、バックアップの取得、故障時の切り替えが仕組みとして用意されています。自前で組むより自由度は下がりますが、運用の手間と担当者頼みの状態を大きく減らせます。
- **覚え方**: 「自炊（自前）か、賄い付き（マネージド）か」で覚えます。
- **まちがえやすい**: 「任せた＝何もしなくてよい」ではありません。設定、アクセス権、バックアップの世代や戻し方の確認は利用者の仕事です。
- **関連語**: [IaaS・PaaS・SaaS](#g-virt-iaas-paas-saas)、[責任共有モデル](#g-virt-shared-responsibility)、[サーバーレス](#g-virt-serverless)
- **確かめかた**: 管理画面でバックアップの設定と保持期間、更新が適用される時間帯を確認します。

<a id="g-virt-shared-responsibility"></a>
## 責任共有モデル（セキニンキョウユウモデル）

- **一言**: 事業者と利用者で守る範囲を分ける、クラウドの役割分担の考え方です。
- **たとえ**: 賃貸住宅の分担です。建物の構造や共用部は大家さん、部屋の施錠と家財の管理は入居者の担当です。
- **くわしく**: 事業者は建物、電源、物理機器、基盤のソフトを守ります。利用者は自分が置いた設定、アクセス権、データ、公開範囲を守ります。境目は使うサービスの段で変わり、SaaS に近いほど利用者の担当は狭くなります。
- **覚え方**: 「クラウドそのものの安全は事業者、クラウドで作る中身の安全は自分」と分けます。
- **まちがえやすい**: 「クラウドだから安全」ではありません。保存領域を誰でも読める設定にしてしまう事故は、利用者側の担当範囲です。
- **関連語**: [クラウド](#g-virt-cloud)、[IaaS・PaaS・SaaS](#g-virt-iaas-paas-saas)、[マネージドサービス](#g-virt-managed-service)
- **確かめかた**: 使っている事業者の公式ドキュメントで責任分担の図を確認し、自分の担当範囲を書き出します。

<a id="g-virt-iac"></a>
## IaC（Infrastructure as Code）（アイ・エー・シー）

- **一言**: サーバーの構成をコードで書き、その通りに作る進め方です。
- **たとえ**: 家具の組み立て方を口伝えではなく説明書として残すやり方です。誰が読んでも同じ形に組み上がります。
- **くわしく**: 手作業の代わりに、構成をテキストで書いて実行します。そのファイルを Git（変更履歴を残す道具）で管理すれば、誰がいつ何を変えたかが残ります。同じコードから検証環境と本番環境を作れるので、環境差による事故が減ります。
- **覚え方**: 「人が読む手順書ではなく、機械が読む手順書にする」と言い換えます。
- **まちがえやすい**: コードを書いた後に手作業で直すと、コードと現物がずれます。次の実行で手直しが上書きされ、原因の分かりにくい障害になります。
- **関連語**: [Ansible](#g-virt-ansible)、[Terraform](#g-virt-terraform)、[冪等性](#g-virt-idempotency)
- **確かめかた**: 構成ファイルの置き場で `git log --oneline` を実行し、変更の履歴が残っているかを見ます。

<a id="g-virt-ansible"></a>
## Ansible（アンシブル）

- **一言**: 既存のサーバーへ接続し、設定作業を自動化する構成管理の道具です。
- **たとえ**: 手順書を持って現地に出向く作業スタッフです。訪問先の一覧と作業内容を渡せば、全台を同じ手順で回ってくれます。
- **くわしく**: YAML（読みやすい書式のテキスト）であるべき状態を書き、対象サーバーの一覧（インベントリ）と組み合わせて実行します。相手側に常駐ソフトを置く必要はなく、SSH（暗号化された遠隔接続）と Python が使えれば動きます。パッケージの導入、設定ファイルの配布、サービスの起動などが守備範囲です。
- **覚え方**: 「常駐ソフト要らずで訪問する、手ぶらの作業員」と身軽さで覚えます。
- **まちがえやすい**: 書いた順に上から処理されるので、順番に意味があります。「宣言すれば勝手に良い順で並ぶ」わけではありません。
- **関連語**: [IaC（Infrastructure as Code）](#g-virt-iac)、[Terraform](#g-virt-terraform)、[冪等性](#g-virt-idempotency)
- **確かめかた**: `ansible --version` で導入を確認します。`ansible-playbook --syntax-check ファイル名` で、書式だけを検査できます。

<a id="g-virt-terraform"></a>
## Terraform（テラフォーム）

- **一言**: クラウドの資源そのものをコードから作り、状態を管理する道具です。
- **たとえ**: 図面から建物を建てる建築業者です。図面と現物を突き合わせ、足りない棟を建て、余分な棟を片づけます。
- **くわしく**: 「最終的にどうあってほしいか」を書くと、現状との差を計算して必要な変更だけを行います。作った資源は状態ファイルに記録され、次の実行ではそれと比べます。サーバー、ネットワーク、権限など、クラウドの構成要素をまとめて扱えます。
- **覚え方**: 「Terraform は箱を用意する係、Ansible は中身を整える係」と分担で覚えます。
- **まちがえやすい**: 管理画面で手作業して構成を変えると、状態ファイルと食い違います。次の実行で差として扱われるため、変更はコード側に寄せます。
- **関連語**: [IaC（Infrastructure as Code）](#g-virt-iac)、[Ansible](#g-virt-ansible)、[クラウド](#g-virt-cloud)
- **確かめかた**: `terraform validate` で書式を確かめ、`terraform plan` で「これから何が変わるか」だけを表示します。

<a id="g-virt-idempotency"></a>
## 冪等性（ベキトウセイ）

- **一言**: 同じ操作を何度実行しても、結果が同じ状態に落ち着く性質です。
- **たとえ**: エレベーターの呼び出しボタンです。1 回押しても 5 回押しても、来るかごは 1 台だけです。
- **くわしく**: 自動化では、途中で失敗した処理をもう一度流す場面がよくあります。冪等なら、すでに済んだ部分は「変更なし」と判断され、二重に作られません。「追記する」ではなく「この内容にそろえる」と書くのが、実現のこつです。
- **覚え方**: 「連打してもエレベーターは 1 台」で、回数と結果が無関係なことを覚えます。
- **まちがえやすい**: 「2 回目は何も起きないこと」ではなく「同じ状態になること」です。実物がずれていれば直しに行くので、変更が発生する場合もあります。
- **関連語**: [IaC（Infrastructure as Code）](#g-virt-iac)、[Ansible](#g-virt-ansible)、[Terraform](#g-virt-terraform)
- **確かめかた**: `terraform plan` で「No changes」と出れば、コードと現物がそろっています。Ansible なら `ansible-playbook --check ファイル名` で、変更の予定が無いかを見ます。

<a id="g-virt-ci-cd"></a>
## CI/CD（シー・アイ・シー・ディー）

- **一言**: 変更したコードを自動で検査し、届けるところまでつなぐ仕組みです。
- **たとえ**: 工場のベルトコンベアです。部品を載せると検査台を通り、合格したものだけが出荷口へ流れます。人が一つずつ運ぶ手間がありません。
- **くわしく**: CI は継続的インテグレーションの略で、変更を持ち寄るたびに自動で組み立てと検査を行う進め方です。CD は継続的デリバリーの略で、検査を通ったものを配れる形にまとめ、決めた環境へ届けることです。Git（変更履歴を残す道具）へ保存した時などをきっかけに、決めた手順が自動で走ります。コンテナイメージを作ってレジストリへ置くまでを、この流れに任せるのが定番です。
- **覚え方**: 「CI は毎回ためす、CD は自動で届ける」と役割で分けて覚えます。
- **まちがえやすい**: CD は 2 通りの意味で使われ、配れる状態までを指す場合と、本番への反映まで自動で行う場合があります。どちらの意味かを確かめないと、人の承認を飛ばす話になりかねません。
- **関連語**: [IaC（Infrastructure as Code）](#g-virt-iac)、[コンテナイメージ](#g-virt-container-image)、[レジストリとタグ](#g-virt-registry-tag)
- **確かめかた**: リポジトリで `ls .github/workflows` や `cat .gitlab-ci.yml` を実行し、自動処理の定義があるかを見ます。実行の成否は、使っているサービスの画面の履歴一覧で確認します（名前や置き場はサービスによって異なります）。
