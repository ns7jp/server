# 13. 構築プロジェクトと現場の言葉

[用語集の入口](README.md) / [さくいん](index.md) / [前: 運用・監視・障害対応](12-operations.md) / [次: 数字と単位の読み方](numbers.md)

この章では、技術書にはあまり載らないのに、現場の会話や求人票では毎日出てくる言葉を集めました。手を動かす技術ではなく、仕事の進め方と人の役割を表す言葉なので、早く覚えるほど打ち合わせが楽になります。

> **この章で最初に押さえる 3 語**: 要件定義 ／ パラメータシート ／ カットオーバー

<a id="g-proj-requirements"></a>
## 要件定義（ヨウケンテイギ）

- **一言**: お客さまが本当に欲しいものを言葉にして、作る範囲を決める最初の工程です。
- **たとえ**: 家を建てる前の打ち合わせです。「部屋はいくつ」「駐車場は何台分」を先に決めないと、工事は始められません。
- **くわしく**: 何を作るか、どこまでやるか、いつまでに終えるかを文書にします。ここで決めた内容が、あとの設計や見積もりの土台になります。あいまいなまま進むと、完成してから「思っていたのと違う」となり、作り直しになります。遠慮せずに質問して、決めたことは必ず書き残します。
- **覚え方**: 「何が欲しいか」が要件定義で、「どう作るか」は次の設計、と分けて覚えます。
- **まちがえやすい**: 要件定義で決めるのは「何が欲しいか」で、使う製品や設定値は設計で決めます。ただし、速さや止められる時間といった条件（非機能要件）は、要件として先に決めます。
- **関連語**: [基本設計と詳細設計](#g-proj-basic-detail-design)、[工数と見積もり](#g-proj-man-hours)、[受入試験・UAT](#g-proj-uat)
- **確かめかた**: 案件のフォルダで「要件定義書」という名前の文書を開き、やることの一覧と「対象外」と書かれた範囲を読みます。

<a id="g-proj-basic-detail-design"></a>
## 基本設計と詳細設計（キホンセッケイ／ショウサイセッケイ）

- **一言**: 全体の方針を決めるのが基本設計、実際の設定値まで決めるのが詳細設計です。
- **たとえ**: 家づくりでいう間取り図が基本設計、コンセントの位置や壁紙の品番まで書き込んだ図面が詳細設計です。
- **くわしく**: 基本設計では、サーバーを何台置くか、どの機能をどこに載せるかを決めます。詳細設計では、ホスト名や IP アドレス（機器の住所にあたる番号）、時刻合わせの設定まで具体的に書きます。詳細設計が固まれば、書いてあるとおりに手を動かせば構築できる状態になります。現場では「基設」「詳設」と略され、どこまでを基本設計と呼ぶかは会社や案件によって異なります。
- **覚え方**: 基本は「絵」、詳細は「数字」と覚えると区別できます。
- **まちがえやすい**: 基本設計に細かい設定値まで書くと、値を変えるたびに 2 つの文書を直すことになります。設定値は詳細設計側に寄せるのが原則です。
- **関連語**: [要件定義](#g-proj-requirements)、[パラメータシート](#g-proj-parameter-sheet)、[構成図](#g-proj-diagram)
- **確かめかた**: 手元の設計書の目次を開き、方針を語る章と、設定値の表が並ぶ章のどちらに当たるかを見ます。

<a id="g-proj-parameter-sheet"></a>
## パラメータシート

- **一言**: 機器やソフトの設定値を一覧表にまとめた、構築作業の台本になる文書です。
- **たとえ**: マンションの入居者名簿のようなものです。部屋番号（IP アドレス）と名前（ホスト名）が 1 行ずつ並びます。
- **くわしく**: ホスト名、IP アドレス、時刻合わせの相手先、利用者アカウントなどを表にまとめます。構築する人はこの表を見ながら設定し、試験する人はこの表と実機を突き合わせます。表計算ソフトで作ることが多く、様式や粒の細かさは案件によって異なります。
- **覚え方**: パラメータは設定値のことなので、設定値の「答え合わせ表」と覚えます。
- **まちがえやすい**: 作業中に実機だけ直して、シートを直し忘れる取り違えがとても多いです。実機とシートが食い違うと、次の担当者は必ず迷います。
- **関連語**: [基本設計と詳細設計](#g-proj-basic-detail-design)、[構築・ビルド](#g-proj-build)、[試験項目書とエビデンス](#g-proj-test-evidence)
- **確かめかた**: `hostnamectl` と `ip -br addr` の出力を、シートのホスト名と IP アドレスの欄に照らし合わせます。

<a id="g-proj-diagram"></a>
## 構成図（コウセイズ）

- **一言**: サーバーやネットワークのつながりを、絵にして一目で分かるようにした図です。
- **たとえ**: 電車の路線図です。駅（機器）と線路（通信経路）が描いてあるので、初めての人でも乗り換えが分かります。
- **くわしく**: 機器の置き場所や配線を描いた物理構成図と、通信の流れや役割を描いた論理構成図があります。ネットワーク構成図やシステム構成図など、呼び名や描く範囲は現場によって異なります。障害のときは、まず構成図を開いて「どこが止まると何が止まるか」を探します。
- **覚え方**: 「言葉で 10 分、図なら 10 秒」と覚え、説明が長くなったら図を出します。
- **まちがえやすい**: 構成図が最新とは限りません。機器が増えても図が直されないことは多いので、実機の状態と必ず突き合わせます。
- **関連語**: [基本設計と詳細設計](#g-proj-basic-detail-design)、[ラッキングと結線](#g-proj-racking)、[ドキュメント整備](#g-proj-documentation)
- **確かめかた**: `ip -br addr` と `ip route` を実行し、図に描かれたつながり先や経路と合っているかを見ます。

<a id="g-proj-man-hours"></a>
## 工数と見積もり（コウスウ／ミツモリ）

- **一言**: 作業にかかる人と時間の量が工数、それをお金と期間に直したものが見積もりです。
- **たとえ**: ペンキ塗りと同じです。壁の面積と塗る人数で日数が決まり、その日数から料金が出ます。
- **くわしく**: 工数は「人日（にんにち）」「人月（にんげつ）」で数えます。1 人日は 1 人が 1 日働く量、1 人月は 1 人が 1 か月働く量です。見積もりは、この工数に単価を掛け、試験や手直しの時間も足して作ります。1 人月を何時間と数えるか、単価をいくらにするかは、会社や案件によって異なります。
- **覚え方**: 「人 × 時間＝工数」と掛け算で覚えれば、人を増やしても総量は減らないと分かります。
- **まちがえやすい**: 「10 人日だから 10 人でやれば 1 日」は成り立ちません。引き継ぎや待ち時間が増えて、かえって遅くなることもあります。
- **関連語**: [WBS とスケジュール](#g-proj-wbs)、[元請けと下請け・多重下請け](#g-proj-prime-sub)、[客先常駐と SES](#g-proj-ses)
- **確かめかた**: 自分が担当した作業の開始と終了を記録し、見積もり時の工数と実績を並べて比べます。

<a id="g-proj-wbs"></a>
## WBS とスケジュール（ダブリュー・ビー・エス／スケジュール）

- **一言**: 作業を細かく分けた一覧が WBS、それに日付と担当を入れたものがスケジュールです。
- **たとえ**: 旅行の持ち物リストと旅程表の関係です。まず何が要るかを全部書き出し、次にいつ何をするかを並べます。
- **くわしく**: WBS は Work Breakdown Structure の略で、大きな作業を小さな作業に割っていく表です。1 つの作業が数日で終わる大きさまで割ると、進み具合が見えるようになります。どこまで細かく割るかは、案件の大きさによって異なります。スケジュールでは、その作業に担当者と期日を付け、前後関係（これが終わらないと次が始まらない、という順番）をつなぎます。
- **覚え方**: WBS は「作業を分解（Breakdown）した構造（Structure）」なので、分解してから日付、の順です。
- **まちがえやすい**: WBS に「試験」「移行」とだけ書くのは分解不足です。粒が大きいと、遅れに気づくのが最後になります。
- **関連語**: [工数と見積もり](#g-proj-man-hours)、[課題管理表・QA 表](#g-proj-issue-list)、[カットオーバー](#g-proj-cutover)
- **確かめかた**: 手元の WBS を開き、自分の担当行に「担当者」「期日」「終わったかどうか」の 3 つが入っているかを確かめます。

<a id="g-proj-issue-list"></a>
## 課題管理表・QA 表（カダイカンリヒョウ／キュー・エー・ヒョウ）

- **一言**: 決まっていないことや困りごとを 1 行ずつ書き、担当と期限を付けて追う表です。
- **たとえ**: レストランの注文伝票です。伝票が残っている限り、その料理はまだ出ていないと誰にでも分かります。
- **くわしく**: 「この設定値は誰に聞けばよいか」「この動きは仕様どおりか」といった宙に浮いた話を書き出します。1 行に、内容・起票日・担当者・期限・状態（未着手／対応中／完了）を書きます。会議で決まったことも、この表に戻して記録します。口頭で流すと忘れられがちなので、若手ほど書く癖をつけると信頼されます。
- **覚え方**: 「宙に浮いた話は表に降ろす」と覚えると、書いた時点で誰かの担当になると分かります。
- **まちがえやすい**: 課題管理表は責任追及の表ではありません。書いた人が悪いのではなく、書かれずに消えた課題こそが事故になります。
- **関連語**: [WBS とスケジュール](#g-proj-wbs)、[要件定義](#g-proj-requirements)、[ドキュメント整備](#g-proj-documentation)
- **確かめかた**: 表を期限の列で並べ替え、状態が「未着手」のまま期限を過ぎている行がないかを見ます。

<a id="g-proj-kitting"></a>
## キッティング

- **一言**: 買ってきた機器に初期設定を入れ、すぐ使える状態に仕立てる作業です。
- **たとえ**: 新しいスマートフォンの初期設定を、100 台分まとめてやるようなものです。
- **くわしく**: OS の導入、ホスト名や IP アドレスの設定、必要なソフトの導入、資産番号のシール貼りまでを含みます。台数が多いときは、1 台を作り込んでその複製（イメージ）を配る方法をとります。手順を決めて流れ作業にすることが、品質と速さの決め手になります。
- **覚え方**: kit は「一式」なので、箱から出して一式そろえる作業がキッティングだと覚えます。
- **まちがえやすい**: キッティングは機器を設置することではありません。設置する前に、机の上で仕上げておく作業を指すのが一般的で、含む範囲は現場によって異なります。
- **関連語**: [ラッキングと結線](#g-proj-racking)、[構築・ビルド](#g-proj-build)、[資産管理台帳](#g-proj-asset-ledger)
- **確かめかた**: 仕上げた 1 台で `hostnamectl` と `ip -br addr` を実行し、台帳やシートの値と一致するかを確かめます。

<a id="g-proj-racking"></a>
## ラッキングと結線（ラッキング／ケッセン）

- **一言**: 機器をラックに取り付けるのがラッキング、ケーブルをつなぐのが結線です。
- **たとえ**: 引っ越し先で棚を組んで家電を並べるのがラッキング、その家電に電源と LAN ケーブルを挿すのが結線です。
- **くわしく**: ラックは、幅 19 インチの機器を取り付ける規格のものが広く使われ、高さの位置は U（ユニット）という単位で数えます。重い機器は下のほうに載せ、位置はラック搭載図のとおりに合わせます。結線では、どの機器のどの口からどこへつなぐかを書いた結線表を見ながら挿し、ケーブルの両端に同じ番号のタグを付けます。ラックの大きさや使える電源の量は、データセンターによって異なります。
- **覚え方**: 「棚に載せてラッキング、線を結んで結線」と読み下せば、そのまま意味になります。
- **まちがえやすい**: ケーブルをきれいに束ねすぎると、1 本抜くために全部ほどく羽目になります。見た目より、あとで抜ける余裕を優先します。
- **関連語**: [キッティング](#g-proj-kitting)、[構成図](#g-proj-diagram)、[夜間作業・休日作業](#g-proj-night-work)
- **確かめかた**: ラック搭載図と実機の U 位置を見比べ、結線表のタグ番号がケーブルの両端に付いているかを目で確かめます。

<a id="g-proj-build"></a>
## 構築・ビルド（コウチク／ビルド）

- **一言**: 設計書のとおりにサーバーを組み立て、動く状態まで持っていく作業そのものです。
- **たとえ**: 説明書どおりに組み立て家具を組む時間です。ネジ 1 本の順番まで決まっていて、思いつきで飛ばすとあとで合わなくなります。
- **くわしく**: OS の導入から、ネットワーク設定、ミドルウェア（データベースなど、業務ソフトの土台になるソフト）の導入と設定までを指します。パラメータシートを片手に進め、終わったら自分で軽く動作を見ます。近年は手作業ではなく、設定を書いたファイルから自動で組み立てるやり方（構成管理ツール）も広く使われます。
- **覚え方**: 設計が「図面」なら構築は「工事」で、図面どおりに建てる時間だと覚えます。
- **まちがえやすい**: 構築が終わっても完成ではありません。試験に通ってはじめて「できた」と言えます。
- **関連語**: [パラメータシート](#g-proj-parameter-sheet)、[単体試験・結合試験・総合試験](#g-proj-test-phases)、[キッティング](#g-proj-kitting)
- **確かめかた**: 構築の直後に `systemctl list-units --type=service --state=running` を実行します。動いているはずのサービスがそろっているかを見ます（systemd を使う環境の場合です）。

<a id="g-proj-test-phases"></a>
## 単体試験・結合試験・総合試験（タンタイシケン／ケツゴウシケン／ソウゴウシケン）

- **一言**: 部品ごと、つないだところ、全体の順に、範囲を広げながら動きを確かめる試験です。
- **たとえ**: 料理でいえば、材料をひと口味見するのが単体、合わせたソースを味見するのが結合、一皿として味見するのが総合です。
- **くわしく**: 単体試験は 1 台や 1 機能だけを見ます。結合試験は機器と機器をつないだ通信や連携を見ます。総合試験は本番に近い構成で、業務の流れどおりに一通り動かします。呼び名や区切り方は案件によって異なるので、試験計画書でどこまでを見るのかを確かめます。
- **覚え方**: 1 台（点）、つなぎ目（線）、全体（面）の順に範囲を広げる、と覚えます。
- **まちがえやすい**: 単体試験を飛ばして結合試験から始めると、不具合が出たときに原因の候補が一気に増えます。急がば回れです。
- **関連語**: [構築・ビルド](#g-proj-build)、[試験項目書とエビデンス](#g-proj-test-evidence)、[受入試験・UAT](#g-proj-uat)
- **確かめかた**: 試験項目書を開き、各項目に単体・結合・総合のどれなのかが書かれているかを見ます。

<a id="g-proj-uat"></a>
## 受入試験・UAT（ウケイレシケン／ユー・エー・ティー）

- **一言**: 作った側ではなく、使うお客さま自身が「これで受け取れる」と確かめる試験です。
- **たとえ**: 新築の家の内覧です。建てた大工ではなく、これから住む人が扉を開け閉めして確かめます。
- **くわしく**: UAT は User Acceptance Test の略です。要件定義で決めたことが満たされているかを、使う人の目線で確かめます。ここで合格をもらうと、検収（納品物を受け取ったと認める手続き）に進みます。だから受入試験の日程と合格の条件は、早い段階で合意しておきます。
- **覚え方**: UAT の U は User（使う人）なので、作った人ではなく使う人がやる試験だと覚えます。
- **まちがえやすい**: UAT は動作の細かい確認をやり直す場ではありません。動作は総合試験までに確かめ、UAT では業務として使えるかを見ます。
- **関連語**: [要件定義](#g-proj-requirements)、[単体試験・結合試験・総合試験](#g-proj-test-phases)、[引き渡し・ハンドオーバー](#g-proj-handover)
- **確かめかた**: 契約書や試験計画書で「検収条件」「合格基準」と書かれた箇所を探し、誰が合否を判定するのかを確かめます。

<a id="g-proj-test-evidence"></a>
## 試験項目書とエビデンス（シケンコウモクショ／エビデンス）

- **一言**: 何をどう確かめるかの一覧が試験項目書、確かめた証拠がエビデンスです。
- **たとえ**: 健康診断の検査項目表と、その結果を印刷した検査結果票の関係です。
- **くわしく**: 試験項目書には、手順・期待する結果・実際の結果・合否の判定を書きます。エビデンスは画面の写し（スクリーンショット）やコマンドの出力を保存したものです。あとで「本当に確認したのか」と聞かれたときに答えられるよう、実施日時と実施者も残します。保存の形式や置き場所は案件によって異なります。
- **覚え方**: エビデンスは evidence（証拠）なので、「やりました」ではなく「これが証拠です」と出せる形にします。
- **まちがえやすい**: 合格した項目だけ残すのは不十分です。失敗して直したあとの再試験も、記録として残します。
- **関連語**: [単体試験・結合試験・総合試験](#g-proj-test-phases)、[パラメータシート](#g-proj-parameter-sheet)、[受入試験・UAT](#g-proj-uat)
- **確かめかた**: `date` と `hostnamectl` のように、日時と状態を表示するコマンドの出力を並べて保存し、日時つきの記録にします。

<a id="g-proj-migration"></a>
## 移行・マイグレーション（イコウ／マイグレーション）

- **一言**: いま動いている環境から新しい環境へ、データと役割を引っ越しさせる作業です。
- **たとえ**: 引っ越しそのものです。荷造り（取り出し）、運搬（転送）、荷ほどき（取り込み）、そして新居で暮らせるかの確認まで含みます。
- **くわしく**: データ移行、設定移行、利用者アカウントの移行など、対象ごとに手順が分かれます。移行では、件数や容量が前後で合っているかを必ず数で確かめます。旧環境はすぐには消さず、しばらく戻れるように残しておくのが定石です。
- **覚え方**: 引っ越しと同じで「運ぶ前に数え、運んだあとも数える」と覚えます。
- **まちがえやすい**: データをコピーできた時点では移行完了ではありません。新環境で業務が回ることを確かめて、はじめて移行です。
- **関連語**: [カットオーバー](#g-proj-cutover)、[リハーサル・予行演習](#g-proj-rehearsal)、[切り戻し・ロールバック](#g-proj-rollback)
- **確かめかた**: 移行の前後で `find . -type f | wc -l` のようにファイル数を数え、前後で同じ数になっているかを見ます。

<a id="g-proj-replace"></a>
## リプレース・更改（リプレース／コウカイ）

- **一言**: 古くなった機器や仕組みを、新しいものへまるごと入れ替える案件のことです。
- **たとえ**: 10 年乗った車の買い替えです。まだ走れても、部品が手に入らなくなる前に乗り換えます。
- **くわしく**: 機器やソフトには、製造元が修理や問い合わせ対応をやめる期限（保守期限）があります。その期限が来る前に入れ替える計画を立て、現状の調査、設計、構築、移行、切り替えの順に進めます。「来期リプレース」は、次の年度に入れ替える予定だ、という意味の言い方です。業務のやり方は変えずに、土台だけを新しくするのが基本の考え方です。
- **覚え方**: replace は「置き換える」なので、中身は同じで器だけ新しくする、と覚えます。
- **まちがえやすい**: 新しい機能を作る案件と混同しがちですが、主役はあくまで入れ替えです。まったく同じ製品に替えるとは限らず、後継の機種やクラウドへ移ることもよくあります。
- **関連語**: [移行・マイグレーション](#g-proj-migration)、[カットオーバー](#g-proj-cutover)、[資産管理台帳](#g-proj-asset-ledger)
- **確かめかた**: 資産管理台帳の保守期限の欄を古い順に並べ、`cat /etc/os-release` で見える OS の版と製造元が公開する期限を見比べます。

<a id="g-proj-cutover"></a>
## カットオーバー

- **一言**: 新しい環境に本番を切り替え、そこから業務が新環境で動き出す瞬間です。
- **たとえ**: 新しい店舗の開店です。看板を掛け替えた瞬間から、お客さまは新しい店に入ってきます。
- **くわしく**: 切り替えの日時、実施する順番、誰が「よし」と言うかを事前に決めます。切り替えた直後は監視を厚くし、問題があれば決めた時刻までに切り戻すかどうかを判断します。意味の近い言葉として「本番切り替え」「サービスイン」「本稼働」も使われます。
- **覚え方**: cut over は「切って（cut）向こう側へ（over）」なので、線を切り替える絵で覚えます。
- **まちがえやすい**: カットオーバーは作業の終わりではなく、運用の始まりです。切り替え後の数日は、いちばん問い合わせが多い時期です。
- **関連語**: [移行・マイグレーション](#g-proj-migration)、[切り戻し・ロールバック](#g-proj-rollback)、[本番作業と作業手順書](#g-proj-procedure)
- **確かめかた**: 切り替え計画書に「切り替え日時」「判断する人」「切り戻しの期限」の 3 つが書かれているかを確かめます。

<a id="g-proj-rollback"></a>
## 切り戻し・ロールバック（キリモドシ／ロールバック）

- **一言**: 作業がうまくいかないとき、元の状態に戻して業務を守る手当てです。
- **たとえ**: 登山の下山ルートです。登り始める前に、引き返す道と引き返す時刻を決めておきます。
- **くわしく**: 手順書には、作業手順と同じ丁寧さで切り戻し手順を書きます。どこまで戻すか、どのくらいで戻せるか、誰が戻す判断をするかを事前に決めます。「この時刻を過ぎたら切り戻す」という判断時刻を決めておくと、当日に迷いません。
- **覚え方**: roll back は「巻き戻す」なので、作業を始める前に巻き戻しボタンを用意しておく、と覚えます。
- **まちがえやすい**: 切り戻し手順を書いただけでは戻せません。リハーサルで実際に戻してみて、時間を測ってはじめて使えるものになります。
- **関連語**: [カットオーバー](#g-proj-cutover)、[リハーサル・予行演習](#g-proj-rehearsal)、[本番作業と作業手順書](#g-proj-procedure)
- **確かめかた**: 手元の手順書に「切り戻し」の章があり、判断の時刻と所要時間が書かれているかを確かめます。

<a id="g-proj-rehearsal"></a>
## リハーサル・予行演習（リハーサル／ヨコウエンシュウ）

- **一言**: 本番と同じ手順を事前に通しでやってみて、時間と抜けを確かめる練習です。
- **たとえ**: 結婚式の前日リハーサルです。歩く順番と時間を通しでやっておくから、当日あわてません。
- **くわしく**: 本番に近い環境で、手順書を読みながら書いてあるとおりに実施します。目的は 3 つで、手順の抜けを見つけること、所要時間を測ること、担当の分担を体に入れることです。切り戻し手順も必ず通して、本当に戻せることを確かめます。
- **覚え方**: 「本番でやることは、本番までに一度やる」と覚えます。
- **まちがえやすい**: 慣れた人が手順を飛ばして進めると、リハーサルの意味がなくなります。書かれていない操作をした時点で、手順書の不備が隠れてしまいます。
- **関連語**: [本番作業と作業手順書](#g-proj-procedure)、[切り戻し・ロールバック](#g-proj-rollback)、[移行・マイグレーション](#g-proj-migration)
- **確かめかた**: リハーサルの記録に、各手順の開始・終了時刻と、手順書を直した箇所が残っているかを見ます。

<a id="g-proj-procedure"></a>
## 本番作業と作業手順書（ホンバンサギョウ／サギョウテジュンショ）

- **一言**: 実際に動いている環境へ手を入れる作業と、その台本にあたる文書です。
- **たとえ**: 手術と手術計画書の関係です。相手は生きて動いているので、思いつきで切ることはできません。
- **くわしく**: 手順書には、目的、始めてよい条件、1 手ずつのコマンドと期待する結果、確認方法、切り戻し手順、連絡先を書きます。打ち間違いを防ぐため、コマンドはそのまま貼り付けられる形で書きます。本番では、手順書に書かれていない操作はしません。作業前に読み合わせをして、実施者と確認者の 2 人体制で進めるのが基本です。
- **覚え方**: 「書いてあることだけやる、やったことは全部書く」と覚えます。
- **まちがえやすい**: 検証環境で成功した手順が、本番でそのまま通るとは限りません。台数や負荷、権限が違えば結果も変わります。
- **関連語**: [リハーサル・予行演習](#g-proj-rehearsal)、[作業申請と変更管理](#g-proj-change-request)、[立ち会い](#g-proj-attendance)
- **確かめかた**: 手順書の 1 行を読み、そのままコピーして打てる形になっているか、あいまいな表現が残っていないかを確かめます。

<a id="g-proj-change-request"></a>
## 作業申請と変更管理（サギョウシンセイ／ヘンコウカンリ）

- **一言**: 本番に手を入れる前に、内容と日時を届け出て承認をもらう決まりごとです。
- **たとえ**: マンションの共用部を使う工事の届け出です。管理組合の許可なしに、勝手に足場は組めません。
- **くわしく**: 申請には、作業内容、影響する範囲、実施日時、切り戻しの方法、緊急連絡先を書きます。承認されると作業番号（チケット番号）が発行され、当日はその番号で呼ばれます。誰がいつ何を変えたかが残るので、障害のときに「直前の変更」をたどれます。多くの現場では、申請が通っていない作業は実施できません。
- **覚え方**: 「無断で触らない、変えたら残す」の 2 つが変更管理だと覚えます。
- **まちがえやすい**: 「設定を 1 行だけ」でも変更は変更です。小さいから申請は要らない、という自己判断が事故のもとになります。
- **関連語**: [本番作業と作業手順書](#g-proj-procedure)、[夜間作業・休日作業](#g-proj-night-work)、[保守契約と SLA](#g-proj-maintenance-sla)
- **確かめかた**: 障害の切り分けでは、まず変更管理の記録を開き、直前に承認された作業がないかを探します。

<a id="g-proj-attendance"></a>
## 立ち会い（タチアイ）

- **一言**: 作業の場に別の担当者や関係者が同席し、確認と判断を担う役割です。
- **たとえ**: 工事の現場に同席する建物の管理人です。作業するのは業者ですが、鍵を開け、傷が付いていないかを見るのは管理人です。
- **くわしく**: お客さま側の立ち会い、保守ベンダーの立ち会い、社内の先輩の立ち会いなど、立場はさまざまです。手順どおりに進んでいるかを見て、判断が必要な場面でその場で決めます。入館の手続きが要る施設では、立ち会う人の名前を事前に届け出ます。
- **覚え方**: 「手は 1 人、目はもう 1 人」と覚えると、立ち会いが見学ではないと分かります。
- **まちがえやすい**: 立ち会いは見学ではありません。声に出して確認し、判断した内容を記録に残すところまでが役目です。
- **関連語**: [本番作業と作業手順書](#g-proj-procedure)、[夜間作業・休日作業](#g-proj-night-work)、[試験項目書とエビデンス](#g-proj-test-evidence)
- **確かめかた**: 作業計画書の体制欄を見て、実施者・確認者・立ち会う人が別々の名前になっているかを確かめます。

<a id="g-proj-night-work"></a>
## 夜間作業・休日作業（ヤカンサギョウ／キュウジツサギョウ）

- **一言**: 業務が止まっている時間帯に合わせて行う、深夜や休日のサーバー作業です。
- **たとえ**: 電車が走らない終電後に線路を直すのと同じです。走っている間は線路に触れません。
- **くわしく**: 利用者が少ない時間帯に、停止をともなう作業をまとめて行います。作業できる時間の枠（作業ウィンドウ）が決まっていて、その時刻までに終わらなければ切り戻します。眠気と焦りで手順を飛ばしやすいので、読み上げと復唱、休憩の取り方まで計画に入れます。手当や振替休日の扱いは会社によって異なります。
- **覚え方**: 「人が使わない時間に、人が眠い作業をする」から、手順書と交代要員が要ると覚えます。
- **まちがえやすい**: 夜間だから安全、ではありません。人が少ないぶん、問題が起きたときに助けを呼びにくい時間帯です。
- **関連語**: [本番作業と作業手順書](#g-proj-procedure)、[切り戻し・ロールバック](#g-proj-rollback)、[立ち会い](#g-proj-attendance)
- **確かめかた**: 作業計画の時間割に、切り戻しを判断する時刻と、撤収までの時間が含まれているかを確かめます。

<a id="g-proj-ses"></a>
## 客先常駐と SES（キャクサキジョウチュウ／エス・イー・エス）

- **一言**: お客さまの職場で働く形が客先常駐、その働き方を支える契約の一つが SES です。
- **たとえ**: 自分の会社に籍を置いたまま、よその会社の席に通って働く形です。給料は自社から出て、机は先方にあります。
- **くわしく**: SES は System Engineering Service の略で、日本の現場で使われる呼び方です。多くは準委任契約で、成果物の完成ではなく、決められた時間の作業に対して対価が支払われます。誰が作業を指示するか（指揮命令）は自社の責任者にあるのが原則です。契約の形は案件によって異なるので、入る前に自分の契約を確かめます。
- **覚え方**: SES は「時間を売る」、請負は「完成品を売る」と、売り物の違いで覚えます。
- **まちがえやすい**: 常駐先の社員と机を並べていても、雇い主は自社です。派遣契約では派遣先が指示できますが、SES で常駐先から直接指示を受ける形は契約上の問題になります。
- **関連語**: [元請けと下請け・多重下請け](#g-proj-prime-sub)、[SIer](#g-proj-sier)、[工数と見積もり](#g-proj-man-hours)
- **確かめかた**: 自分の契約書や注文書を開き、契約の種類が準委任・請負・派遣のどれなのかを確かめます。

<a id="g-proj-prime-sub"></a>
## 元請けと下請け・多重下請け（モトウケ／シタウケ／タジュウシタウケ）

- **一言**: お客さまと直接契約する会社が元請け、その先で仕事を請ける会社が下請けです。
- **たとえ**: 家を建てるときの工務店と、その下で働く大工・電気屋・水道屋の関係です。お客さまの窓口は工務店 1 社だけです。
- **くわしく**: 元請けは全体の責任を負い、進み方の管理とお客さまへの報告を担います。下請けはその一部を請け、さらに下へ流れていくことを多重下請けと呼びます。段が増えるほど、要件が伝わるまでに時間がかかり、途中で話が変わりやすくなります。誰が決める人かを早い段階で見極めるのが、現場で困らないコツです。
- **覚え方**: 「お客さまに近いほど元、遠いほど下」と、連絡の距離で覚えます。
- **まちがえやすい**: 現場での役割の大小と、契約の段は別物です。下請けの技術者が実質の中心を担っていることも珍しくありません。
- **関連語**: [SIer](#g-proj-sier)、[客先常駐と SES](#g-proj-ses)、[上流工程と下流工程](#g-proj-upstream-downstream)
- **確かめかた**: 案件の体制図を見て、自分の会社が誰と契約しているのか（直接の発注元）をたどります。

<a id="g-proj-upstream-downstream"></a>
## 上流工程と下流工程（ジョウリュウコウテイ／カリュウコウテイ）

- **一言**: 要件定義や設計が上流、構築や試験、運用が下流と呼ばれる工程の区分です。
- **たとえ**: 川の流れです。上流で水を汚すと、下流のすべてに濁りが届きます。
- **くわしく**: 上流は「決める」仕事、下流は「作って確かめる」仕事です。上流の決めごとがあいまいだと、下流で手戻りが起き、費用も時間も増えます。どこまでを上流と呼ぶかは会社によって異なり、運用を下流に含めない数え方もあります。求人票では「上流工程の経験」が歓迎条件になることが多いですが、下流を知らないまま書いた設計は現場で使えないものになりがちです。
- **覚え方**: 川の上流から下流へ、決める・作る・確かめるの順に流れると覚えます。
- **まちがえやすい**: 上流が偉くて下流が下、という意味ではありません。仕事が流れる順番を表しているだけの言葉です。
- **関連語**: [要件定義](#g-proj-requirements)、[基本設計と詳細設計](#g-proj-basic-detail-design)、[元請けと下請け・多重下請け](#g-proj-prime-sub)
- **確かめかた**: 求人票の「担当工程」欄を見て、要件定義から運用までのどこが書かれているかを読み取ります。

<a id="g-proj-sier"></a>
## SIer（エスアイヤー）

- **一言**: お客さまの要望を聞いて、機器やソフトを組み合わせ、動く仕組みにして納める会社です。
- **たとえ**: 旅行会社です。飛行機も宿もバスも自社では持たず、それらを組み合わせて 1 つの旅程にして売ります。
- **くわしく**: SI は System Integration の略で、複数のものを組み合わせて 1 つの仕組みにすることです。それを行う会社を SIer と呼びます。要件定義から設計、構築、試験、引き渡しまでを請け負い、そのまま保守運用まで続くこともあります。自社製品を売るメーカーとは立場が違い、他社の製品も組み合わせて納めるのが仕事の中身です。
- **覚え方**: SI（組み合わせる）に er（する人・会社）が付いて SIer だと覚えます。
- **まちがえやすい**: SIer は日本で生まれた言い方で、英語では通じにくい言葉です。海外の相手には system integrator と伝えます。
- **関連語**: [元請けと下請け・多重下請け](#g-proj-prime-sub)、[客先常駐と SES](#g-proj-ses)、[上流工程と下流工程](#g-proj-upstream-downstream)
- **確かめかた**: 会社案内や求人票を読み、自社製品を売る会社か、他社製品を組み合わせて納める会社かを読み分けます。

<a id="g-proj-helpdesk"></a>
## ヘルプデスクと運用オペレーター（ヘルプデスク／ウンヨウオペレーター）

- **一言**: 問い合わせに答えるのがヘルプデスク、手順どおりに機器を見守るのが運用オペレーターです。
- **たとえ**: ヘルプデスクはお店の受付、運用オペレーターはビルの防災センターです。片方は人を、片方は設備を見ています。
- **くわしく**: ヘルプデスクは、利用者からの「つながらない」「パスワードを忘れた」に一次対応します。運用オペレーターは、監視画面や警報を見て、手順書に沿って初動を行い、必要なら担当者を呼び出します。どちらも運用手順書が仕事の土台で、自分で判断してよい範囲があらかじめ決められています。
- **覚え方**: ヘルプデスクは「人の困りごと」、オペレーターは「機械の異常」が入り口だと覚えます。
- **まちがえやすい**: 手順書にない対応を自分の判断でやってしまうのが、いちばん多い失敗です。範囲外はためらわずエスカレーション（上位の担当者への引き継ぎ）します。
- **関連語**: [保守契約と SLA](#g-proj-maintenance-sla)、[本番作業と作業手順書](#g-proj-procedure)、[インフラエンジニアの職種の広がり](#g-proj-infra-roles)
- **確かめかた**: 手元の運用手順書で、自分の判断でよい範囲と、エスカレーション先の連絡方法を確かめます。

<a id="g-proj-infra-roles"></a>
## インフラエンジニアの職種の広がり（インフラエンジニアノショクシュノヒロガリ）

- **一言**: サーバー、ネットワーク、クラウド、監視、セキュリティなどに枝分かれした職種の総称です。
- **たとえ**: 建設の世界と同じで、基礎工事、電気、配管、警備に分かれています。全部を一人でやる人はまれです。
- **くわしく**: サーバーエンジニア、ネットワークエンジニア、クラウドエンジニアなどが代表です。ほかに SRE（サービスが止まらないよう仕組みで支える役割）、セキュリティエンジニア、運用や監視の担当もあります。入り口が運用や監視でも、そこから設計や構築へ移る道はよくあります。求人票の職種名だけでは中身が分からないので、担当工程と扱う機器で読み解きます。
- **覚え方**: 「土台（サーバー）・道（ネットワーク）・見張り（監視）・鍵（セキュリティ）」の 4 方向に広がると覚えます。
- **まちがえやすい**: 職種名と実際の仕事は一致しないことがあります。同じ「インフラエンジニア」でも、配属先によって触るものは大きく変わります。
- **関連語**: [ヘルプデスクと運用オペレーター](#g-proj-helpdesk)、[上流工程と下流工程](#g-proj-upstream-downstream)、[客先常駐と SES](#g-proj-ses)
- **確かめかた**: 求人票の業務内容を読み、扱う機器・担当工程・当直の有無の 3 点を書き出して比べます。

<a id="g-proj-maintenance-sla"></a>
## 保守契約と SLA（ホシュケイヤク／エス・エル・エー）

- **一言**: 壊れたときに直す約束が保守契約、その品質を数字で約束したものが SLA です。
- **たとえ**: 家電の延長保証と、その保証書に書かれた「翌営業日に訪問」という条件の関係です。
- **くわしく**: 保守契約では、対応する時間帯、部品の交換、窓口の連絡先などを決めます。SLA は Service Level Agreement の略で、稼働率や、連絡を受けてから対応を始めるまでの時間などを約束します。約束の中身と、守れなかったときの扱いは契約によって異なります。運用の現場では、この時間を目安に「あと何分で一次回答」と動きます。
- **覚え方**: SLA の L は Level（水準）で、どの水準を守るかを数字にした約束だと覚えます。
- **まちがえやすい**: SLA に書かれた時間が、復旧までの時間とは限りません。到着までなのか、対応を始めるまでなのか、復旧までなのかは契約ごとに違います。
- **関連語**: [ヘルプデスクと運用オペレーター](#g-proj-helpdesk)、[引き渡し・ハンドオーバー](#g-proj-handover)、[資産管理台帳](#g-proj-asset-ledger)
- **確かめかた**: 保守契約書を開き、対応時間帯・連絡先・対象機器の一覧の 3 点を確かめます。

## 資産管理台帳（シサンカンリダイチョウ）

- **一言**: 機器やソフトを 1 台ずつ登録し、置き場所と持ち主を管理するための帳簿です。
- **たとえ**: 図書館の蔵書台帳です。どの本が今どこにあり、誰が借りているかが分かります。
- **くわしく**: 管理番号、型番、製造番号（シリアル）、設置場所、用途、保守の期限、担当者などを記録します。故障で交換するとき、保守期限を確認するとき、台数を問われたときに使います。台帳と現物が合っていることが大事なので、機器を動かしたら台帳も直します。
- **覚え方**: 「モノには番号、番号には行き先」と覚え、番号で追えるようにするのが台帳です。
- **まちがえやすい**: 台帳は買ったときに作って終わりではありません。廃棄や移設を書かないと、実在しない機器が台帳に残り続けます。
- **関連語**: [キッティング](#g-proj-kitting)、[保守契約と SLA](#g-proj-maintenance-sla)、[ドキュメント整備](#g-proj-documentation)
- **確かめかた**: `hostnamectl` に出る機種名や、`lsblk` で見えるディスクの構成を台帳の記載と照らし合わせます。表示される項目は環境によって異なります。

## ドキュメント整備（ドキュメントセイビ）

- **一言**: 設計書や手順書を、次の人が読んで動ける状態にそろえておく仕事です。
- **たとえ**: お店の引き継ぎノートです。自分が休んだ日に、別の人が同じ手順で開店できるかどうかが基準になります。
- **くわしく**: 対象は設計書、パラメータシート、構成図、運用手順書、連絡先一覧などです。大事なのは、置き場所が一つに決まっていること、どれが最新版か分かること、直したら日付と変更内容を残すことです。読む人を「明日入る新人」と想像して書くと、細かさがちょうどよくなります。
- **覚え方**: 「探せない文書は、無いのと同じ」と覚え、置き場所と最新版をそろえます。
- **まちがえやすい**: 完璧な文書を目指して書き終わらないより、粗くても最新であるほうが役に立ちます。古い正解より、新しい現状です。
- **関連語**: [構成図](#g-proj-diagram)、[パラメータシート](#g-proj-parameter-sheet)、[引き渡し・ハンドオーバー](#g-proj-handover)
- **確かめかた**: 文書の置き場所を開き、更新日付と版数（バージョン）で新しい順にたどれるかを確かめます。

## Git／バージョン管理（ギット／バージョンカンリ）

- **一言**: 設定ファイルや手順書の変更履歴を残し、前の状態にいつでも戻せる仕組みです。
- **たとえ**: ゲームのセーブデータです。こまめに保存しておけば、失敗しても好きな地点からやり直せます。
- **くわしく**: Git は、ファイルを直した時点ごとに記録し、誰がいつどの行を変えたかを残す道具です。Ansible や Terraform のように、設定を文章で書いて自動で作らせる道具では、その設定ファイルを Git で保管するのが前提になっています。作業のときは本流とは別の枝（ブランチ）で試し、問題がなければ本流に取り込む進め方をします。GitHub や GitLab は、その記録をみんなで共有する置き場を貸すサービスです。
- **覚え方**: 「保存して残す」が Git、「別の道で試す」がブランチと、2 つの動きで覚えます。
- **まちがえやすい**: Git と GitHub は別物です。Git は手元だけでも動く仕組みで、GitHub はそれを預かるサービスの名前です。
- **関連語**: [ドキュメント整備](#g-proj-documentation)、[作業申請と変更管理](#g-proj-change-request)、Ansible
- **確かめかた**: 作業中のフォルダで `git status` を実行して直した箇所を確かめ、`git log --oneline -5` で最近の変更履歴を読みます。

## 引き渡し・ハンドオーバー（ヒキワタシ／ハンドオーバー）

- **一言**: 作った環境と文書を運用担当へ渡し、面倒を見る責任の持ち主を移す区切りです。
- **たとえ**: 新築の家の引き渡しです。鍵と、保証書と、設備の説明書をそろえて手渡します。
- **くわしく**: 渡すものは、環境そのもの、設計書、手順書、パラメータシート、資産管理台帳、そして未解決の課題一覧です。引き継ぎ会を開き、運用担当が実際に操作してみる時間をとります。この日を境に、問い合わせ先も構築チームから運用チームへ移ります。残っている課題を隠さず一覧にして渡すのが、渡す側の礼儀です。
- **覚え方**: 「鍵と説明書と、直っていない箇所のメモ」の 3 点がそろって引き渡しだと覚えます。
- **まちがえやすい**: 引き渡しはサポートの終わりではありません。しばらく構築側が支援する期間を設けることが多く、その長さは契約によって異なります。
- **関連語**: [ドキュメント整備](#g-proj-documentation)、[受入試験・UAT](#g-proj-uat)、[保守契約と SLA](#g-proj-maintenance-sla)
- **確かめかた**: 引き継ぎチェックリストを開き、渡す文書の欄と残課題の欄が最後まで埋まっているかを確かめます。
