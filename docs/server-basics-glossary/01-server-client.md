# 1. サーバーとクライアント ― 全体像をつかむ

[用語集の入口](README.md) / [さくいん](index.md) / [次: サーバーのハードウェア](02-hardware.md)

この章では、現場に入った初日から耳に飛び込んでくる言葉をまとめます。細かい設定は後の章にゆずり、まずは「誰が誰に何を頼んでいるのか」という全体像をつかみます。

> **この章で最初に押さえる 3 語**: サーバー ／ クライアント ／ リクエストとレスポンス

<a id="g-intro-server"></a>
## サーバー

- **一言**: 頼まれた仕事を引き受けて、結果を返し続ける側のコンピューターです。
- **たとえ**: レストランの厨房です。注文を受けて料理を作り、皿にして出す側にあたります。
- **くわしく**: サーバーは機械の名前ではなく「役割」の名前です。同じ 1 台でも、頼まれる側に回っていればサーバーと呼びます。役割ごとに Web サーバー、データベースサーバーのように呼び分けます。
- **覚え方**: 英語の serve は「給仕する」、料理を出す側がサーバーだと覚えます。
- **まちがえやすい**: 高価な業務用の機械だけがサーバー、ではありません。手元のパソコンでもサーバー用のソフトを動かせば、その瞬間からサーバーです。
- **関連語**: [クライアント](#g-intro-client)、[ホスト](#g-intro-host)、[サーバー機とサーバーソフトウェアの違い](#g-intro-server-machine-software)
- **確かめかた**: `curl -I https://example.com` を実行すると、返事の中に `Server:` の行が見えることがあります（出ないこともあり、環境によって異なります）。

<a id="g-intro-client"></a>
## クライアント

- **一言**: サーバーに仕事を頼み、返ってきた結果を受け取る側のことです。
- **たとえ**: レストランで注文する側の席です。自分では作らず、頼んで運ばれてくるのを待ちます。
- **くわしく**: ブラウザ、スマホアプリ、`curl` のようなコマンドがクライアントです。画面を持つとは限らず、プログラムが黙って通信する場合もクライアントと呼びます。
- **覚え方**: 頼む側がクライアント、受ける側がサーバー、と対で覚えます。
- **まちがえやすい**: 人ではなく、ソフトや機器を指す言葉です。サーバー同士の通信でも、頼んだ側はそのときだけクライアントになります。
- **関連語**: [サーバー](#g-intro-server)、[リクエストとレスポンス](#g-intro-request-response)、[エンドユーザー](#g-intro-end-user)
- **確かめかた**: `curl -v https://example.com` を実行すると、自分がクライアントとして送っている行が `>` 付きで表示されます。

<a id="g-intro-host"></a>
## ホスト

- **一言**: ネットワークにつながり、住所を持つ 1 台のコンピューターのことです。
- **たとえ**: マンションの 1 部屋です。表札にあたるのがホスト名、部屋番号にあたるのが IP アドレスです。
- **くわしく**: 「サーバー 3 台」と数えるとき、その 1 台 1 台がホストです。手順書に出てくる接続先も、たいていホスト名で書かれています。作業前に今どのホストにいるかを確かめる習慣が、事故を防ぎます。
- **覚え方**: host は「家主」、ネットワーク上の一軒家だと覚えます。
- **まちがえやすい**: サーバーと同じ意味ではありません。サーバーは役割の話、ホストは「どの 1 台か」という所在の話です。
- **関連語**: [ノード](#g-intro-node)、[サーバー](#g-intro-server)、[物理サーバーと仮想サーバー](#g-intro-physical-virtual-server)
- **確かめかた**: `hostname` で今いる機械の名前が出ます。`hostnamectl` なら、もう少し詳しい情報も並びます。

<a id="g-intro-node"></a>
## ノード

- **一言**: ネットワークやクラスターを構成する、1 つ 1 つの機器のことです。
- **たとえ**: 路線図の駅です。線路（ケーブル）でつながれた点の 1 つ 1 つがノードにあたります。
- **くわしく**: サーバー、ルーター、仮想サーバー、クラスター（複数台を束ねた集まり）の中の 1 台などを、まとめてノードと呼びます。「ノードを 1 台足す」のように、台数を増やす話でよく使われます。
- **覚え方**: node は「結び目」、線でつながれた点の 1 つだと覚えます。
- **まちがえやすい**: ホストとほぼ同じものを指しますが、ノードは「つながりの中の 1 点」という見方を強めた言い方です。
- **関連語**: [ホスト](#g-intro-host)、[冗長化](#g-intro-redundancy)、[システム構成図](#g-intro-architecture-diagram)
- **確かめかた**: 構成図の中で四角や丸として描かれた 1 つ 1 つがノードです。クラスターを扱う現場なら `kubectl get nodes` のような一覧コマンドがあります（環境によって異なります）。

<a id="g-intro-request-response"></a>
## リクエストとレスポンス（リクエスト・レスポンス）

- **一言**: クライアントが送る「お願い」と、サーバーが返す「返事」の 1 往復です。
- **たとえ**: 注文票と料理です。「ハンバーグをください」と伝えるのがリクエスト、運ばれてくる皿がレスポンスです。
- **くわしく**: リクエストには「何をしたいか」と「どこに対してか」が入ります。レスポンスにはステータスコード（結果を表す 3 桁の数字）が付きます。200 は成功、404 は指定先が見つからない、500 はサーバー側のエラーです。障害調査は、この往復のどこで止まったかを探す作業になります。
- **覚え方**: 行き（リクエスト）と帰り（レスポンス）で 1 往復、と覚えます。
- **まちがえやすい**: 画面が出ないからといって、サーバーが壊れたとは限りません。そもそもリクエストが届いていない場合もあり、404 と 500 では原因の場所がまったく違います。
- **関連語**: [クライアント](#g-intro-client)、[プロトコル](#g-intro-protocol)、[セッション](#g-intro-session)
- **確かめかた**: `curl -i https://example.com` を実行すると、返事の 1 行目にステータスコードが表示されます。

<a id="g-intro-protocol"></a>
## プロトコル

- **一言**: 通信の手順と言葉づかいを決めた、機械どうしの共通ルールです。
- **たとえ**: 電話のマナーです。「もしもし」→ 名乗る → 用件、という順番をお互いが守るから会話が成り立ちます。
- **くわしく**: Web の表示は HTTP と HTTPS、遠隔操作は SSH、メール送信は SMTP というように、用途ごとに決まっています。手順がそろっていなければ、同じ機械につながっていても会話は成立しません。
- **覚え方**: プロトコルは話し方の作法、作法が違う相手とは話が通じないと覚えます。
- **まちがえやすい**: HTTP と HTTPS は別のプロトコルです（通信内容を暗号化するかどうかが違います）。片方だけつながって、もう片方はつながらない状況はよく起こります。
- **関連語**: [リクエストとレスポンス](#g-intro-request-response)、[セッション](#g-intro-session)、[クライアント](#g-intro-client)
- **確かめかた**: `curl -v https://example.com` の出力に、`HTTP/1.1` や `HTTP/2` のように使われたプロトコルが表示されます。

<a id="g-intro-session"></a>
## セッション

- **一言**: 通信を始めてから終わるまでの、ひとまとまりのやり取りのことです。
- **たとえ**: 美容室の 1 回の来店です。受付から会計までがひとまとまりで、次に行けば別の来店として扱われます。
- **くわしく**: リクエストとレスポンスの 1 往復だけでは、サーバーは相手を覚えていません。そこでサーバーは、セッション ID という目印の文字列を発行します。それを Cookie（ブラウザに預ける小さなメモ）に持たせて、同じ相手だと見分けます。SSH でつないでから切るまでも、1 セッションと数えます。
- **覚え方**: session は「1 回の面談」、始まりと終わりが必ずあると覚えます。
- **まちがえやすい**: ブラウザを閉じればすぐ消える、とは限りません。有効期限や、無操作で切れるまでの時間は環境によって異なります。
- **関連語**: [リクエストとレスポンス](#g-intro-request-response)、[プロトコル](#g-intro-protocol)、[アプリケーション](#g-intro-application)
- **確かめかた**: `who` で、今ログインしているセッションが一覧できます。Web なら、ブラウザの開発者ツールで Cookie の一覧を見ます。

<a id="g-intro-infrastructure"></a>
## インフラ（インフラストラクチャ）

- **一言**: アプリを動かすために下から支える、機器や回線や電源などの土台です。
- **たとえ**: 建物の基礎と、水道・電気・ガスです。住む人は普段意識しませんが、止まれば生活が全部止まります。
- **くわしく**: インフラストラクチャ（下部構造、つまり土台）の略です。サーバー、ネットワーク、ストレージ（データを保管する装置）、電源、監視の仕組みまでを含みます。インフラ担当の仕事は、この土台を用意し、一部が壊れても業務が続くようにしておくことです。
- **覚え方**: infra は「下」、下から支える土台だと覚えます。
- **まちがえやすい**: インフラはサーバーだけを指す言葉ではありません。回線や電源、監視も含めて、初めて土台がそろいます。
- **関連語**: [データセンター](#g-intro-datacenter)、[オンプレミス](#g-intro-onpremise)、[クラウド](#g-intro-cloud)
- **確かめかた**: `df -h` で保存領域の空き、`free -h` でメモリ（作業用の記憶領域）の空きを見て、土台の余裕を数字で確認します。

<a id="g-intro-onpremise"></a>
## オンプレミス

- **一言**: 自分たちで機器を用意して持ち、自分たちで面倒を見る形のことです。
- **たとえ**: 持ち家です。好きに改造できるかわりに、雨漏りの修理費も自分持ちになります。
- **くわしく**: 機器の購入、設置、配線、故障時の交換までを自社で計画します。要件に合わせて細かく作り込めますが、増やすときは発注と納品の時間がかかります。「オンプレ」と略します。
- **覚え方**: on premises は「敷地の上に」、自分の土地に自分の機械を置くと覚えます。
- **まちがえやすい**: 自社の部屋に置くことだけがオンプレミスではありません。データセンターの一区画を借り、そこに自社の機器を置く形もオンプレミスです。
- **関連語**: [クラウド](#g-intro-cloud)、[データセンター](#g-intro-datacenter)、[ラックと 1U](#g-intro-rack-1u)
- **確かめかた**: 機器に自社の資産管理シールが貼ってあるか、ハードウェアの保守契約書があるかを見ると判断できます。

<a id="g-intro-cloud"></a>
## クラウド

- **一言**: 他社が持つ機器を、必要な分だけ借りて使うサービスの形のことです。
- **たとえ**: レンタカーです。買わずに借りて、使い終われば返し、使った分だけ払います。
- **くわしく**: 管理画面から短時間でサーバーを増やせ、要らなくなれば消せます。機器そのものの故障対応は、基本的に事業者側の担当です。借りる範囲によって、機械だけ借りる形、動かす土台まで借りる形、完成したソフトを使う形に分かれます。料金の考え方は事業者や契約によって異なります。
- **覚え方**: 買うのがオンプレミス、借りるのがクラウド、と対で覚えます。
- **まちがえやすい**: クラウドだから絶対に落ちない、ではありません。予備を用意して落ちにくくする設計は、借りている側の仕事です。
- **関連語**: [オンプレミス](#g-intro-onpremise)、[冗長化](#g-intro-redundancy)、[物理サーバーと仮想サーバー](#g-intro-physical-virtual-server)
- **確かめかた**: 契約している事業者の管理画面で、動いている台数と契約内容を見ます。機械の中からは `systemd-detect-virt` で仮想化の種類が見えることもあります（環境によって異なります）。

<a id="g-intro-datacenter"></a>
## データセンター

- **一言**: サーバーを安全に置くために造られた、電源と空調に強い専用の建物です。
- **たとえ**: 機械のための頑丈なホテルです。空調と警備がついていて、部屋にあたるラックを借りて泊めます。
- **くわしく**: 停電に備えて UPS（電気が切れても一定時間だけ電気を送り続ける装置）や自家発電を持ち、通信回線も複数用意されているのが一般的です。入退室は申請制で、勝手には入れません。「DC」と略します。
- **覚え方**: サーバーの寮、人ではなく機械が住んでいる建物だと覚えます。
- **まちがえやすい**: クラウドの反対語ではありません。クラウド事業者の機器も、どこかのデータセンターの中に置かれています。
- **関連語**: [ラックと 1U](#g-intro-rack-1u)、[オンプレミス](#g-intro-onpremise)、[インフラ](#g-intro-infrastructure)
- **確かめかた**: 現場に行く前に、入館申請の手順書と持ち込みのルールを確認します。

<a id="g-intro-rack-1u"></a>
## ラックと 1U（ラック・イチユー）

- **一言**: サーバーを積み重ねる棚がラック、その高さを数える単位が 1U です。
- **たとえ**: 本棚と本の厚みです。棚がラックで、本 1 冊分の厚みにあたるのが 1U です。
- **くわしく**: 機器を取り付ける幅が 19 インチのラックが広く使われ、高さの単位 1U は 1.75 インチ（約 4.4 cm）と決まっています。機器も 1U サーバー、2U サーバーのように厚みで呼びます。1 本のラックに何 U 入るかは、製品によって異なります。
- **覚え方**: U は Unit の U、数字が大きいほど分厚い機器だと覚えます。
- **まちがえやすい**: 空きが U で足りていても、設置できるとは限りません。奥行き、重量、そのラックで使える電力にも上限があります。
- **関連語**: [データセンター](#g-intro-datacenter)、[オンプレミス](#g-intro-onpremise)、[サーバー機とサーバーソフトウェアの違い](#g-intro-server-machine-software)
- **確かめかた**: 機器の仕様書に「1U」「2U」と書かれています。どのラックの何 U 目に載っているかは、ラック搭載図で確認します。

<a id="g-intro-server-machine-software"></a>
## サーバー機とサーバーソフトウェアの違い（サーバーキ・サーバーソフトウェアノチガイ）

- **一言**: 同じ「サーバー」でも、機械そのものを指す時とソフトを指す時があります。
- **たとえ**: 厨房と料理人です。厨房（機械）があっても、料理人（ソフト）がいなければ料理は出てきません。
- **くわしく**: 機械は電源やディスク（データを記録する部品）を持つ、手で触れるハードウェアです。そこに Web サーバーやデータベースのソフトを入れて、初めて役割を持ったサーバーになります。1 台の機械に、複数のサーバーソフトを同居させることもできます。
- **覚え方**: 箱の話（機械）か中身の話（ソフト）か、で聞き分けると覚えます。
- **まちがえやすい**: 「サーバーが落ちた」には、機械ごと止まった場合とソフトだけ止まった場合があります。`ping` は返るのに画面が出ないなら、まずソフト側を疑います。
- **関連語**: [サーバー](#g-intro-server)、[ミドルウェア](#g-intro-middleware)、[物理サーバーと仮想サーバー](#g-intro-physical-virtual-server)
- **確かめかた**: 機械の生死は `ping -c 3 example.com`、ソフトの生死は `systemctl status nginx` のように、分けて確認します。

<a id="g-intro-physical-virtual-server"></a>
## 物理サーバーと仮想サーバー（ブツリサーバー・カソウサーバー）

- **一言**: 手で触れる 1 台が物理、その中にソフトで作った 1 台が仮想サーバーです。
- **たとえ**: 一軒家とシェアハウスの個室です。建物は 1 つでも、玄関と鍵は部屋ごとに分かれています。
- **くわしく**: ハイパーバイザー（1 台を複数台に見せる土台のソフト）が CPU やメモリを分け合い、複数の仮想サーバーを動かします。仮想サーバーは短時間で作れて複製もできるので、台数の増減が楽になります。
- **覚え方**: 箱は 1 つ、部屋はいくつも、と覚えます。
- **まちがえやすい**: 物理 1 台が壊れると、その上の仮想サーバーはまとめて止まります。仮想サーバーとコンテナは別物で、コンテナは OS の中核部分（カーネル）を共有する、もっと軽い間借りです。
- **関連語**: [ホスト](#g-intro-host)、[クラウド](#g-intro-cloud)、[冗長化](#g-intro-redundancy)
- **確かめかた**: `systemd-detect-virt` の結果や、`lscpu` の出力に仮想化の表示があるかで見分けます（環境によって異なります）。

<a id="g-intro-redundancy"></a>
## 冗長化（ジョウチョウカ）

- **一言**: 同じ役割の予備を用意し、1 つ壊れても止まらないようにする備えです。
- **たとえ**: 車のスペアタイヤと、ビルの非常階段です。普段は使いませんが、無いといざという時に困ります。
- **くわしく**: サーバーを 2 台にする、電源を 2 系統から取る、回線を 2 本引く、といったやり方があります。ディスクを RAID（複数台を束ねて 1 台に見せる仕組み）にするのも冗長化です。壊れた側から予備側へ自動で切り替わることを、フェイルオーバーと呼びます。
- **覚え方**: ムダに見えて命綱、と覚えます。
- **まちがえやすい**: 冗長化はバックアップの代わりになりません。誤って消したデータは、予備側でも同じように消えます。
- **関連語**: [可用性](#g-intro-availability)、[ノード](#g-intro-node)、[24 時間 365 日](#g-intro-24-365)
- **確かめかた**: `ip a` で通信の口が何本あるかを見ます。`cat /proc/mdstat` ではソフトウェア RAID の構成が見えます（機器側で組んだ RAID は見えません）。

<a id="g-intro-availability"></a>
## 可用性（カヨウセイ）

- **一言**: 使いたいときにいつでも使える度合いを表す、止まりにくさの指標です。
- **たとえ**: 24 時間営業のコンビニです。閉まっている時間が短いほど、可用性が高い店になります。
- **くわしく**: 稼働率（動いていた時間の割合）で表します。たとえば稼働率 99.9% なら、1 年の停止が 9 時間弱までという計算です。9 の数を増やすほど、必要な設備も費用も大きくなります。どこまでを目標にするかは業務の重さで決めるため、環境によって異なります。
- **覚え方**: ナインが増えるほど休めない、と覚えます。
- **まちがえやすい**: 可用性と性能は別の話です。表示が速くても落ちれば可用性は低く、遅くても動き続けていれば可用性は高いと数えます。
- **関連語**: [冗長化](#g-intro-redundancy)、[24 時間 365 日](#g-intro-24-365)、[システムとサービスの違い](#g-intro-system-vs-service)
- **確かめかた**: `uptime` で、前回の起動からの連続稼働時間が見えます。長期の稼働率は、監視ツールのレポートで確認します。

<a id="g-intro-environments"></a>
## 本番環境・検証環境・開発環境（ホンバンカンキョウ・ケンショウカンキョウ・カイハツカンキョウ）

- **一言**: 利用者が使う本番と、その手前で安全に試すための場所の呼び分けです。
- **たとえ**: 舞台の本番、リハーサル、稽古場です。稽古場でどれだけ失敗しても、お客様には見えません。
- **くわしく**: 開発環境は作りながら壊す場所、検証環境（ステージング）は本番に近い構成で最終確認する場所、本番環境は実際の利用者が触る場所です。dev、stg、prd のように略しますが、呼び方は現場によって異なります。本番の作業だけは、手順書と承認を必ず通します。
- **覚え方**: 稽古（開発）→ リハ（検証）→ 本番、と左から右へ進むと覚えます。
- **まちがえやすい**: 検証で動いたから本番でも動く、とは限りません。データの量、権限、外部との接続が違うためです。
- **関連語**: [構築と運用](#g-intro-build-and-operate)、[ホスト](#g-intro-host)、[アプリケーション](#g-intro-application)
- **確かめかた**: `hostname` を打ち、名前に含まれる dev / stg / prd から今いる環境を確かめます。

<a id="g-intro-24-365"></a>
## 24 時間 365 日（ニジュウヨジカン・サンビャクロクジュウゴニチ）

- **一言**: 夜も休日も止めずに動かし続ける、無停止運用の考え方のことです。
- **たとえ**: 病院の当直です。人は交代しても、灯りは消しません。
- **くわしく**: 人が寝ている間も機械は動くので、異常を自動で見つけて知らせる監視の仕組みが要ります。呼び出しに備える当番をオンコールと呼び、交代表を組んで回します。更新作業は、止めずに行うか、告知したうえで短い停止時間を取って行います。
- **覚え方**: 「24/365」と書き、機械は休まず人が交代すると覚えます。
- **まちがえやすい**: 無停止は、一度も止めないという意味ではありません。計画停止（あらかじめ知らせて止めるメンテナンス）は、むしろ健全な運用の一部です。
- **関連語**: [可用性](#g-intro-availability)、[冗長化](#g-intro-redundancy)、[構築と運用](#g-intro-build-and-operate)
- **確かめかた**: `uptime` で連続稼働時間を見ます。合わせて、監視の通知先と当番表がそろっているかを確認します。

<a id="g-intro-build-and-operate"></a>
## 構築と運用（コウチク・ウンヨウ）

- **一言**: 作って動くまでが構築、その後ずっと面倒を見続けるのが運用です。
- **たとえ**: 家を建てるのが構築、住みながら掃除と点検を続けるのが運用です。
- **くわしく**: 構築は設計、調達、設定、テストまでで、終わりがあります。運用は監視、バックアップ、更新、障害対応、問い合わせ対応と続き、終わりがありません。運用しやすさを見越して構築するのが、経験のある人の仕事です。
- **覚え方**: 建てる人と住む人、時間が長いのは住む側（運用）だと覚えます。
- **まちがえやすい**: 動いたから完了、ではありません。手順書と構成の記録を残さない構築は、あとの運用で必ず行き詰まります。
- **関連語**: [本番環境・検証環境・開発環境](#g-intro-environments)、[24 時間 365 日](#g-intro-24-365)、[インフラ](#g-intro-infrastructure)
- **確かめかた**: `crontab -l` で、定期実行の登録内容が一覧できます。運用の仕組みが仕込まれているかの手がかりになります。

<a id="g-intro-system-vs-service"></a>
## システムとサービスの違い（システム・サービスノチガイ）

- **一言**: 目的のために組んだ仕組み全体がシステム、受け手が得る価値がサービスです。
- **たとえ**: 鉄道です。線路と車両と信号の集まりがシステムで、乗客が受け取る「移動できること」がサービスです。
- **くわしく**: システムは作り手側から見た言い方、サービスは使い手側から見た言い方です。さらに Linux では、裏で待機し続ける個々のプログラム（デーモン）も「サービス」と呼びます。同じ言葉が 2 通りの意味で使われるので、会話ではどちらの話か確かめます。
- **覚え方**: 作りの話がシステム、届ける価値がサービス、と対で覚えます。
- **まちがえやすい**: 「サービスを止めます」と言われたら、業務全体を止めるのか、1 つのプログラムを止めるだけなのかを必ず聞き返します。
- **関連語**: [アプリケーション](#g-intro-application)、[エンドユーザー](#g-intro-end-user)、[可用性](#g-intro-availability)
- **確かめかた**: `systemctl list-units --type=service` で、その機械で動いているサービスの一覧が見えます。

<a id="g-intro-middleware"></a>
## ミドルウェア

- **一言**: OS とアプリの間に入り、共通して必要な役目を引き受けるソフトです。
- **たとえ**: 電源の延長タップです。壁のコンセント（OS）と家電（アプリ）の間に入り、どの家電でも使える形で電気を配ります。
- **くわしく**: Web サーバー、データベース、アプリケーションサーバー（アプリの処理を動かす土台）などが代表です。「通信を受ける」「データを保存する」といった、どのシステムでも要る機能を既製品として用意してくれます。設定ファイルを整えるのが、構築作業の中心になります。
- **覚え方**: middle は真ん中、OS の上でアプリの下に挟まる層だと覚えます。
- **まちがえやすい**: アプリの一部ではなく、入れ替えのきく土台です。OS の更新とは別に、ミドルウェア自身の更新も必要になります。
- **関連語**: [アプリケーション](#g-intro-application)、[サーバー機とサーバーソフトウェアの違い](#g-intro-server-machine-software)、[インフラ](#g-intro-infrastructure)
- **確かめかた**: `nginx -v` や `mysql --version` のように、版を表示するオプションで確認します（入っているものは環境によって異なります）。

<a id="g-intro-application"></a>
## アプリケーション

- **一言**: 利用者の目的を直接かなえる、業務そのものを行うソフトのことです。
- **たとえ**: レストランで出てくる料理そのものです。お客様が欲しいのは料理で、厨房の設備ではありません。
- **くわしく**: 予約サイト、在庫管理、スマホアプリなどが該当します。ミドルウェアの上で動き、その下には OS と機器があります。「アプリ」と略します。障害では、アプリ自身の不具合か下の土台の不調かを切り分けるのが最初の一歩です。
- **覚え方**: apply は「当てはめる」、目的に直接当てるソフトだと覚えます。
- **まちがえやすい**: アプリが重いから機械が非力、とは限りません。作りの問題であれば、機械を増やしても速くなりません。
- **関連語**: [ミドルウェア](#g-intro-middleware)、[バックエンドとフロントエンド](#g-intro-backend-frontend)、[エンドユーザー](#g-intro-end-user)
- **確かめかた**: `ps aux` で、動いているプログラムの一覧が見えます。ログの置き場所は環境によって異なるため、先に担当者へ確認します。

<a id="g-intro-backend-frontend"></a>
## バックエンドとフロントエンド（バックエンド・フロントエンド）

- **一言**: 利用者に見える表側がフロント、裏で処理する側がバックエンドです。
- **たとえ**: レストランの客席と厨房です。客席の飾り付けと、厨房の火加減は別の担当です。
- **くわしく**: フロントエンドはブラウザやスマホの中で動く画面まわり、バックエンドはサーバー側の処理とデータの保管です。サーバー担当が主に見るのは、バックエンド側と、その下の土台になります。
- **覚え方**: 見える側がフロント、見えない側がバックエンド、と対で覚えます。
- **まちがえやすい**: 画面の崩れはフロント側の問題であることが多く、サーバーを触っても直りません。まず、どちら側の問題かを切り分けます。
- **関連語**: [クライアント](#g-intro-client)、[アプリケーション](#g-intro-application)、[リクエストとレスポンス](#g-intro-request-response)
- **確かめかた**: ブラウザの開発者ツールで Network タブを開き、返事のステータスコードが正常かどうかを見ます。

<a id="g-intro-end-user"></a>
## エンドユーザー

- **一言**: 途中の作り手ではなく、最後に実際にそれを使う人のことです。
- **たとえ**: 料理を食べるお客様です。厨房の設備がいくら立派でも、まずければ意味がありません。
- **くわしく**: サーバーを動かす目的は、最終的にこの人たちの体験を守ることです。「CPU の数値は正常」でも、画面が開かないなら障害として扱います。停止のお知らせを届ける相手でもあります。
- **覚え方**: end は「終わり」、受け渡しの列の一番うしろに立つ人だと覚えます。
- **まちがえやすい**: エンドユーザーは社外のお客様とは限りません。社内システムなら同僚が、その仕組みを自分も業務で使うなら自分自身もエンドユーザーです。
- **関連語**: [クライアント](#g-intro-client)、[システムとサービスの違い](#g-intro-system-vs-service)、[可用性](#g-intro-availability)
- **確かめかた**: `curl -o /dev/null -s -w "%{time_total}\n" https://example.com` で、外から見た応答時間を秒数で確認できます。

<a id="g-intro-architecture-diagram"></a>
## システム構成図（システムコウセイズ）

- **一言**: どの機器がどうつながっているかを 1 枚の絵にした、現場の地図です。
- **たとえ**: 路線図です。駅名を一つずつ暗記しなくても、乗り換えの全体像は 1 枚で分かります。
- **くわしく**: 四角が機器、線が通信、矢印が向きを表すのが一般的です。障害のときはこの図に指を置き、上流から順に「ここまでは届いているか」を潰していきます。ネットワーク図やラック搭載図に分かれていることもあります。
- **覚え方**: 困ったら図に指を置く、と覚えます。
- **まちがえやすい**: 図は放っておくと古くなります。実機と食い違うときに正しいのは実機のほうなので、直したら図も必ず更新します。
- **関連語**: [ノード](#g-intro-node)、[インフラ](#g-intro-infrastructure)、[ホスト](#g-intro-host)
- **確かめかた**: `ip a` で自分の口とアドレス、`ip route` でどこへ出ていくかを見て、図と合っているか照らし合わせます。
