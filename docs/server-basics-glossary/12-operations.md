# 12. 運用・監視・障害対応

[用語集の入口](README.md) / [さくいん](index.md) / [前: セキュリティ](11-security.md) / [次: 構築プロジェクトと現場の言葉](13-project.md)

サーバーは作って終わりではなく、動き続けるのを見守る仕事がここから始まります。この章では、監視の種類から障害が起きたときの動き方まで、現場で毎日飛び交う言葉をまとめます。

> **この章で最初に押さえる 3 語**: 監視 ／ 障害切り分け ／ エスカレーション

<a id="g-ops-operation-maintenance"></a>
## 運用と保守（ウンヨウトホシュ）

- **一言**: 動かし続ける仕事が運用、壊れや古びを直す仕事が保守です。
- **たとえ**: マンションでいえば、毎日の見回りやゴミ出しが運用です。雨漏りの修理や古い設備の交換が保守にあたります。
- **くわしく**: 運用は監視、バックアップの確認、問い合わせ対応など、決まった作業を回し続けることです。保守は障害の修理や部品の交換、ソフトの更新など、状態を保つための手当てを指します。契約書では「運用保守」とひとまとめに書かれることも多く、どこまでが自分の担当かを最初に確かめます。
- **覚え方**: 「運用は回す、保守は直す」と動詞で覚えます。
- **まちがえやすい**: 構築が終われば楽になると思われがちですが、期間も費用も人手も運用側のほうが長く続きます。
- **関連語**: [監視](#g-ops-monitoring) ／ [定期メンテナンス](#g-ops-scheduled-maintenance) ／ [稼働報告](#g-ops-service-report)
- **確かめかた**: 契約書や作業一覧表を開き、自分の担当が「運用」の欄か「保守」の欄かを確認します。

<a id="g-ops-monitoring"></a>
## 監視（カンシ）

- **一言**: サーバーの状態を機械が自動で見張り、異常を人に知らせる仕組みです。
- **たとえ**: 家の火災報知器です。人が一日中天井を見上げていなくても、煙を感じたら鳴って教えてくれます。
- **くわしく**: 監視は「決めた項目を、決めた間隔で測り、決めた条件を外れたら知らせる」の三つでできています。人が画面を見ていられる時間は限られるので、夜中の異常に気づくには監視が要ります。何を見るかによって死活監視、リソース監視、ログ監視、外形監視などに分かれます。
- **覚え方**: 「測る・比べる・知らせる」の三拍子が監視です。
- **まちがえやすい**: 監視を入れれば障害が減ると思われがちですが、監視は気づくための道具で、壊れそのものを防ぐ働きはありません。
- **関連語**: [死活監視](#g-ops-alive-monitoring) ／ [閾値](#g-ops-threshold) ／ [アラートと通知](#g-ops-alert-notification)
- **確かめかた**: 監視ツールの対象一覧に、担当するサーバーが登録されているかを確認します。各サーバーに入れるエージェント（情報を送り続ける小さな常駐プログラム）方式なら、`systemctl is-active <サービス名>` で稼働も見ます。

<a id="g-ops-alive-monitoring"></a>
## 死活監視（シカツカンシ）

- **一言**: 相手が生きているかどうかだけを、定期的に確かめる監視です。
- **たとえ**: 一人暮らしの親に毎朝電話して、出るかどうかだけ確かめるようなものです。長い話はしません。
- **くわしく**: ping（相手に小さな信号を送って返事を見る確認）で応答があるかを調べます。決まったポート（サービスの受付窓口の番号）につながるかで判断する方法もあります。返事がなければダウンと判定し、通知を出します。一度の失敗で騒がないよう、たとえば三回続けて失敗したら異常とする、といった条件を付けます。
- **覚え方**: 「生きてる？」の一問だけ、が死活監視です。
- **まちがえやすい**: ping が返ることと、サービスが使えることは別です。OS は動いていても Web サーバーのプログラムが止まっている状態は、ping だけの死活監視では見つかりません。
- **関連語**: [外形監視](#g-ops-synthetic-monitoring) ／ [リソース監視](#g-ops-resource-monitoring) ／ [監視](#g-ops-monitoring)
- **確かめかた**: `ping -c 4 example.com` で応答を確認します。ポートを見るなら `ss -ltn` で待ち受けの一覧を出します。

<a id="g-ops-resource-monitoring"></a>
## リソース監視（リソースカンシ）

- **一言**: CPU やメモリ、ディスクの使われ具合を数値で見張る監視です。
- **たとえ**: 車の燃料計と水温計です。今は走れていても、針が上がり続けていれば止まる前に手を打てます。
- **くわしく**: CPU 使用率、メモリ使用量、ディスクの空き容量、ネットワークの流量などを一定間隔で記録します。時間の順に並べると増え方の傾向が見え、いつ足りなくなるかを予想できます。ディスクが満杯になるとログすら書けずサービスが止まるため、空き容量は特に大事な項目です。
- **覚え方**: 燃料計と同じで、「あとどれだけ余っているか」を数字で見ます。
- **まちがえやすい**: 瞬間の値だけを見て慌てがちですが、一時的な高負荷は珍しくありません。数分続いているかどうかで判断します。
- **関連語**: [閾値](#g-ops-threshold) ／ [メトリクス・ログ・トレース](#g-ops-metrics-logs-traces) ／ [監視](#g-ops-monitoring)
- **確かめかた**: `df -h` で空き容量、`free -h` でメモリ、`vmstat 1 5` や `uptime` で CPU と混み具合を見ます。

<a id="g-ops-load-average"></a>
## ロードアベレージ

- **一言**: 順番待ちをしている処理の数を平均した、混み具合を表す値です。
- **たとえ**: スーパーのレジに並んでいる人数の平均です。レジが何台あるかを知らないと、混んでいるかどうかは決められません。
- **くわしく**: `uptime` などで 1 分、5 分、15 分の三つの平均値が並んで出ます。この数字は、CPU の順番を待っている処理と、ディスクの読み書きを待っている処理の合計です。判断は CPU のコア数（同時に処理できる数）と比べて行い、4 コアで 4.0 なら、ちょうど使い切っている目安です。三つの数字を左から読み、増えている途中か落ち着いてきたかを見ます。
- **覚え方**: 「コア数と並べて初めて読める数字」と覚えます。
- **まちがえやすい**: CPU 使用率とは別の値です。使用率は 100 % が上限ですが、この値に上限はなく、待ちが増えれば 20 でも 50 でも上がります。
- **関連語**: [リソース監視](#g-ops-resource-monitoring) ／ [閾値](#g-ops-threshold) ／ [障害切り分け](#g-ops-troubleshooting-isolation)
- **確かめかた**: `uptime` で三つの平均値を、`nproc` で CPU のコア数を確認し、二つを見比べます。内訳は `vmstat 1 5` の待ち行列の欄で見ます。

<a id="g-ops-log-monitoring"></a>
## ログ監視（ログカンシ）

- **一言**: ログに出た特定の文字列を見つけて知らせる監視です。
- **たとえ**: 日記を毎晩めくって「痛い」「熱い」という言葉が出ていないか探す作業です。機械が代わりに読んでくれます。
- **くわしく**: error や failed といった語、あるいは特定の応答コード（HTTP 500 など）を条件にして、出たら通知します。数値で表せない異常、たとえば認証の失敗が急に増えた兆候をつかむのに向いています。ログは量が多いので、拾う条件を絞らないと通知だらけになります。
- **覚え方**: 数値で測れない異常は、言葉で探すのがログ監視です。
- **まちがえやすい**: error の語が入っていても、正常な処理の一部として毎日出ている行があります。件数や前後の行まで見てから騒ぐようにします。
- **関連語**: [syslog](#g-ops-syslog) ／ [誤検知と見逃し](#g-ops-false-positive-negative) ／ [監視](#g-ops-monitoring)
- **確かめかた**: `journalctl -p err -n 50` で直近のエラーを確認します。ファイルなら `grep -i error /var/log/syslog` のように探しますが、ログの置き場所は環境によって異なります。

<a id="g-ops-synthetic-monitoring"></a>
## 外形監視（ガイケイカンシ）

- **一言**: 利用者と同じ経路で外から実際に使ってみる監視です。
- **たとえ**: 店の外から客のふりをして入り、注文が通るか試す覆面調査です。厨房の中だけ見ていてもわかりません。
- **くわしく**: サーバーの外側にある監視地点から URL にアクセスし、応答コードや表示内容、応答時間を確かめます。途中の DNS（名前を住所に変える仕組み）や回線、証明書の期限切れなど、中からは見えない問題に気づけます。ログイン後の画面まで自動で操作して確かめる作り方もあります。
- **覚え方**: 「外の目で、客と同じ道を通る」から外形監視です。
- **まちがえやすい**: サーバーの中から自分自身に接続して確認しても外形監視にはなりません。外の経路を通らないと、途中の故障が見えないためです。
- **関連語**: [死活監視](#g-ops-alive-monitoring) ／ [影響範囲](#g-ops-impact-scope) ／ [監視](#g-ops-monitoring)
- **確かめかた**: 別のネットワークから `curl -o /dev/null -s -w "%{http_code} %{time_total}\n" https://example.com` を実行し、応答コードと所要時間を確認します。

<a id="g-ops-threshold"></a>
## 閾値（シキイチ）

- **一言**: ここを超えたら異常とみなす、あらかじめ決めた境目の値です。
- **たとえ**: 体温計で「何度から熱とみなすか」を先に決めておくのと同じです。線が引いてあるから、誰が見ても同じ判断になります。
- **くわしく**: 使用率がいくつで警告、いくつで重大、のように段階を分けるのが一般的で、適切な値は環境によって異なります。低すぎると通知が鳴りやまず、高すぎると気づいたときには手遅れです。運用しながら実際の値の動きを見て、少しずつ調整していきます。
- **覚え方**: 閾は敷居のこと、またぐと部屋が変わる境目です。
- **まちがえやすい**: 一度超えただけで通知すると雑音が増えます。「5 分続けて超えたら」のように、時間の条件も一緒に決めます。
- **関連語**: [リソース監視](#g-ops-resource-monitoring) ／ [アラートと通知](#g-ops-alert-notification) ／ [通知疲れ](#g-ops-alert-fatigue)
- **確かめかた**: 監視設定の画面を開き、項目ごとの警告値と重大値、判定に使う継続時間を一覧して確認します。

<a id="g-ops-alert-notification"></a>
## アラートと通知（アラートトツウチ）

- **一言**: 異常と判定するのがアラート、人に届ける手段が通知です。
- **たとえ**: 火災報知器が「火事だ」と判定するのがアラート、ベルが鳴って耳に届くのが通知です。
- **くわしく**: 監視が閾値を外れたと判定した状態がアラートで、メールやチャットなどで人に伝える動きが通知です。誰に、どの経路で、どの重さのものを送るかを決めておかないと、重大な異常が受信箱に埋もれます。夜間は電話、日中はチャットのように、時間帯で経路を変えることもあります。
- **覚え方**: 「判定するのがアラート、届けるのが通知」と役割で分けます。
- **まちがえやすい**: アラートが出ていることと、人が気づいていることは別です。通知先が退職者のアドレスのままだった、という事故は珍しくありません。
- **関連語**: [閾値](#g-ops-threshold) ／ [エスカレーション](#g-ops-escalation) ／ [通知疲れ](#g-ops-alert-fatigue)
- **確かめかた**: 監視ツールのアラート一覧と通知先の設定を開き、宛先が今の担当者になっているかを確認します。

<a id="g-ops-false-positive-negative"></a>
## 誤検知と見逃し（ゴケンチトミノガシ）

- **一言**: 異常でないのに鳴るのが誤検知、異常なのに鳴らないのが見逃しです。
- **たとえ**: 料理の湯気で火災報知器が鳴るのが誤検知、本当のぼやなのに鳴らないのが見逃しです。
- **くわしく**: 誤検知はフォールスポジティブ、見逃しはフォールスネガティブとも呼びます。判定を厳しくすると誤検知が増え、緩めると見逃しが増えるので、両方をゼロにはできません。どちらが困るかで決め、サービスが止まる項目は多少うるさくても厳しめにします。
- **覚え方**: 「鳴りすぎが誤検知、鳴らなすぎが見逃し」と鳴り方で覚えます。
- **まちがえやすい**: 誤検知が続くと通知そのものを止めたくなりますが、止めた項目で本番障害が起きるのが典型的な失敗です。止めるのではなく、条件のほうを直します。
- **関連語**: [閾値](#g-ops-threshold) ／ [通知疲れ](#g-ops-alert-fatigue) ／ [ログ監視](#g-ops-log-monitoring)
- **確かめかた**: 過去一か月のアラート履歴を開き、実際に手を動かす必要があった件数の割合を数えます。

<a id="g-ops-alert-fatigue"></a>
## 通知疲れ（ツウチヅカレ）

- **一言**: 通知が多すぎて、本当の異常にも反応できなくなる状態です。
- **たとえ**: 毎晩鳴る車の盗難ブザーです。近所の人はもう誰も窓の外を見ません。
- **くわしく**: アラート疲れとも呼びます。意味のない通知が一日に何十件も届くと、人は中身を読まずに消すようになります。件数を減らす、重さで経路を分ける、同じ原因の通知はまとめる、といった手入れを定期的に行います。通知は届けばよいものではなく、対応する人が動ける量に保つものです。
- **覚え方**: オオカミ少年と同じで、鳴らしすぎると誰も来てくれません。
- **まちがえやすい**: 通知が多いのは監視が丁寧な証拠だと思われがちですが、対応されない通知は無いのと同じです。
- **関連語**: [誤検知と見逃し](#g-ops-false-positive-negative) ／ [アラート抑止](#g-ops-alert-suppression) ／ [閾値](#g-ops-threshold)
- **確かめかた**: 直近一週間の通知件数と、そのうち実際に対応した件数を数えて比べます。

<a id="g-ops-alert-suppression"></a>
## アラート抑止（アラートヨクシ）

- **一言**: 予定作業や既知の障害の間だけ、通知を一時的に止める仕組みです。
- **たとえ**: 工事中の店に「本日休業」の札を出すようなものです。閉まっている理由がわかっていれば、客は驚きません。
- **くわしく**: メンテナンスモードやサイレンスとも呼ばれ、対象と期間を決めて通知だけを抑えます。停止作業のたびに大量のダウン通知が飛ぶと、本物の異常が埋もれてしまうためです。期間は必ず区切り、作業が延びたときは延長する運用にします。
- **覚え方**: 「消す」のではなく「期間を決めて黙らせる」のが抑止です。
- **まちがえやすい**: 抑止したまま解除を忘れると、その区間はまったく監視していないのと同じになります。解除の時刻も申請書に書いておきます。
- **関連語**: [定期メンテナンス](#g-ops-scheduled-maintenance) ／ [通知疲れ](#g-ops-alert-fatigue) ／ [変更管理と作業申請](#g-ops-change-management)
- **確かめかた**: 監視ツールのメンテナンス設定の一覧を開き、期限が切れているはずの抑止が残っていないかを確認します。

<a id="g-ops-escalation"></a>
## エスカレーション

- **一言**: 自分の手に負えない事象を、上位の担当者へ引き上げることです。
- **たとえ**: レストランで、新人が判断できない苦情を店長に引き渡すのと同じです。
- **くわしく**: 誰に、どの状態になったら、どの手段で上げるかを先に決めておきます。判断の基準は時間と影響で作るのが一般的です。決めた時間で復旧の見込みが立たない、または利用者が使えていない場合はすぐ上げる、といった形にします。迷った時間の分だけ復旧が遅れるので、早く上げるのは失敗ではありません。
- **覚え方**: エスカレーターと同じ語で、上の階へ運ぶ動きです。
- **まちがえやすい**: 自分で解決しないと評価が下がると考えて抱え込むのが、いちばんよくない失敗です。基準を超えたら機械的に上げます。
- **関連語**: [一次対応と二次対応](#g-ops-first-second-line) ／ [オンコールと当番](#g-ops-oncall) ／ [影響範囲](#g-ops-impact-scope)
- **確かめかた**: 連絡網（引き上げ先の一覧表）を開き、電話番号と時間帯ごとの担当が最新かを確認します。

<a id="g-ops-first-second-line"></a>
## 一次対応と二次対応（イチジタイオウトニジタイオウ）

- **一言**: 受けて止血するのが一次対応、原因まで踏み込むのが二次対応です。
- **たとえ**: 救急の現場で止血して運ぶのが一次対応、病院で検査して治すのが二次対応です。
- **くわしく**: 一次対応は通知を受け取り、状況を確認し、決められた手順で影響を抑えるところまでを担当します。二次対応は原因の調査、設定の変更、修正の適用など、専門的な作業を受け持ちます。一次でどこまで確認し、どの時点で二次へ渡すかを手順書に書いておくと、夜中でも判断に迷いません。
- **覚え方**: 「一次は止める人、二次は治す人」です。
- **まちがえやすい**: 一次対応の段階で原因を突き止めようと粘るのは順序が逆です。まず利用者が使える状態に戻すことを優先します。
- **関連語**: [エスカレーション](#g-ops-escalation) ／ [暫定対応と恒久対応](#g-ops-workaround-permanent-fix) ／ [手順書・ランブック](#g-ops-runbook)
- **確かめかた**: 手順書の「一次対応」の節を開き、自分ひとりの権限で実施できる作業だけになっているかを読みます。

<a id="g-ops-troubleshooting-isolation"></a>
## 障害切り分け（ショウガイキリワケ）

- **一言**: どこまでが正常で、どこから壊れているかを順に絞る作業です。
- **たとえ**: 家の電気が点かないとき、電球、スイッチ、ブレーカーと順に確かめていくのと同じです。
- **くわしく**: 利用者側、ネットワーク、サーバー、アプリ、データベースと経路を区切り、正常な範囲を一つずつ確定させます。片方が正常だと言い切れれば、疑う場所が半分に減ります。思いつきで設定を変えず、確認した事実を記録しながら進めるのが結局いちばん早い道です。
- **覚え方**: 「疑う場所を半分ずつ削る」のが切り分けです。
- **まちがえやすい**: 複数の設定を同時に変えると、どれが効いたのかわからなくなります。変更は一度に一つだけにします。
- **関連語**: [事象・原因・対処の分け方](#g-ops-symptom-cause-action) ／ [影響範囲](#g-ops-impact-scope) ／ [外形監視](#g-ops-synthetic-monitoring)
- **確かめかた**: `dig example.com`、`ping -c 4 example.com`、`curl -v https://example.com` を経路の順に実行し、どこまで応答が返るかを確かめます。サーバーの上では `ss -ltn` で待ち受けを見ます。

<a id="g-ops-symptom-cause-action"></a>
## 事象・原因・対処の分け方（ジショウ・ゲンイン・タイショノワケカタ）

- **一言**: 起きた事実、その理由、行った作業を混ぜずに書き分けることです。
- **たとえ**: 病院の記録と同じで、「熱が出た」「風邪だった」「薬を出した」を別々の欄に書きます。
- **くわしく**: 事象には観測できた事実だけを、時刻と数値付きで書きます。原因は調べてわかった理由で、確定していなければ「推定」と明記します。対処は自分が実際に行った操作です。三つを分けて書くと、後から読む人が判断をやり直せます。
- **覚え方**: 「何が起きた・なぜ・何をした」の三段で書きます。
- **まちがえやすい**: 「重かったので再起動しました」は三つが混ざった書き方です。事象は「応答に 30 秒かかった」のように数字で書きます。
- **関連語**: [インシデントと問題](#g-ops-incident-problem) ／ [障害切り分け](#g-ops-troubleshooting-isolation) ／ [エビデンス・証跡](#g-ops-evidence)
- **確かめかた**: 過去の障害報告書を開き、事象、原因、対処が別の段落に分かれているかを読み比べます。

<a id="g-ops-incident-problem"></a>
## インシデントと問題（インシデントトモンダイ）

- **一言**: 目の前で困っている出来事がインシデント、その根っこが問題です。
- **たとえ**: 雨漏りにバケツを置くのがインシデント対応、屋根の割れを直すのが問題対応です。
- **くわしく**: インシデントはサービスの中断や品質低下そのもので、目的は一刻も早く元に戻すことです。問題はインシデントを繰り返させている原因側で、目的は再発を止めることです。二つを別の管理表で追うと、今日戻す作業と来月直す作業が混ざりません。
- **覚え方**: インシデントは「今の困りごと」、問題は「繰り返す理由」です。
- **まちがえやすい**: インシデントが閉じたら終わりにしがちですが、原因が残っていれば同じ通知がまた鳴ります。
- **関連語**: [暫定対応と恒久対応](#g-ops-workaround-permanent-fix) ／ [ポストモーテム](#g-ops-postmortem) ／ [復旧](#g-ops-recovery)
- **確かめかた**: 課題管理表で、同じ内容のインシデントが何度立っているかを数えます。

<a id="g-ops-impact-scope"></a>
## 影響範囲（エイキョウハンイ）

- **一言**: 誰が、どの機能を、いつから使えないのかを示す範囲です。
- **たとえ**: 停電の連絡と同じです。「何丁目が」「何時から」がわからなければ、住民は動きようがありません。
- **くわしく**: 対象の利用者、止まっている機能、開始時刻、データの欠損の有無を最初に押さえます。ここが決まると、エスカレーションの緊急度も、利用者への案内文も自然に決まります。全面停止か一部の人だけかで、取るべき対応がまったく変わります。
- **覚え方**: 「誰が・何を・いつから」の三点セットです。
- **まちがえやすい**: 「サーバーが落ちました」だけでは影響範囲になりません。その結果として利用者が何をできないのかまで書きます。
- **関連語**: [インシデントと問題](#g-ops-incident-problem) ／ [エスカレーション](#g-ops-escalation) ／ [稼働報告](#g-ops-service-report)
- **確かめかた**: 外形監視の結果とアクセスログの件数を見比べ、実際に失敗している利用者の割合を確かめます。

<a id="g-ops-workaround-permanent-fix"></a>
## 暫定対応と恒久対応（ザンテイタイオウトコウキュウタイオウ）

- **一言**: 今すぐ止血するのが暫定対応、原因ごと直すのが恒久対応です。
- **たとえ**: パンクにスペアタイヤを付けるのが暫定、新しいタイヤに替えるのが恒久です。
- **くわしく**: 暫定対応はサービスを戻すことが目的で、再起動、不要ファイルの整理、故障した機器の切り離しなどが当たります。恒久対応は設定や設計、プログラムを直して同じ事象を起こさなくする作業です。暫定で終わらせないよう、実施した時点で恒久対応の課題を必ず起票します。
- **覚え方**: 「今日戻すのが暫定、二度と起こさないのが恒久」です。
- **まちがえやすい**: 暫定対応でサービスが戻ると直った気になりますが、スペアタイヤのまま高速道路に乗っている状態です。
- **関連語**: [インシデントと問題](#g-ops-incident-problem) ／ [復旧](#g-ops-recovery) ／ [変更管理と作業申請](#g-ops-change-management)
- **確かめかた**: 課題管理表で、暫定対応のまま残っている項目と、その期限を確認します。

<a id="g-ops-recovery"></a>
## 復旧（フッキュウ）

- **一言**: 利用者が元どおり使える状態に戻すこと、またはその時点です。
- **たとえ**: 通行止めの道路が開通した瞬間です。原因の調査はこれからでも、車はもう通れます。
- **くわしく**: 復旧の判定は担当者の感覚ではなく、決めた確認方法で行います。外形監視が正常に戻り、代表的な操作が成功し、エラーが止まったという条件をそろえて宣言します。復旧の時刻は稼働報告や利用者への案内に載るので、記録に残しておきます。
- **覚え方**: 「直った」ではなく「使える」に戻った時点が復旧です。
- **まちがえやすい**: プロセスが起動したことと復旧は違います。実際に利用者の操作が通るところまで確認します。
- **関連語**: [影響範囲](#g-ops-impact-scope) ／ [暫定対応と恒久対応](#g-ops-workaround-permanent-fix) ／ [外形監視](#g-ops-synthetic-monitoring)
- **確かめかた**: `curl -o /dev/null -s -w "%{http_code}\n" https://example.com` で、応答コードが正常な値に戻ったかを確認します。

<a id="g-ops-postmortem"></a>
## ポストモーテム

- **一言**: 障害のあとに、経緯と原因と再発防止をまとめる振り返りです。
- **たとえ**: 試合後のビデオ反省会です。負けた選手を責めるためではなく、次に勝つために見ます。
- **くわしく**: 時系列、影響範囲、原因、対処、うまくいった点、詰まった点を書き出します。大事なのは、人ではなく仕組みを対象にすることです。「誰が間違えたか」ではなく「なぜ間違えられる状態だったか」を書きます。出てきた改善は課題として起票し、担当と期限を付けて追いかけます。
- **覚え方**: 「責めない、隠さない、次に活かす」の会です。
- **まちがえやすい**: 反省文にしてしまうと、次から報告そのものが上がらなくなります。事実と改善策だけを書きます。
- **関連語**: [インシデントと問題](#g-ops-incident-problem) ／ [事象・原因・対処の分け方](#g-ops-symptom-cause-action) ／ [手順書・ランブック](#g-ops-runbook)
- **確かめかた**: 過去の振り返り資料を開き、改善項目に担当者と期限が入っているかを確認します。

<a id="g-ops-runbook"></a>
## 手順書・ランブック（シュジュンショ・ランブック）

- **一言**: 誰がやっても同じ結果になるよう、作業を順に書いた文書です。
- **たとえ**: 料理のレシピです。分量と手順が書いてあるから、作る人が変わっても同じ味になります。
- **くわしく**: 目的、事前確認、実行するコマンド、成功したときの見え方、失敗したときの戻し方を書きます。障害対応用のものはランブックとも呼ばれ、眠い頭でも読めるよう一本道にするのがこつです。使うたびに、詰まった箇所をその場で直していきます。
- **覚え方**: 「読んだとおりに打てば終わる」のが良い手順書です。
- **まちがえやすい**: 書いた本人しか読めない手順書が量産されがちです。初めての人に試してもらうと、抜けている前提がはっきりします。
- **関連語**: [一次対応と二次対応](#g-ops-first-second-line) ／ [定期メンテナンス](#g-ops-scheduled-maintenance) ／ [引き継ぎ・申し送り](#g-ops-handover)
- **確かめかた**: 手順書を開き、コマンドがそのまま貼れる形で書かれているか、戻し方の節があるかを確認します。

<a id="g-ops-scheduled-maintenance"></a>
## 定期メンテナンス（テイキメンテナンス）

- **一言**: 日を決めて計画的に行う、点検や更新のための作業です。
- **たとえ**: 車の車検です。壊れてから直すより、決めた日に見るほうが安く早く済みます。
- **くわしく**: 更新プログラムの適用、証明書の入れ替え、ログの整理、バックアップからの復元確認などを予定に組み込みます。サービスを止める場合は利用の少ない時間帯を選び、事前に利用者へ案内します。作業前に監視の抑止をかけ、終わったら解除するまでが一連の流れです。
- **覚え方**: 「壊れる前に、日を決めて触る」のが定期メンテナンスです。
- **まちがえやすい**: 作業予定を監視ツールに入れ忘れ、大量のダウン通知で当番を叩き起こしてしまう事故がよくあります。
- **関連語**: [アラート抑止](#g-ops-alert-suppression) ／ [変更管理と作業申請](#g-ops-change-management) ／ [手順書・ランブック](#g-ops-runbook)
- **確かめかた**: `systemctl list-timers` や `crontab -l` で、自動実行されている作業の予定を確認します。

<a id="g-ops-batch-job"></a>
## バッチ処理・ジョブ（バッチショリ・ジョブ）

- **一言**: 決めた時刻に、たまった仕事をまとめて自動で走らせる処理です。
- **たとえ**: 夜のうちに回す食洗機です。人が寝ている間に、ためた食器を一度に片づけてくれます。
- **くわしく**: 一日分の集計、データの取り込み、バックアップ、古いファイルの整理などが当たります。実行の一回分をジョブと呼び、cron や systemd のタイマーが時刻になったら起動します。利用者の少ない夜間に寄せることが多いため、朝いちばんに前夜の結果を確かめる運用になります。処理の成否は終了コード（プログラムが終わるときに返す番号）で判定し、失敗したら通知する作りにします。
- **覚え方**: 「ためて、まとめて、決めた時刻に」の三拍子です。
- **まちがえやすい**: 起動したことと成功したことは別です。「ジョブが落ちた」はその処理が途中で終わった意味で、サーバー自体が止まったわけではありません。
- **関連語**: [定期メンテナンス](#g-ops-scheduled-maintenance) ／ [ログ監視](#g-ops-log-monitoring) ／ [手順書・ランブック](#g-ops-runbook)
- **確かめかた**: `crontab -l` で登録された予定を見ます。前回の結果は `journalctl -u <サービス名> -n 50` や、処理が出しているログファイルの末尾で確認します。

<a id="g-ops-change-management"></a>
## 変更管理と作業申請（ヘンコウカンリトサギョウシンセイ）

- **一言**: 本番に触る前に、内容と手順を届け出て承認を得る決まりです。
- **たとえ**: マンションの共用部を工事する前に、管理組合へ申請して許可をもらうのと同じです。
- **くわしく**: 申請書には目的、作業日時、手順、影響範囲、戻し方、確認方法を書きます。承認が要るのは慎重さのためだけでなく、障害時に直前の変更をすぐ突き止めるためでもあります。緊急時の事後申請の型も決めておくと、夜間の対応が止まりません。
- **覚え方**: 申請書は、あとで自分を守るアリバイになります。
- **まちがえやすい**: 「設定を一行だけだから」と申請を飛ばした作業が、後の原因不明の障害になります。小さくても記録を残します。
- **関連語**: [リリースと切り戻し](#g-ops-release-rollback) ／ [定期メンテナンス](#g-ops-scheduled-maintenance) ／ [エビデンス・証跡](#g-ops-evidence)
- **確かめかた**: 変更管理表を開き、直近一週間に本番へ入った変更の一覧と承認者を確認します。

<a id="g-ops-release-rollback"></a>
## リリースと切り戻し（リリーストキリモドシ）

- **一言**: 新しい版を本番へ出すのがリリース、前の版へ戻すのが切り戻しです。
- **たとえ**: 新メニューを店に出すのがリリース、評判が悪くて前のメニューに戻すのが切り戻しです。
- **くわしく**: 切り戻しはロールバックとも呼びます。リリース計画には、いつまでに直らなければ戻すかという判断の時刻と、戻す手順をセットで書きます。データの形まで変わる変更は単純に戻せないことがあるため、戻せるかどうかを事前に確かめておきます。
- **覚え方**: 「出す前に、戻し方を書く」が鉄則です。
- **まちがえやすい**: 前のプログラムに入れ替えれば元通り、とは限りません。データベースの構造が変わっていると戻せない場合があります。
- **関連語**: [変更管理と作業申請](#g-ops-change-management) ／ [復旧](#g-ops-recovery) ／ [手順書・ランブック](#g-ops-runbook)
- **確かめかた**: リリース手順書に「切り戻し手順」と、戻すかどうかを決める時刻が書かれているかを確認します。

<a id="g-ops-deploy"></a>
## デプロイ

- **一言**: 作ったプログラムを本番のサーバーへ置いて、動く状態にする作業です。
- **たとえ**: 刷り上がった本を倉庫から書店の棚へ並べる作業です。刷るのと並べるのは別の日の仕事です。
- **くわしく**: 材料からプログラムの形を組み立てるのがビルドで、その成果物をサーバーへ運んで入れ替えるのがデプロイです。ファイルの配置、設定の反映、プログラムの入れ替え、動作確認までがひと続きの流れになります。デプロイした版を利用者へ出すと決めるところまで含めた全体がリリースで、置いた時点と出す時点をずらす進め方もあります。「今日はデプロイ」と言われたら、この置き換えの作業をする日だと考えます。
- **覚え方**: 「作るのがビルド、置くのがデプロイ、出すのがリリース」と並べて覚えます。
- **まちがえやすい**: 作業が終わったことと、利用者に新しい版が見えていることは別です。古い版が残る場所や、途中の機器が持つ保存済みの内容が原因で、見え方が変わらないことがあります。
- **関連語**: [リリースと切り戻し](#g-ops-release-rollback) ／ [変更管理と作業申請](#g-ops-change-management) ／ 構築・ビルド
- **確かめかた**: 配置先のディレクトリで `ls -l` を実行し、更新日時が今回の作業時刻になっているかを見ます。`systemctl status <サービス名>` で入れ替え後の起動時刻も確認します。

<a id="g-ops-handover"></a>
## 引き継ぎ・申し送り（ヒキツギ・モウシオクリ）

- **一言**: 交代する相手に、進行中の状況と次の一手を渡すことです。
- **たとえ**: 病院で夜勤に交代するときの申し送りです。患者の名前だけでなく、今の状態と次の処置を伝えます。
- **くわしく**: 未解決の事象、実施済みの対処、次にやること、連絡済みの相手、注意点を短く書きます。口頭だけでなくチャットやシートに文字で残すと、三人目に伝わるときも内容が変わりません。「何もありませんでした」も立派な申し送りです。
- **覚え方**: 「終わったこと」より「途中のこと」を渡します。
- **まちがえやすい**: やった対処だけを伝えて、まだ確認していないことを伝え忘れがちです。未確認の項目こそ書きます。
- **関連語**: [オンコールと当番](#g-ops-oncall) ／ [一次対応と二次対応](#g-ops-first-second-line) ／ [稼働報告](#g-ops-service-report)
- **確かめかた**: 当番の交代記録を開き、未解決事項の欄が空欄のまま流れていないかを確認します。

<a id="g-ops-oncall"></a>
## オンコールと当番（オンコールトトウバン）

- **一言**: 決めた時間帯に、呼び出しへ応じる担当を置く体制です。
- **たとえ**: 休日診療の当番医と同じです。全員が起きている必要はなく、その日の当番だけが電話を持ちます。
- **くわしく**: 誰がいつ担当かを表にし、電話が通じる状態と一次対応の手順書がそろって初めて成り立ちます。応答時間の目安、つながらないときの次の連絡先、代わってもらうときの決まりも先に決めます。持ち回りにして、負担が特定の人に偏らないようにします。
- **覚え方**: 「その日は電話を手放さない人」が当番です。
- **まちがえやすい**: 当番であることと、その人が全部直せることは別です。当番の役目は受けて動かすことで、必要ならすぐ引き上げます。
- **関連語**: [エスカレーション](#g-ops-escalation) ／ [引き継ぎ・申し送り](#g-ops-handover) ／ [アラートと通知](#g-ops-alert-notification)
- **確かめかた**: 当番表と通知先の設定を並べ、今日の当番に通知が届く設定になっているかを確認します。

<a id="g-ops-service-report"></a>
## 稼働報告（カドウホウコク）

- **一言**: 一定期間のサービスの状態と対応内容をまとめて示す報告です。
- **たとえ**: 毎月届く電気使用量のお知らせです。数字が並ぶから、増えているのか減っているのかがわかります。
- **くわしく**: 稼働率（決めた期間のうち正常に使えていた時間の割合）、障害の件数と内容、通知の傾向、リソースの推移などを載せます。読み手は技術者とは限らないので、専門用語には一言の説明を添えます。毎回同じ形で出すと、変化があったときに気づきやすくなります。
- **覚え方**: サービスの通信簿を、決まった形で毎回渡すのが稼働報告です。
- **まちがえやすい**: 障害の無かった月を「特になし」で終わらせがちですが、傾向の数字を載せてこそ次の予兆が見えます。
- **関連語**: [運用と保守](#g-ops-operation-maintenance) ／ [メトリクス・ログ・トレース](#g-ops-metrics-logs-traces) ／ SLA・SLO・SLI
- **確かめかた**: 監視ツールのレポート機能で、対象期間の稼働率とアラート件数を出力します。

<a id="g-ops-observability"></a>
## 可観測性・オブザーバビリティ（カカンソクセイ・オブザーバビリティ）

- **一言**: 外に出ている情報だけで、中で何が起きたか説明できる度合いです。
- **たとえ**: 車の運転席です。速度計も警告灯も無ければ、エンジンを開けるまで不調がわかりません。
- **くわしく**: 監視が「決めた異常に気づく」ことなら、可観測性は「予想していなかった不調も後から追える」ことを目指します。そのために、数値、出来事の記録、処理の道筋という三種類の情報をあらかじめ出しておきます。作った後から足すのは手間がかかるので、構築の段階で何を出すかを決めます。
- **覚え方**: 監視は「気づく力」、可観測性は「説明できる力」です。
- **まちがえやすい**: ツールを入れれば可観測性が上がると思われがちですが、アプリ側が情報を出していなければ何も見えません。
- **関連語**: [メトリクス・ログ・トレース](#g-ops-metrics-logs-traces) ／ [監視](#g-ops-monitoring) ／ [Prometheus と Grafana](#g-ops-prometheus-grafana)
- **確かめかた**: 遅かった処理を一つ選び、今ある画面とログだけで原因を説明できるかを試してみます。

<a id="g-ops-metrics-logs-traces"></a>
## メトリクス・ログ・トレース

- **一言**: 数値の記録、出来事の記録、処理の道筋の記録という三種類です。
- **たとえ**: 宅配便でいえば、日ごとの取扱個数の集計がメトリクス、いつ何があったかの伝票の控えがログ、荷物一個が通った営業所の順路がトレースです。
- **くわしく**: メトリクスは CPU 使用率のように時間ごとの数値で、傾向を見るのに向きます。ログは一件ごとの出来事の記録で、いつ何が起きたかを追えます。トレースは一つの要求がどのサーバーのどの処理を通ったかをつなげた記録で、どこで時間がかかったかを探せます。
- **覚え方**: 「数値・出来事・道筋」の三つ、と順番で覚えます。
- **まちがえやすい**: ログをたくさん取れば足りると考えがちですが、複数のサーバーをまたぐ遅さはトレースがないと追い切れません。
- **関連語**: [可観測性・オブザーバビリティ](#g-ops-observability) ／ [リソース監視](#g-ops-resource-monitoring) ／ [ログ監視](#g-ops-log-monitoring)
- **確かめかた**: `vmstat 1 5` で数値の記録、`journalctl -n 20` で出来事の記録を並べて見比べます。

<a id="g-ops-prometheus-grafana"></a>
## Prometheus と Grafana（プロメテウスとグラファナ）

- **一言**: 数値を集めて貯めるのが Prometheus、絵にするのが Grafana です。
- **たとえ**: 毎日の体重を書き留めるノートが Prometheus、それを折れ線グラフに描く方眼紙が Grafana です。
- **くわしく**: Prometheus は監視対象が公開している数値を定期的に取りに行き、時刻付きの数値の並びとして保存します。条件式でアラートを判定する機能も持ちますが、通知の振り分けは Alertmanager という別の道具が担うのが一般的です。Grafana は保存された数値を画面に並べる道具です。Prometheus 以外の保存先の数値も、同じ画面に表示できます。
- **覚え方**: 「集めるプロメテウス、見せるグラファナ」と役割で覚えます。
- **まちがえやすい**: Grafana に絵が出ているからといって、Grafana が数値を集めているわけではありません。集めているのは Prometheus の側です。
- **関連語**: [メトリクス・ログ・トレース](#g-ops-metrics-logs-traces) ／ [可観測性・オブザーバビリティ](#g-ops-observability) ／ [閾値](#g-ops-threshold)
- **確かめかた**: `curl -s http://localhost:9090/-/healthy` で Prometheus の生存を確認します。ポート番号は環境によって異なります。

<a id="g-ops-zabbix"></a>
## Zabbix（ザビックス）

- **一言**: 監視から通知、画面表示までを一つで担うオープンソースの監視ソフトです。
- **たとえ**: ビルの防災センターです。各階のセンサーの情報が一か所に集まり、担当者はそこだけ見ていれば済みます。
- **くわしく**: 集約役のサーバー、各機器に入れるエージェント（情報を送る常駐プログラム）、データベース、表示画面の組み合わせで動きます。死活、リソース、ログ、外形といった監視を一つの設定画面でまとめて管理できます。通知先や条件も同じ場所で決められ、SNMP を使えばエージェントを入れられない機器も扱えます。
- **覚え方**: 「一つの司令室で、集める・判定する・知らせるまで済ませる」型です。
- **まちがえやすい**: エージェントを入れれば自動で全部見てくれるわけではありません。何を監視するかは、設定して初めて有効になります。
- **関連語**: [監視](#g-ops-monitoring) ／ [SNMP](#g-ops-snmp) ／ [閾値](#g-ops-threshold)
- **確かめかた**: `systemctl status zabbix-agent` でエージェントの稼働を確認します。サービス名は版や環境によって異なります。

<a id="g-ops-snmp"></a>
## SNMP（エス・エヌ・エム・ピー）

- **一言**: 機器の状態を共通の形式でやり取りする、監視用の約束事です。
- **たとえ**: 全国共通の健康診断票です。書式が同じだから、どこのメーカーの機械でも同じ欄を読めます。
- **くわしく**: ルーターやスイッチ、プリンタなど、監視ソフト専用のプログラムを入れにくい機器でよく使います。監視側から値を問い合わせる形と、機器側から異常を送りつける形（トラップ）があります。バージョン 2c まではコミュニティ名（合言葉のような文字列）だけで読め、通信も暗号化されません。バージョン 3 では利用者ごとの認証と暗号化が使えます。
- **覚え方**: Simple Network Management Protocol の頭文字、網の中の機器を管理する共通語です。
- **まちがえやすい**: コミュニティ名を初期値のまま外向きに開けると、機器の情報を第三者に読まれます。参照元のアドレスを絞ります。
- **関連語**: [監視](#g-ops-monitoring) ／ [Zabbix](#g-ops-zabbix) ／ [死活監視](#g-ops-alive-monitoring)
- **確かめかた**: `snmpwalk -v 2c -c <コミュニティ名> <機器のアドレス> system` で、機器の基本情報を読み出します。読み取りだけの操作です。

<a id="g-ops-syslog"></a>
## syslog（シスログ）

- **一言**: OS や機器のログを共通の形式で受け渡す、標準的な仕組みです。
- **たとえ**: 社内の連絡票です。どの部署も同じ用紙に書くから、総務が一か所でまとめて綴じられます。
- **くわしく**: 日時、発信元、種別、重要度（レベル）、本文といった決まった形でログを扱います。同じサーバー内に書くことも、ネットワーク越しに集約用のサーバーへ送ることもできます。集約しておけば、障害でそのサーバーに入れなくなってもログが残ります。今の Linux では systemd-journald や rsyslog が受け口を担うことが多いです。
- **覚え方**: 「ログの共通用紙と配送便」が syslog です。
- **まちがえやすい**: ログを手元にだけ置くと、ディスク障害や不正な侵入で消えることがあります。重要なログは別のサーバーへも送ります。
- **関連語**: [ログ監視](#g-ops-log-monitoring) ／ [エビデンス・証跡](#g-ops-evidence) ／ [メトリクス・ログ・トレース](#g-ops-metrics-logs-traces)
- **確かめかた**: `journalctl -n 20` で直近のログを、`ls -l /var/log/` で保存先の一覧を確認します。

<a id="g-ops-evidence"></a>
## エビデンス・証跡（エビデンス・ショウセキ）

- **一言**: 作業や状態を証明するために残す、記録や画面の控えです。
- **たとえ**: 買い物のレシートです。「払った」と言うだけでなく、紙が残っているから後から確かめられます。
- **くわしく**: 作業前後のコマンドの実行結果、設定ファイルの差分、画面の写しなどを、日時がわかる形で保存します。目的は自分を守ることと、次に同じ作業をする人が状況を再現できるようにすることです。監査や報告で求められることも多いので、保存場所と保管期間を先に決めておきます。
- **覚え方**: 「言った」ではなく「残っている」ことが証跡です。
- **まちがえやすい**: 作業後の結果だけを残しても、変わったことの証明にはなりません。作業前の状態もそろえて残します。
- **関連語**: [変更管理と作業申請](#g-ops-change-management) ／ [事象・原因・対処の分け方](#g-ops-symptom-cause-action) ／ [syslog](#g-ops-syslog)
- **確かめかた**: `date` を先に実行し、続けて確認コマンドの結果を画面ごと保存します。`script` コマンドで端末のやり取りをファイルに残す方法もあります。
