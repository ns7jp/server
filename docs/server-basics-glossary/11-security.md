# 11. セキュリティ

[用語集の入口](README.md) / [さくいん](index.md) / [前: 可用性・性能・設計の考え方](10-availability.md) / [次: 運用・監視・障害対応](12-operations.md)

セキュリティは専門部署だけの仕事ではなく、サーバーを触る人全員の日常業務です。この章では「何を守るのか」と「どう守るのか」を、現場でも面接でも同じ言葉で言えるように整理します。

> **この章で最初に押さえる 3 語**: 認証と認可 ／ 最小権限の原則 ／ パッチ適用

<a id="g-sec-cia"></a>
## 情報セキュリティの 3 要素（ジョウホウセキュリティノサンヨウソ）

- **一言**: 守る中身を機密性・完全性・可用性の 3 つに分けて考える物差しです。
- **たとえ**: 銀行の貸金庫と同じです。他人に中を見せない（機密性）、預けた物がすり替わらない（完全性）、開けたいときに開けられる（可用性）の 3 点で考えます。
- **くわしく**: セキュリティの目的は「とにかく固くする」ことではありません。どの要素をどこまで守るかを決めるための基準です。英語の頭文字から CIA と呼ぶこともあります。たとえば通信を全部止めれば機密性は上がりますが、可用性は下がります。
- **覚え方**: 「見せない・変えさせない・止めない」の 3 点セットと覚えます。
- **まちがえやすい**: 可用性を忘れがちです。安全のためにサービスを止める判断も、1 つの要素を犠牲にしていると自覚して行います。
- **関連語**: [認証と認可](#g-sec-authn-authz)、[アクセスログと監査ログ](#g-sec-access-audit-log)、冗長化
- **確かめかた**: 自分の職場のセキュリティポリシー文書で、この 3 語がどう定義されているかを探します。コマンドではなく文書で確認する用語です。

<a id="g-sec-authn-authz"></a>
## 認証と認可（ニンショウ／ニンカ）

- **一言**: 認証は「誰か」を確かめ、認可は「何をしてよいか」を決めます。
- **たとえ**: マンションの入口で顔と鍵を確認するのが認証です。その人が開けられるのは自分の部屋だけと決まっているのが認可です。
- **くわしく**: ログイン画面でパスワードや鍵を照合するのが認証です。ログインできた後に、そのユーザーがどのファイルを読めるかを決めるのが認可です。英語では認証を Authentication、認可を Authorization と書き分けます。原則として認証が先で、本人を確かめてから認可の判断に進みます。
- **覚え方**: 「証」は本人のあかし、「可」はしてよいというゆるし、と漢字で覚えます。
- **まちがえやすい**: ログインできた＝何でもできる、ではありません。認証を通っても認可がなければ操作は拒否されます。
- **関連語**: [最小権限の原則](#g-sec-least-privilege)、[多要素認証](#g-sec-mfa)、[特権 ID](#g-sec-privileged-id)
- **確かめかた**: Linux なら `id` で自分の所属グループを、`ls -l` でファイルごとの許可を確認できます。

<a id="g-sec-password-policy"></a>
## パスワードポリシー

- **一言**: 使ってよいパスワードの条件や運用の決まりをまとめた組織のルールです。
- **たとえ**: 玄関の鍵についての家族の決めごとと同じです。「簡単に複製できる鍵は使わない」「合鍵は何本まで」を先に決めておきます。
- **くわしく**: 文字数、使う文字の種類、使い回しの禁止、変更の間隔などを定めます。近ごろは、定期的な変更を強いるより、長くて推測されにくい文字列と多要素認証を組み合わせる考え方が広がっています。具体的な条件は組織や環境によって異なります。
- **覚え方**: 「長さは正義、使い回しは罪」と覚えます。
- **まちがえやすい**: 記号を混ぜることより、長さを伸ばすほうが効きます。複雑にしすぎて付箋に書かれたら、かえって危険です。
- **関連語**: [多要素認証](#g-sec-mfa)、[アカウント管理と棚卸し](#g-sec-account-review)、[秘密情報の扱い](#g-sec-credentials)
- **確かめかた**: Linux なら `chage -l ユーザー名` で有効期限を、`cat /etc/login.defs` で既定値を確認できます。文字数などの条件をどこに書くかは環境によって異なります。

<a id="g-sec-mfa"></a>
## 多要素認証／MFA（タヨウソニンショウ／エム・エフ・エー）

- **一言**: パスワードに加えて、別の種類の証明も要求する仕組みです。
- **たとえ**: 銀行の ATM と同じです。カード（持ち物）と暗証番号（記憶）の 2 つがそろって、はじめてお金が出ます。
- **くわしく**: 要素は「知っているもの」「持っているもの」「体の特徴」の 3 種類です。スマホアプリのワンタイムコードやハードウェアキーは「持っているもの」にあたります。パスワードが漏れても、もう 1 つの要素がなければ入れないため、被害を手前で止められます。
- **覚え方**: 「知識・所持・生体」から 2 種類以上、と覚えます。
- **まちがえやすい**: 手順が 2 段階でも、パスワードと秘密の質問のように「知っているもの」だけなら多要素ではありません。要素の数ではなく、種類の数を数えます。
- **関連語**: [認証と認可](#g-sec-authn-authz)、[パスワードポリシー](#g-sec-password-policy)、[ソーシャルエンジニアリング](#g-sec-social-engineering)
- **確かめかた**: 各サービスの管理画面で、自分と管理者アカウントの MFA が有効になっているかを確認します。

<a id="g-sec-account-review"></a>
## アカウント管理と棚卸し（アカウントカンリ／タナオロシ）

- **一言**: 誰のアカウントがなぜ存在するかを台帳で管理し、定期的に見直すことです。
- **たとえ**: 会社の入館証の管理と同じです。退職者の証を回収しないと、辞めた人がいつまでも建物に入れてしまいます。
- **くわしく**: 入社・異動・退職に合わせて、アカウントを作り、権限を変え、消していきます。棚卸しは、台帳と実際のサーバー上のアカウントを突き合わせ、差分を洗い出す点検です。使われていないアカウントは、気づかれにくいので攻撃者に狙われます。
- **覚え方**: 「作るときより、消すときが大事」と覚えます。
- **まちがえやすい**: 退職者のアカウントを止めただけで終わりにしがちです。その人が知っている共有パスワードや鍵も、あわせて変えないと意味がありません。
- **関連語**: [最小権限の原則](#g-sec-least-privilege)、[特権 ID](#g-sec-privileged-id)、[アクセスログと監査ログ](#g-sec-access-audit-log)
- **確かめかた**: Linux なら `getent passwd` で（外部の認証サービス経由も含めて）アカウントを、`last` や `lastlog` で最終ログインを一覧できます。使えるコマンドは環境によって異なります。

<a id="g-sec-least-privilege"></a>
## 最小権限の原則（サイショウケンゲンノゲンソク）

- **一言**: 仕事に必要な最低限の権限だけを、必要な人にだけ与える考え方です。
- **たとえ**: ホテルのカードキーと同じです。清掃係には客室の鍵を渡しますが、金庫室の鍵は渡しません。
- **くわしく**: 権限を広く配ると、うっかり操作の影響も、乗っ取られたときの被害も、そのまま広がります。まず何もできない状態から始め、必要になった分だけ足していくのが基本です。一時的に付けた権限は、期限を決めて必ず外します。
- **覚え方**: 「最初は渡さない、困ったら足す」と覚えます。
- **まちがえやすい**: 面倒だからと全員に管理者権限を配ると、後から絞るのは非常に大変です。広げるのは一瞬、狭めるのは調整の連続です。
- **関連語**: [特権 ID](#g-sec-privileged-id)、[認証と認可](#g-sec-authn-authz)、[SELinux と AppArmor](#g-sec-selinux-apparmor)
- **確かめかた**: `sudo -l` で、自分が管理者として実行できるコマンドの範囲を確認できます。

<a id="g-sec-privileged-id"></a>
## 特権 ID（トッケンアイディー）

- **一言**: サーバーの設定を何でも変えられる、強い権限を持つアカウントです。
- **たとえ**: マンションのマスターキーです。全部屋を開けられるので、貸出簿を付けて金庫で保管します。
- **くわしく**: Linux の root、Windows の Administrator、クラウドの管理者アカウントなどが該当します。ふだんは一般ユーザーで作業し、必要なときだけ `sudo` などで一時的に権限を借りるのが基本の使い方です。誰がいつ何のために使ったかを、記録に残せる形にしておきます。
- **覚え方**: 「マスターキーは貸出簿とセット」と覚えます。
- **まちがえやすい**: 特権 ID を複数人で共有すると、ログを見ても誰の操作か分かりません。個人のアカウントから昇格する形にします。
- **関連語**: [最小権限の原則](#g-sec-least-privilege)、[アカウント管理と棚卸し](#g-sec-account-review)、[アクセスログと監査ログ](#g-sec-access-audit-log)
- **確かめかた**: `id -u` の結果が 0 なら root です。`getent group wheel` や `getent group sudo` で管理者グループの所属者を確認できます。

<a id="g-sec-symmetric-asymmetric"></a>
## 共通鍵暗号と公開鍵暗号（キョウツウカギアンゴウ／コウカイカギアンゴウ）

- **一言**: 同じ鍵で開け閉めするか、対になる 2 つの鍵を使い分けるかの違いです。
- **たとえ**: 共通鍵は自宅の玄関の鍵で、施錠も解錠も同じ鍵です。公開鍵は郵便ポストで、投函口は誰でも使えますが、取り出せるのは鍵を持つ本人だけです。
- **くわしく**: 共通鍵暗号は処理が速く、大量のデータを暗号化するのに向きます。公開鍵暗号は処理が重い代わりに、事前に秘密の鍵を手渡ししなくても安全に通信を始められます。TLS では、接続のはじめに公開鍵の技術を使って共通鍵を安全に決め、そのあとの本文は共通鍵で速く暗号化します。
- **覚え方**: 「速いが渡すのが難しい共通鍵、遅いが渡しやすい公開鍵」と覚えます。
- **まちがえやすい**: 公開鍵と秘密鍵を取り違えがちです。人に配ってよいのが公開鍵、絶対に外に出さないのが秘密鍵です。
- **関連語**: [ハッシュ](#g-sec-hash)、[サーバー証明書](#g-sec-server-certificate)、[TLS と SSL](#g-sec-tls-ssl)
- **確かめかた**: `ls -l ~/.ssh` で、公開鍵（末尾が `.pub`）と秘密鍵が別のファイルになっていることを確認できます。

<a id="g-sec-hash"></a>
## ハッシュ

- **一言**: 元に戻せない形で、データを決まった長さの短い値に変換する計算です。
- **たとえ**: 材料をミキサーにかけるようなものです。同じ材料なら必ず同じ見た目になりますが、そこから元の材料には戻せません。
- **くわしく**: パスワードはそのまま保存せず、ハッシュにした値を保存します。ログイン時は入力された文字列を同じ方法でハッシュ化し、保存済みの値と一致するかを比べます。パスワード用には、利用者ごとに違う文字列（ソルト）を混ぜる、パスワード専用の方式を使います。元のデータが 1 文字違うだけで結果はまったく別の値になるので、ファイルの改ざんや破損の確認にも使えます。
- **覚え方**: 「ミキサーは回せても、逆回しはできない」と一方通行で覚えます。
- **まちがえやすい**: ハッシュは暗号化ではありません。暗号化は鍵があれば元に戻せますが、ハッシュは鍵があっても戻せません。
- **関連語**: [共通鍵暗号と公開鍵暗号](#g-sec-symmetric-asymmetric)、[パスワードポリシー](#g-sec-password-policy)、[サーバー証明書](#g-sec-server-certificate)
- **確かめかた**: `sha256sum ファイル名` で値を計算し、配布元が公開している値と見比べます。

<a id="g-sec-server-certificate"></a>
## サーバー証明書（サーバーショウメイショ）

- **一言**: このサーバーが名乗るドメインの持ち主だと第三者が保証する電子ファイルです。
- **たとえ**: 運転免許証と同じです。自作のカードは信用されませんが、役所が発行したものなら信用されます。
- **くわしく**: 証明書には、ドメイン名、公開鍵、有効期限、発行者の署名が入っています。ブラウザは接続先から証明書を受け取り、発行者の署名と有効期限を確かめて、相手が名乗るドメインの持ち主かを判断します。有効期限が切れると利用者に警告が出るので、更新の管理そのものが運用の仕事になります。
- **覚え方**: 「鍵に名札を付けて、第三者にハンコをもらったもの」と覚えます。
- **まちがえやすい**: 証明書がある＝安全なサイト、ではありません。証明しているのはドメインの持ち主であって、運営者の善良さではありません。
- **関連語**: [認証局](#g-sec-ca)、[TLS と SSL](#g-sec-tls-ssl)、[共通鍵暗号と公開鍵暗号](#g-sec-symmetric-asymmetric)
- **確かめかた**: ブラウザのアドレスバーの鍵アイコンから中身を見られます。コマンドなら `openssl s_client -connect example.com:443 -servername example.com` で受け取った証明書を表示できます。

<a id="g-sec-ca"></a>
## 認証局／CA（ニンショウキョク／シー・エー）

- **一言**: 申請者の身元を確かめて証明書を発行する、信頼の元締めの組織です。
- **たとえ**: パスポートを発行する役所です。役所そのものが信用されているから、そこが出した書類も信用されます。
- **くわしく**: OS やブラウザには、あらかじめ信頼する認証局の一覧が組み込まれています。その一覧にある認証局が署名した証明書だけが、警告なしで受け入れられます。社内専用の認証局（プライベート CA）を立てることもありますが、その場合は各端末に「この認証局を信頼する」設定を配る必要があります。
- **覚え方**: 「証明書はパスポート、CA は発行する役所」と覚えます。
- **まちがえやすい**: 自分で作った証明書（自己署名証明書）は、CA の保証がないため警告が出ます。検証用と本番用は分けて考えます。
- **関連語**: [サーバー証明書](#g-sec-server-certificate)、[TLS と SSL](#g-sec-tls-ssl)、[ハッシュ](#g-sec-hash)
- **確かめかた**: Linux では `ls /etc/ssl/certs` で信頼済み証明書の置き場を確認できます。場所は環境によって異なります。

<a id="g-sec-tls-ssl"></a>
## TLS と SSL（ティー・エル・エス／エス・エス・エル）

- **一言**: 通信を暗号化する仕組みで、SSL は古い名前、TLS が今の名前です。
- **たとえ**: 店の名前が変わっても、常連が昔の屋号で呼び続けるようなものです。中身は新しい TLS ですが、看板だけ SSL の名前で残っています。
- **くわしく**: SSL は 1990 年代に広まった規格で、その後継として TLS に引き継がれました。今の HTTPS 通信は実際には TLS で守られていますが、現場では「SSL 証明書」「SSL 化」という言い方が残っています。古いバージョンには弱点が見つかっているため、新しいバージョンだけを許可する設定が一般的です。
- **覚え方**: 「SSL は旧姓、TLS が現姓」と覚えます。
- **まちがえやすい**: 「SSL 証明書」と呼んでいても、中身は TLS で使うものです。呼び名が違うだけで別物ではありません。
- **関連語**: [サーバー証明書](#g-sec-server-certificate)、[通信の暗号化と保存データの暗号化](#g-sec-encryption-transit-rest)、[認証局](#g-sec-ca)
- **確かめかた**: `curl -v https://example.com` の出力に、どのバージョンで接続したかが表示されます。

<a id="g-sec-encryption-transit-rest"></a>
## 通信の暗号化と保存データの暗号化（ツウシンノアンゴウカ／ホゾンデータノアンゴウカ）

- **一言**: 運んでいる途中を守るか、置いてある間を守るかの違いです。
- **たとえ**: 現金輸送車で運ぶのが通信の暗号化、金庫にしまうのが保存データの暗号化です。守る場面がまったく違います。
- **くわしく**: 通信の暗号化は、ネットワークの途中で盗み見られないようにします。TLS がその代表です。保存データの暗号化は、ディスクやバックアップ媒体を持ち出されても中身を読ませないようにします。英語では前者を in transit、後者を at rest と呼び、両方そろって初めて一続きで守れます。
- **覚え方**: 「移動中（transit）と置きっぱなし（rest）」と英語で覚えます。
- **まちがえやすい**: HTTPS だからデータベースの中身も暗号化されている、ということはありません。それぞれ別に設定します。
- **関連語**: [TLS と SSL](#g-sec-tls-ssl)、[共通鍵暗号と公開鍵暗号](#g-sec-symmetric-asymmetric)、バックアップ
- **確かめかた**: Linux では `lsblk -f` で、暗号化されたボリューム（`crypto_LUKS` と表示）があるかを確認できます。

<a id="g-sec-firewall"></a>
## ファイアウォール

- **一言**: 通信を通すか止めるかを、ルールにしたがって判断する門番です。
- **たとえ**: ビルの受付です。「何階の誰に会いに来たか」を聞き、リストにない人は中に入れません。
- **くわしく**: 送信元、宛先、ポート番号などの条件を並べ、多くの製品では上から順に当てはめて判定します。基本の書き方は「原則すべて拒否して、必要な通信だけ許可する」です。サーバー自身で動かすもの（ホスト型）と、ネットワーク機器として置くもの（ネットワーク型）があります。
- **覚え方**: 「まず全部閉めて、要るものだけ開ける」と覚えます。
- **まちがえやすい**: ファイアウォールは入口を絞るだけです。許可したポートを通ってくる攻撃までは止められません。
- **関連語**: [セキュリティグループ](#g-sec-security-group)、[ポートを閉じる](#g-sec-close-ports)、[WAF](#g-sec-waf)
- **確かめかた**: `sudo firewall-cmd --list-all` や `sudo nft list ruleset`、`sudo iptables -L -n` で現在のルールを一覧できます。使うコマンドは環境によって異なります。

<a id="g-sec-firewalld-iptables"></a>
## firewalld と iptables（ファイアウォールディー／アイピーテーブルズ）

- **一言**: Linux でファイアウォールの規則を設定する、代表的な 2 つの道具です。
- **たとえ**: 同じシャッターを、新しいリモコンでも昔ながらの手動レバーでも動かせる状態に似ています。触る場所は 2 つですが、開け閉めする扉は同じ 1 つです。
- **くわしく**: Linux 本体には、通信を通すか止めるかを判断する機能が組み込まれています。iptables は、その判断の規則を 1 行ずつ書き並べていく、昔からある道具です。firewalld は常駐して規則をまとめて管理する仕組みで、公開用や社内用といった区分（ゾーン）ごとに許可を書けます。Red Hat 系は firewalld、Ubuntu 系は ufw が既定で入るなど、使う道具は環境によって異なります。
- **覚え方**: 「firewalld は規則を預かる管理係、iptables は規則を直接書く道具」と覚えます。
- **まちがえやすい**: firewalld が動いている環境で `iptables` を直接使うと、画面の表示と実際の設定が食い違うことがあります。どちらか片方の道具に寄せて設定するのが安全です。
- **関連語**: [ファイアウォール](#g-sec-firewall)、[ポートを閉じる](#g-sec-close-ports)、[セキュリティグループ](#g-sec-security-group)
- **確かめかた**: `sudo firewall-cmd --state` で firewalld が動いているか、`sudo firewall-cmd --get-active-zones` でどの区分が使われているかを確認できます。`sudo iptables -S` なら規則を 1 行ずつ表示できます。

<a id="g-sec-security-group"></a>
## セキュリティグループ

- **一言**: クラウドで仮想サーバーごとに付ける、許可リスト型のファイアウォールです。
- **たとえ**: 建物の入口ではなく、部屋のドアごとに付ける鍵です。同じ建物の中でも、部屋ごとに入れる人を変えられます。
- **くわしく**: 主要なクラウドでは、仮想サーバーやネットワークの接続口に割り当てて使います。許可するルールだけを書き、書かれていない通信は届きません。同じ役割のサーバーをまとめて 1 つのグループで管理できるので、台数が増えても設定がばらつきません。拒否ルールを書けるかなど細かい仕様は、クラウドによって異なります。
- **覚え方**: 「サーバー 1 台ずつに着せる防護服」と覚えます。
- **まちがえやすい**: 接続元に `0.0.0.0/0`（どこからでも可）を指定すると、世界中に開放されます。検証中に広げた設定を、本番へそのまま持ち込まないようにします。
- **関連語**: [ファイアウォール](#g-sec-firewall)、[DMZ](#g-sec-dmz)、[ポートを閉じる](#g-sec-close-ports)
- **確かめかた**: 使っているクラウドの管理画面で、対象サーバーに付いているルールの一覧と、接続元の範囲を見ます。

<a id="g-sec-dmz"></a>
## DMZ（ディー・エム・ゼット）

- **一言**: 外部に公開するサーバーだけを置く、社内網から切り離した中間の区画です。
- **たとえ**: 玄関と居間の間にある応接間です。宅配の人は応接間までは通しますが、寝室には入れません。
- **くわしく**: Web サーバーやメールサーバーなど、インターネットから直接アクセスされる機器を置きます。DMZ から社内ネットワークへ向かう通信は、必要最小限に絞ります。こうしておくと、公開サーバーが乗っ取られても、社内の重要なデータまで一気に届きにくくなります。
- **覚え方**: 「外と中の間に置く応接間」と覚えます。
- **まちがえやすい**: DMZ に置けば安全になる、わけではありません。侵入されたときに被害の範囲を狭めるための区切りです。
- **関連語**: [ファイアウォール](#g-sec-firewall)、[セキュリティグループ](#g-sec-security-group)、[多層防御](#g-sec-defense-in-depth)
- **確かめかた**: ネットワーク構成図で、公開サーバーがどの区画に置かれ、社内側とどう仕切られているかを確認します。

<a id="g-sec-close-ports"></a>
## ポートを閉じる（ポートヲトジル）

- **一言**: 使っていない通信の窓口をふさぎ、不要なサービスを止めることです。
- **たとえ**: 家の戸締まりです。使っていない部屋の窓が開いていると、そこから入られます。
- **くわしく**: サーバーは役割ごとに、ポート番号という窓口を開けて待ち受けます。初期状態では使う予定のないサービスまで動いていることがあり、そのぶん入口が増えます。ファイアウォールで塞ぐだけでなく、サービス自体を止めれば、窓口そのものが無くなります。
- **覚え方**: 「開けておく窓は、使う窓だけ」と覚えます。
- **まちがえやすい**: ファイアウォールで塞いでも、サービスは動いたままです。内部からは接続できるので、止められるものは止めるのが確実です。
- **関連語**: [ファイアウォール](#g-sec-firewall)、[セキュリティグループ](#g-sec-security-group)、[脆弱性](#g-sec-vulnerability)
- **確かめかた**: `sudo ss -lntup` で待ち受け中のポートを、`systemctl list-units --type=service` で動作中のサービスを一覧できます。

<a id="g-sec-waf"></a>
## WAF（ワフ）

- **一言**: Web アプリ宛ての通信の中身を見て、攻撃らしい要求を弾く仕組みです。
- **たとえ**: 空港の手荷物検査です。建物に入れる人でも、危険物を持っていれば入口で止められます。
- **くわしく**: 正式には Web Application Firewall と書きます。ふつうのファイアウォールはポート番号などでしか判断しませんが、WAF は HTTP の中身を読み、不正な入力のパターンを見つけて遮断します。アプリ側の修正がすぐにできないとき、時間を稼ぐ手段としても使われます。
- **覚え方**: 「ファイアウォールは扉、WAF は手荷物検査」と覚えます。
- **まちがえやすい**: WAF を入れてもアプリの欠陥は消えません。攻撃を弾いているだけなので、原因の修正は別に必要です。
- **関連語**: [ファイアウォール](#g-sec-firewall)、[IDS と IPS](#g-sec-ids-ips)、[脆弱性](#g-sec-vulnerability)
- **確かめかた**: WAF の管理画面で、どのルールが何件ブロックしたか、誤って正常な通信を止めていないかを見ます。

<a id="g-sec-ids-ips"></a>
## IDS と IPS（アイ・ディー・エス／アイ・ピー・エス）

- **一言**: 不審な通信を見つけて知らせるのが IDS、その場で遮断するのが IPS です。
- **たとえ**: 防犯カメラと自動シャッターの違いです。カメラは記録して知らせるだけ、シャッターは侵入者を実際に止めます。
- **くわしく**: IDS は Intrusion Detection System（侵入検知）、IPS は Intrusion Prevention System（侵入防止）の略です。ネットワーク型の IDS は通信のコピーを見るため、本番の通信を止めてしまう心配がありません。IPS は通信の通り道に置くので、誤検知があると正常な通信まで止まる点に注意します。
- **覚え方**: 「D は Detection（見つける）、P は Prevention（止める）」と頭文字で覚えます。
- **まちがえやすい**: IDS は止めてくれません。アラートを誰も見ていなければ、入っていないのとほぼ同じです。
- **関連語**: [WAF](#g-sec-waf)、[ファイアウォール](#g-sec-firewall)、[アクセスログと監査ログ](#g-sec-access-audit-log)
- **確かめかた**: 導入済みなら管理画面の検知一覧を見ます。送信元と、遮断したのか記録だけなのかを確認します。

<a id="g-sec-antimalware"></a>
## ウイルス対策／アンチマルウェア（ウイルスタイサク／アンチマルウェア）

- **一言**: 悪意のあるプログラムを見つけて、隔離したり駆除したりするソフトです。
- **たとえ**: 空港の検疫です。持ち込まれる荷物を調べ、危ないものが見つかったら中に入れずに隔離します。
- **くわしく**: 対象はウイルスだけでなく、身代金を要求するランサムウェアや、不正な遠隔操作の道具も含みます。既知の特徴と照合する方式と、怪しい振る舞いを見る方式があります。特徴を集めた定義ファイルが古いままだと新しい脅威を見逃すため、更新状態を保つことが運用の要点です。
- **覚え方**: 「マルウェアは malicious（悪意ある）ソフト、その検疫係」と覚えます。
- **まちがえやすい**: 入っていること自体は対策ではありません。定義が更新され、検知結果が担当者に届いて、初めて役に立ちます。
- **関連語**: [脆弱性](#g-sec-vulnerability)、[パッチ適用](#g-sec-patching)、[インシデントと情報漏えい](#g-sec-incident-leak)
- **確かめかた**: 製品の管理画面で、定義ファイルの日付と、最後にスキャンした日時を確認します。

<a id="g-sec-vulnerability"></a>
## 脆弱性（ゼイジャクセイ）

- **一言**: 攻撃に悪用できてしまう、ソフトや設定の弱点のことです。
- **たとえ**: 玄関の鍵が古くて簡単に開けられる状態です。壊れてはいないので普段は困りませんが、狙われると弱いです。
- **くわしく**: プログラムの作りの不備だけでなく、初期パスワードのままといった設定の不備も含みます。見つかると開発元が修正版を出すので、利用者側はそれを取り込む作業が必要になります。危険度は、影響の大きさと悪用のしやすさで判断します。
- **覚え方**: 「バグのうち、悪用できるものが脆弱性」と覚えます。
- **まちがえやすい**: 脆弱性がある＝もう侵入されている、ではありません。弱点の存在と、実際の被害は別の話です。
- **関連語**: [CVE](#g-sec-cve)、[パッチ適用](#g-sec-patching)、[ゼロデイ](#g-sec-zero-day)
- **確かめかた**: `apt list --upgradable` や `dnf updateinfo list --security` で、対応が必要な更新があるかを確認できます。コマンドは環境によって異なります。

<a id="g-sec-cve"></a>
## CVE（シー・ブイ・イー）

- **一言**: 公表された脆弱性 1 件ごとに付けられる、世界共通の識別番号です。
- **たとえ**: 事件に付ける事件番号です。番号で呼べば、どの弱点の話をしているのか関係者全員に一発で伝わります。
- **くわしく**: `CVE-2014-0160` のように、西暦と連番を組み合わせた形式で書きます。製品名や表記が違っても、同じ番号なら同じ脆弱性を指します。開発元の告知も、資産管理の道具も、この番号を軸に情報を突き合わせます。
- **覚え方**: 真ん中の V は Vulnerability（脆弱性）の V、と頭文字で覚えます。
- **まちがえやすい**: 番号が付いた＝自分の環境が危ない、ではありません。使っている製品とバージョンが対象条件に当てはまるかを、必ず確認します。
- **関連語**: [脆弱性](#g-sec-vulnerability)、[CVSS](#g-sec-cvss)、[パッチ適用](#g-sec-patching)
- **確かめかた**: 番号で検索し、開発元の告知で対象バージョンと対策を読みます。自分が使っている版は `rpm -q パッケージ名` や `dpkg -l パッケージ名` で確認できます。

<a id="g-sec-cvss"></a>
## CVSS（シー・ブイ・エス・エス）

- **一言**: 脆弱性の深刻さを、共通の物差しで点数にした評価指標です。
- **たとえ**: 地震の震度と同じです。数値で言えば、どのくらい急ぐ話なのかが全員に同じ感覚で伝わります。
- **くわしく**: 攻撃のしやすさや、成立したときの影響の大きさなどから点数を出します。点数が高いほど深刻で、対応の順番を決める材料になります。ただし点数は一般的な条件での評価なので、公開サーバーか社内限定かといった自分の環境の事情も、あわせて判断します。
- **覚え方**: 「CVE は番号、CVSS は点数」、S が多いほうが Score（点数）と覚えます。
- **まちがえやすい**: 点数が低いから放置してよい、とは限りません。小さな弱点も、組み合わせると侵入の踏み台になります。
- **関連語**: [CVE](#g-sec-cve)、[脆弱性](#g-sec-vulnerability)、[パッチ適用](#g-sec-patching)
- **確かめかた**: 開発元や公的機関の告知ページで、CVE 番号の横に書かれた深刻度（Critical、High など）を見ます。

<a id="g-sec-patching"></a>
## パッチ適用（パッチテキヨウ）

- **一言**: 脆弱性や不具合を直す修正プログラムを、サーバーに当てる作業です。
- **たとえ**: 服の穴に当て布をする作業です。小さいうちに当てれば済みますが、放っておくと穴は広がります。
- **くわしく**: 適用の前に、影響範囲の確認、検証環境での動作確認、切り戻し手順の準備を行います。再起動が必要な更新もあるため、業務への影響を考えて実施の時間帯を決めます。頻度や承認の手順は、組織や環境によって異なります。
- **覚え方**: 「当てる前に、戻し方を決める」と覚えます。
- **まちがえやすい**: 適用しただけで安心しがちです。再起動やサービスの再読み込みをしていないと、古いプログラムが動き続けていることがあります。
- **関連語**: [脆弱性](#g-sec-vulnerability)、[CVE](#g-sec-cve)、[ゼロデイ](#g-sec-zero-day)
- **確かめかた**: `uptime` で最後の再起動からの経過時間を確認します。再起動が必要かは `ls /run/reboot-required` や `needs-restarting -r` で分かります（コマンドは環境によって異なります）。

<a id="g-sec-zero-day"></a>
## ゼロデイ

- **一言**: 修正プログラムがまだ無い状態で悪用される、脆弱性や攻撃のことです。
- **たとえ**: 鍵の欠陥を泥棒に先に見つけられた状態です。交換用の鍵がまだ売っていないので、当面は別の方法で家を守ります。
- **くわしく**: 「対策が出てから 0 日目」という意味の言葉です。修正が出るまでは、その機能の停止、通信元の制限、WAF での遮断といった回避策で被害を避けます。開発元の告知を追い、暫定の回避策が公開されていないかを確認するのが実務です。
- **覚え方**: 「対策 0 日目、パッチはまだ無い」と覚えます。
- **まちがえやすい**: ゼロデイは防げないから諦める、というのは誤りです。侵入されても被害を広げない備えは、事前に用意できます。
- **関連語**: [脆弱性](#g-sec-vulnerability)、[パッチ適用](#g-sec-patching)、[WAF](#g-sec-waf)
- **確かめかた**: 使っている製品の開発元が出すセキュリティ情報のページを、定期的に見る習慣を作ります。

<a id="g-sec-selinux-apparmor"></a>
## SELinux と AppArmor（エスイーリナックス／アップアーマー）

- **一言**: プログラムごとに許される操作を OS 側で細かく縛る、Linux の仕組みです。
- **たとえ**: 社員証に「入れるのは 3 階の資料室だけ」と印刷しておくようなものです。本人が何を考えていても、それ以外の扉は開きません。
- **くわしく**: ふつうの権限はユーザー単位ですが、これらはプログラム単位で、触れるファイルや使えるポートを制限します。Web サーバーが乗っ取られても、決められた場所以外は読み書きできません。SELinux は Red Hat 系、AppArmor は Ubuntu 系でよく使われます。
- **覚え方**: 「ユーザーではなく、プログラムに首輪を付ける」と覚えます。
- **まちがえやすい**: 動かないときに、まず無効化してしまいがちです。正しい順番は、拒否されたログを読み、必要な許可だけを足すことです。
- **関連語**: [最小権限の原則](#g-sec-least-privilege)、[アクセスログと監査ログ](#g-sec-access-audit-log)、[認証と認可](#g-sec-authn-authz)
- **確かめかた**: `getenforce` で SELinux の状態を、`sudo aa-status` で AppArmor の状態を確認できます。どちらが入っているかは環境によって異なります。

<a id="g-sec-access-audit-log"></a>
## アクセスログと監査ログ（アクセスログ／カンサログ）

- **一言**: 誰が何にアクセスしたかの記録と、重要な操作の証拠を残す記録です。
- **たとえ**: 店の防犯カメラの映像がアクセスログ、金庫の開閉記録簿が監査ログです。
- **くわしく**: アクセスログは Web サーバーなどへの要求を記録し、日々の状況把握や障害調査に使います。監査ログはログインや権限の変更など、後から「誰がやったか」を示す必要がある操作を残します。書き換えられては意味がないので、別のサーバーに転送して保管することもあります。保存期間は組織や環境によって異なります。
- **覚え方**: 「アクセスログは通行記録、監査ログは責任の記録」と覚えます。
- **まちがえやすい**: 取っていれば十分、ではありません。誰も見ていない、期限切れで消えた、サーバーの時刻がずれている、のどれかで役に立たなくなります。
- **関連語**: [インシデントと情報漏えい](#g-sec-incident-leak)、[特権 ID](#g-sec-privileged-id)、[IDS と IPS](#g-sec-ids-ips)
- **確かめかた**: `ls -l /var/log` でログの置き場と更新時刻を、`journalctl -u sshd` でログイン関連の記録を確認できます。サービス名は環境によって異なります。

<a id="g-sec-incident-leak"></a>
## インシデントと情報漏えい（インシデント／ジョウホウロウエイ）

- **一言**: 事故につながる出来事の全体がインシデント、その一種が情報漏えいです。
- **たとえ**: 交通の世界のヒヤリハットと実際の事故の関係です。ぶつかりそうになった時点で報告するから、次の事故が防げます。
- **くわしく**: 不正アクセス、マルウェア感染、メールの誤送信、端末の紛失なども含まれます。起きたら、まず被害の拡大を止め、次に記録を保全し、それから原因を調べる順番が基本です。慌てて再起動すると、原因を示す痕跡が消えることがあります。報告先と手順は組織によって異なるので、事前に確認しておきます。
- **覚え方**: 「止める・残す・調べる」の順と覚えます。
- **まちがえやすい**: 「たぶん大丈夫」と自分で判断して黙るのが、いちばん悪い対応です。疑わしい時点で報告するのが正解です。
- **関連語**: [アクセスログと監査ログ](#g-sec-access-audit-log)、[ソーシャルエンジニアリング](#g-sec-social-engineering)、[ウイルス対策](#g-sec-antimalware)
- **確かめかた**: 自分の職場の連絡フロー（誰に、どのくらいの時間内に、どの手段で）を、何も起きていないうちに読んでおきます。

<a id="g-sec-social-engineering"></a>
## ソーシャルエンジニアリングとフィッシング（ソーシャルエンジニアリング／フィッシング）

- **一言**: 技術ではなく人をだまして情報を盗む手口と、その代表的な手法です。
- **たとえ**: 電話で「システム部の者ですが」と名乗ってパスワードを聞き出すのがソーシャルエンジニアリングです。フィッシングは、本物そっくりの偽の窓口に誘い込む釣りです。
- **くわしく**: 肩越しに画面をのぞく、業者を装って入館する、といった方法も含まれます。フィッシングはメールやメッセージで偽サイトへ誘導し、入力させた ID とパスワードを盗みます。「急かす」「脅す」「うますぎる話をする」が典型的な合図です。
- **覚え方**: 「fishing（釣り）と同じ読み、餌はメール」と覚えます。
- **まちがえやすい**: 差出人の表示名は簡単に偽装できます。文面のリンク表示ではなく、実際の宛先ドメインを見て判断します。
- **関連語**: [多要素認証](#g-sec-mfa)、[インシデントと情報漏えい](#g-sec-incident-leak)、[秘密情報の扱い](#g-sec-credentials)
- **確かめかた**: パソコンならリンクにカーソルを合わせ、スマホなら長押しして、表示される実際の URL とドメインを見比べます。

<a id="g-sec-credentials"></a>
## 秘密情報／クレデンシャルの扱い（ヒミツジョウホウ／クレデンシャルノアツカイ）

- **一言**: パスワードや鍵など、渡ると成りすまされる秘密情報の管理方法です。
- **たとえ**: 家の合鍵と同じです。玄関マットの下に隠すのではなく、本数を数えて金庫に入れて管理します。
- **くわしく**: 秘密情報（クレデンシャル）には、パスワード、API キー、秘密鍵、接続用の設定文字列などが含まれます。ソースコードや設定ファイルに直接書くと、共有した瞬間に全員へ渡ってしまいます。専用の保管サービスや環境変数で渡し、漏れた疑いがあれば作り直します。共有せず、人ごとに発行するのが原則です。
- **覚え方**: 「コードに書かない、チャットに貼らない、画面に映さない」の 3 つで覚えます。
- **まちがえやすい**: 一度リポジトリに入れた秘密情報は、後から消しても履歴に残ります。消すことより先に、その鍵を無効にして作り直します。
- **関連語**: [パスワードポリシー](#g-sec-password-policy)、[共通鍵暗号と公開鍵暗号](#g-sec-symmetric-asymmetric)、[アカウント管理と棚卸し](#g-sec-account-review)
- **確かめかた**: `ls -l ~/.ssh` で、秘密鍵の許可が本人だけになっているかを確認します。`git log -p` で、過去のコミットに秘密情報が混ざっていないか探せます。

<a id="g-sec-defense-in-depth"></a>
## 多層防御（タソウボウギョ）

- **一言**: 対策を何段も重ね、1 つ破られても被害が広がらないようにする考え方です。
- **たとえ**: 城の守りです。堀、石垣、門、天守と何重にもあるので、堀を越えられてもすぐには落ちません。
- **くわしく**: ファイアウォールも、権限の絞り込みも、パッチも、ログ監視も、単独では完璧になりません。だからこそ層を重ね、1 か所の突破がそのまま情報漏えいにつながらない形にします。英語では defense in depth と言います。この章の用語も、どの層を担当するかで並べ直すと覚えやすくなります。
- **覚え方**: 「分厚い壁 1 枚より、薄い壁を何枚も」と覚えます。
- **まちがえやすい**: 高機能な製品を 1 つ入れれば安心、ではありません。入口・権限・記録のどれが欠けても、そこが最短の抜け道になります。
- **関連語**: [DMZ](#g-sec-dmz)、[最小権限の原則](#g-sec-least-privilege)、[ファイアウォール](#g-sec-firewall)
- **確かめかた**: 自分の担当システムについて、入口・権限・記録の 3 つの層に今どんな対策があるかを書き出し、空欄を探します。
