## 1. 何を測るのか

測る指標は 4 つです。1 つだけ見ても判断できないので、かならず 4 つセットで読みます。

| 指標 | 何を表すか | 何の判断に使うか |
| --- | --- | --- |
| スループット（req/s） | 1 秒あたりに処理できたリクエストの本数 | いま何件さばけているか。並列数を上げても増えなくなったら頭打ちの合図 |
| レイテンシ分布（p50 / p90 / p95 / p99 / max） | 1 件あたりの応答時間が、どのくらいばらついているか | 利用者の体感。レイテンシ SLO（p95 < 500ms）を満たせるかの判定 |
| エラー率 | 完了したリクエストのうち、応答を受け取れなかった割合 | 「速いが失敗している」状態の検出。過負荷の入口 |
| 飽和点（さばききれなくなる点） | 並列数を上げてもスループットが伸びず、レイテンシだけ伸び始める点 | 容量設計（何並列まで受けてよいか）の根拠 |

**スループットだけを見てはいけない理由**: 全部のリクエストを即座に失敗させれば、
req/s はいくらでも大きくできます。エラー率とレイテンシを同時に見て初めて、
その req/s が「ちゃんとさばけた本数」なのかどうかが分かります。

## 2. なぜ平均値ではなくパーセンタイルを見るのか

次の数字は、考え方を説明するための**作り話**です。この構成で実際に測った値では
ありません。

100 件のリクエストのうち、99 件が 10 ミリ秒で返り、1 件だけ 5,000 ミリ秒
かかったとします。平均はおよそ 60 ミリ秒です。数字だけ見ると「速い」ように見えます。
しかし実際には、**100 人に 1 人が 5 秒待たされています。**

平均値は「遅い人がいること」を薄めて隠してしまいます。利用者は平均を体験しません。
自分に返ってきた 1 件を体験します。だから分布（ばらつき）を見ます。

**パーセンタイル**は、応答時間を小さい順に並べたときの位置を表す値です。

| 表記 | 意味 | 読み方 |
| --- | --- | --- |
| p50（中央値） | 下から 50% の位置 | 2 人に 1 人はこれより速い |
| p95 | 下から 95% の位置 | 20 人に 19 人はこれより速い。裏返すと 20 人に 1 人はこれより遅い |
| p99 | 下から 99% の位置 | 100 人に 1 人はこれより遅い |
| max | 最大値 | いちばん運が悪かった 1 件 |

`max` は 1 件のノイズ（たまたま GC が走った、など）で大きく動くので、指標としては
暴れすぎます。逆に平均は遅い側を隠します。**p95 は「ほとんどの利用者の体感」を
1 つの数字で表せて、かつ外れ値 1 件では動きにくい**ため、SLO の指標に向いています。

### パーセンタイルの計算方法（他ツールと比べるときの注意）

[`scripts/perf/load.py`](../scripts/perf/load.py) は **nearest-rank 法（最近接順位法）**
を使います。昇順に並べた N 件に対して、

```text
rank = ceil(q / 100 * N)   （1 以上 N 以下に丸める）
```

を求め、その rank 番目（1 始まり）の値をそのまま返します。線形補間はしません。
つまり、出てくる p95 は**必ず実際に観測されたサンプルのどれか**です。

パーセンタイルの定義はツールによって違います（線形補間するもの、補間方法が
複数あるもの）。他のツールで測った p95 と、この値を単純に突き合わせないでください。

## 3. closed-loop と open-loop の違い

負荷のかけ方には大きく 2 通りあります。

| 方式 | 何を固定するか | 動き | 性格 |
| --- | --- | --- | --- |
| closed-loop（クローズドループ） | **並列数**（同時に投げる本数） | 1 件の応答を受け取ってから、次の 1 件を投げる | サーバーが遅くなると、投げる本数も自然に減る |
| open-loop（オープンループ） | **レート**（秒あたりの本数） | 応答が返ったかに関係なく、決めたペースで投げ続ける | サーバーが遅くなっても、投げる本数は減らない |

### この試験が closed-loop を選んだ理由

1. **飽和点を探す段階試験と相性が良い。** 並列数を 1 → 2 → 4 … と上げていく試験は、
   横軸がそのまま並列数になります。closed-loop は並列数を直接指定できます。
2. **追加の依存を増やさずに実装できる。** Python 3.11 の標準ライブラリだけで素直に
   書けるため、`requirements-dev.txt` に何も足していません。
3. **測定側が先に壊れにくい。** open-loop でサーバーがさばけないレートを入れると、
   未完了のリクエストが際限なく積み上がり、負荷生成器の側（メモリ・スレッド）が
   先に破綻します。何を測ったのか分からない結果になりがちです。

### closed-loop の弱点（読むときの補正）

closed-loop には **coordinated omission（協調的見落とし）** という弱点があります。
サーバーが遅くなると投げ手も自動的にゆっくりになるため、「遅かった時間帯に、
本来なら発生していたはずのリクエスト」が測定から抜け落ちます。その結果、
**遅さが過小評価されやすい**という偏りがあります。

実際の利用者は、待たされてもアクセスをやめてくれません。したがって、
この試験で出る p95 は**楽観側に寄った値**として読んでください。

## 4. 飽和点の見方と容量設計

並列数を少しずつ上げていくと、典型的には次の 3 段階をたどります。

| 段階 | スループット | レイテンシ | エラー率 |
| --- | --- | --- | --- |
| 余裕がある | 並列数にほぼ比例して伸びる | ほぼ横ばい | ほぼ 0 |
| 飽和している | 伸びなくなる（頭打ち） | 待ち行列ができて伸び始める | まだ 0 に近い |
| 破綻している | 落ちることもある | さらに伸びる | タイムアウト・接続拒否が出て上がる |

**飽和点は「余裕がある」から「飽和している」へ切り替わる折れ曲がりの点**です。
ここが分かると、「この構成なら同時どれくらいまで受けてよいか」という容量設計
（キャパシティプランニング）の根拠になります。勘ではなく数字で言えるようになります。

### 判定式（[`scripts/perf/run-perf.sh`](../scripts/perf/run-perf.sh) に実装済み）

並列数の昇順に並べた段 `i`（2 段目以降）について、1 つ手前の段 `i-1` と比べます。

```text
gain_i      = (rps_i - rps_{i-1}) / rps_{i-1}     … スループットの伸び率
lat_ratio_i = p95_i / p95_{i-1}                   … p95 の伸び率
```

次の 2 つを**同時に**満たした最初の段 `i` を「飽和した段」と呼びます。

| 条件 | 式 | 意味 |
| --- | --- | --- |
| (A) | `gain_i < 0.10` | 並列を増やしても、処理量が 10% 未満しか伸びない |
| (B) | `lat_ratio_i > 1.20` | その一方で、p95 は 1.2 倍を超えて悪化した |

報告する**飽和点は、飽和した段 `i` ではなく 1 つ手前の段 `i-1` の並列数**です。
「まだ余裕のあった最大の並列数」を基準値として扱うためです。

`rps_{i-1}` または `p95_{i-1}` が 0 の段は比較できないため、判定から外します。

### 「飽和点: 未検出」の意味

最後の段まで (A) と (B) が同時に成立しなかった場合、飽和点は未検出になります。
これは**「飽和しなかった」ではなく「試した並列数の範囲では見つからなかった」**
という意味です。`--steps` にもっと大きい並列数を足して測り直します。

### 容量設計に使うときの注意

飽和点そのものを運用上の上限にはしません。飽和点は「これ以上増やしても無駄になる
直前」であって、「ここまでなら快適」ではないからです。運用上の上限には、
**飽和点より下で、かつレイテンシ SLO を満たしていた最大の並列数**を使います。
`run-perf.sh` はこの値を `slo_max_concurrency` として飽和点とは別に出力します。

## 6. 実行手順

### 6.1 前提

- **Docker と `docker compose` が動く環境**が必要です。`python3` と `curl` も使います。
- `compose.yaml` が参照する secrets ファイル（`deploy/secrets/*.txt`）を用意しておきます。
  手元で試すだけなら `*.txt.example` をコピーします。
- **本番環境では実行しないでください。** 実際にサーバーへ負荷をかけます。

### 6.2 いちばん簡単な実行

```bash
cd /path/to/server
./scripts/perf/run-perf.sh
```

既定のまま実行すると、次の順番で動きます。

1. 引数を検証します（おかしな値のまま負荷をかけ始めないための安全装置です）。
2. `docker compose -f compose.yaml -f compose.perf.yaml up -d app nginx` で
   `app` と `nginx` だけを起動します（監視系は `profiles` で起動しません）。
3. `http://127.0.0.1:8080/healthz` が 200 を返すまで、最大 120 秒待ちます。
   起動しきる前に測ると、起動の遅さを「サーバーの遅さ」として誤って記録してしまうためです。
4. 200 を確認してから、結果ディレクトリ `./perf-results/<UTC タイムスタンプ>/` を作ります。
   1 度も測れずに終わった実行が、空のディレクトリを残さないようにしています。
5. ウォームアップ（準備運転）を 5 秒ぶん実行します。結果は集計に使いません。
6. 並列数 1, 2, 4, 8, 16, 32 の順に、それぞれ 30 秒ずつ計測します。段と段のあいだは
   3 秒空けて、サーバー側の待ち行列を落ち着かせます。
7. 全段の結果を集計し、飽和点を判定して Markdown サマリーを出力します。
   最終行に `RESULT_JSON=` で機械可読な JSON を出します（`d1-process-down.sh` と同じ作法です）。
8. 終了時に `app` と `nginx` を `stop` します（コンテナも volume も削除しません）。

### 6.3 `run-perf.sh` の引数

| 引数 | 既定値 | 内容 |
| --- | --- | --- |
| `--url URL` | `http://127.0.0.1:8080/healthz` | 負荷をかける対象。`http://` または `https://` で始まる必要があります |
| `--steps LIST` | `1,2,4,8,16,32` | 並列数の段をカンマ区切りで指定します。**昇順必須**（前の段と比べて飽和を判定するため） |
| `--duration SECONDS` | `30` | 1 段あたりの計測秒数（1 以上の整数） |
| `--warmup SECONDS` | `5` | 計測前のウォームアップ秒数（0 以上の整数。0 なら実行しません） |
| `--out-dir DIR` | `./perf-results` | 結果の保存先。この下に実行ごとのディレクトリを作ります |
| `--workers N` | 指定なし | Gunicorn の worker 数を `GUNICORN_WORKERS` として Compose に渡します（[10 章の制約](#10-既知の制約)を必ず読んでください） |
| `--request-timeout SECONDS` | `10` | 1 リクエストあたりの上限秒 |
| `--no-compose` | — | Compose を起動しません。すでに起動済みの環境に対して測るときに使います。後始末もしません |
| `--help`, `-h` | — | 使い方を表示して終了します |

例: 起動済みの環境に対して、並列 1〜8 を 60 秒ずつ測る場合。

```bash
./scripts/perf/run-perf.sh \
  --url http://127.0.0.1:8080/healthz \
  --steps 1,2,4,8 \
  --duration 60 \
  --warmup 10 \
  --out-dir ./perf-results \
  --no-compose
```

### 6.4 出力されるファイル

`--out-dir` の下に、実行ごとのディレクトリ（名前は UTC の `YYYYMMDDTHHMMSSZ`）ができます。

| ファイル | 内容 |
| --- | --- |
| `warmup.json` | ウォームアップの記録。集計には使いません |
| `step-c<並列数>.json` | 各段の詳細（レイテンシ分布、ステータス別内訳、エラー種別、SLO 判定） |
| `summary.md` | 全段をまとめた Markdown。`docs/drills/logs/` にそのまま貼れる形です |

`perf-results/` は `.gitignore` に入っています。実行環境ごとに値が変わる計測データを
リポジトリに含めないためです。残す場合は証跡として別途保存します（[11 章](#11-記録の残し方)）。

### 6.5 `load.py` を単体で使う

1 段だけ測りたいとき、あるいは認証が必要なエンドポイントを測りたいときに使います。

```bash
python3 scripts/perf/load.py \
  --url http://127.0.0.1:8080/healthz \
  --concurrency 8 \
  --duration 30 \
  --warmup 5 \
  --timeout 10 \
  --slo-p95-ms 500 \
  --slo-error-rate 0.01 \
  --label manual-c8 \
  --out ./perf-results/manual-c8.json
```

| 引数 | 既定値 | 内容 |
| --- | --- | --- |
| `--url URL` | （必須） | 対象の URL |
| `--concurrency N` | `4` | 同時に投げる本数（並列数） |
| `--duration SECONDS` | `30.0` | 計測時間（秒） |
| `--warmup SECONDS` | `5.0` | 準備運転の時間。**この期間に完了したぶんは集計から完全に除外します** |
| `--timeout SECONDS` | `10.0` | 1 リクエストのタイムアウト |
| `--out PATH` | なし | 結果 JSON の出力先 |
| `--header 'Name: value'` | なし | 追加する HTTP ヘッダー。複数回指定できます |
| `--slo-p95-ms MS` | なし | p95 のしきい値。指定すると PASS / FAIL を判定します |
| `--slo-error-rate RATE` | なし | エラー率のしきい値（`0.01` = 1%） |
| `--label NAME` | 空 | この実行につける名前。結果 JSON に入ります |

`run-perf.sh` は各段を `--warmup 0` で呼び出し、ウォームアップは最初に 1 回だけ
まとめて実行します。`load.py` を直接使うときは `--warmup` を自分で指定してください。

認証が必要なエンドポイントを測る例です。

```bash
# /metrics（Bearer トークン）
python3 scripts/perf/load.py \
  --url http://127.0.0.1:8080/metrics \
  --header "Authorization: Bearer $(cat deploy/secrets/metrics_token.txt)" \
  --concurrency 4 --duration 30 --label metrics-c4

# /stats（Basic 認証。ヘッダーを自分で組み立てます）
BASIC=$(printf '%s:%s' "monitor" "$(cat deploy/secrets/dashboard_password.txt)" | base64 -w0)
python3 scripts/perf/load.py \
  --url http://127.0.0.1:8080/stats \
  --header "Authorization: Basic ${BASIC}" \
  --concurrency 4 --duration 30 --label stats-c4
```

### 6.6 終了コード

| コード | `run-perf.sh` | `load.py` |
| --- | --- | --- |
| 0 | 全体判定が PASS（SLO を満たした段が 1 つ以上ある） | SLO 判定が PASS、またはしきい値を指定しなかった |
| 1 | 全体判定が FAIL、未知の引数を渡した、または必要なコマンド（`docker` / `curl` / `python3`）が見つからない | SLO 判定が FAIL |
| 2 | 引数の値が不正（昇順でない `--steps`、`--duration 0`、`http(s)` でない URL など） | 引数の値が不正 |
| 3 | `scripts/perf/load.py` が見つからない | — |
| 4 | 120 秒待っても対象 URL が 200 を返さなかった（負荷をかけずに終了します） | — |
| 5 | ある段の結果 JSON が書き出されなかった。集計へ進まずその場で停止します | — |

コード 3・4・5 は「測れなかったので何も記録しない」ための停止です。
数値を推測で埋めないための作りになっています。とくにコード 5 は、
**測れていない段を「エラー率 0」などとして集計に混ぜないための停止**です。
SLO を満たさなかっただけの段では停止せず、最後まで測り切ります（その場合はコード 1）。

### 6.7 GitHub Actions で実行する

`Actions` → **Performance test** → `Run workflow` から手動実行できます。
`app.py`、`compose.yaml`、`compose.perf.yaml`、`Dockerfile`、`deploy/nginx/**`、
`scripts/perf/**` などを変更した pull request でも自動実行されます。

| 入力 | 既定値 | 内容 |
| --- | --- | --- |
| `steps` | `1,2,4,8,16` | 並列数の段 |
| `duration` | `20` | 各段の計測秒数 |
| `warmup` | `5` | 助走時間 |
| `max_error_rate` | `0.05` | この値を超えたらジョブを失敗させるエラー率 |

結果は artifact `perf-test-<run id>-<attempt>` として 30 日保存されます
（各段の JSON、`summary.md`、`run-perf.log`、`result.json`、Compose のログ）。
サマリーはジョブの Summary 欄にも出ます。

**CI の合否方針**: GitHub hosted runner は CPU もディスクも他の利用者と共有され、
実行ごとに性能がばらつきます。そのため「p95 が何ミリ秒未満」という絶対値では
落としません（同じコードでも runner 次第で赤信号になり、信用されなくなるためです）。
CI が落とすのは、環境のばらつきでは説明できない異常だけです。

## 7. 結果の読み方

### 7.1 サマリー表の列

`summary.md` の「各段の結果」表は次の列を持ちます。

| 列 | 意味 |
| --- | --- |
| 並列数 | その段で同時に投げた本数 |
| スループット (req/s) | 完了したリクエスト数 ÷ 計測秒数 |
| p95 (ms) | 応答時間の 95 パーセンタイル |
| エラー率 | エラー件数 ÷ 完了した全リクエスト件数 |
| 前段比 伸び率 | `gain`。1 つ前の段に対するスループットの伸び |
| 前段比 p95 倍率 | `lat_ratio`。1 つ前の段に対する p95 の伸び |
| SLO 判定 | その段が p95 と エラー率のしきい値を満たしたか（PASS / FAIL） |

### 7.2 数え方の約束（ここを誤解すると読み違えます）

| 項目 | 定義 |
| --- | --- |
| エラー率の分母 | ウォームアップ後に**完了した全リクエスト**（成功サンプル + エラー）。打ち切り時点で未完了のものは分子にも分母にも入りません |
| レイテンシの対象 | **応答を受け取れたものだけ。** タイムアウトや接続エラーは応答時間に混ぜず、種別ごとに別で数えます |
| 4xx / 5xx の扱い | 応答は返っているので**レイテンシには含めます**。ただし成功数（2xx / 3xx）からは外れます。内訳は `status_counts` で分かります |
| しきい値ちょうど | PASS とします（`<=` で判定） |
| サンプル 0 件 | FAIL とします。測れていないものを PASS とは呼ばないためです |

### 7.3 出かたのパターンと、その意味

| 出かた | 読み取れること | 次の一手 |
| --- | --- | --- |
| 最後の段までスループットが伸び、p95 も横ばい | まだ余裕がある。飽和点は未検出になる | `--steps` にもっと大きい並列数を足して測り直す |
| スループットが頭打ちになり、p95 だけ伸び始めた | 飽和点に到達した。容量設計の基準が取れた | 1 つ手前の段の並列数を基準値として記録する |
| p95 は伸びていないのにエラー率だけ上がった | 受け口（Nginx や OS の接続まわり）で先に弾かれている疑い。**エラーはレイテンシに混ざらないので見落としやすい** | `error_counts` の種別（timeout / connection_error）と Nginx のログを確認する |
| 並列 1 の段から p95 が大きい | 負荷の問題ではない。処理そのものが遅い | [latency-spike runbook](runbooks/latency-spike.md) の切り分け表で原因を絞る |
| どの段も req/s が不自然に低く、測定ホストの CPU が張り付いている | 負荷生成器の側がボトルネックになっている可能性 | 並列数を下げる、または負荷生成を別ホストへ移す |
| 特定の段だけ `partial: true` | SIGINT で打ち切られた段。値は参考扱い | その段を測り直す |

## 8. レイテンシ SLO との対応

[docs/slo.md の 2.2 レイテンシ](slo.md#22-レイテンシ)は次を定義しています。

> **p95 < 500ms を 28 日のうち 99% の時間で維持**

`run-perf.sh` は各段の合否判定に、この **500ms** と、エラー率 **0.01** を
`load.py` に渡しています。スクリプト側でこの値を書き換えることはしません。

### 対応すること

- **500ms という目標が守れる値なのかどうかの材料になります。** どのくらいの並列数まで
  p95 が 500ms に収まるのかは、測らないと分かりません。この試験はそこを埋めます。
- SLO を満たした最大並列数（`slo_max_concurrency`）は、そのまま容量設計の入力になります。

### 対応しないこと（ここが重要です）

| 違い | 内容 |
| --- | --- |
| 期間の条件 | SLO は「**28 日のうち 99% の時間で**維持」という時間の条件を含みます。1 回の負荷試験は数十秒から数分の一断面にすぎず、SLO の合否を置き換えることはできません |
| 測定点 | SLO の SLI は blackbox-exporter の `probe_duration_seconds`（30 秒間隔の外形監視）です。この試験は負荷生成器から測った応答時間で、測定点が違います |
| エラー率と可用性 SLO | 可用性 SLO は「30 日窓で probe 成功率 99.5%」です。`run-perf.sh` のエラー率しきい値 `0.01` は、1 回の試験で明らかに壊れている状態を弾くためのスクリプト内の値であり、可用性 SLO そのものではありません |
| 境界の扱い | `load.py` はしきい値ちょうどを PASS とします（`p95 <= 500`）。`slo.md` の表記は `p95 < 500ms`（未満）です。ちょうど 500.0ms のときだけ判断が分かれます |

したがって、結果を書くときの言い方はこうなります。

- ✅ 「並列 N のとき、この環境では p95 が 500ms を下回った」
- ❌ 「レイテンシ SLO を達成した」

## 9. 測定の限界

この試験が**保証しないこと**を先に書きます。結果を人に見せるときは、必ずこの節も
一緒に示してください。

1. **1 台・ローカル・コンテナ内の計測です。** 負荷生成器と対象サーバーが同じマシンに
   いるため、ネットワーク遅延がほぼゼロです。実際の利用者は必ずもっと遠くにいます。
2. **負荷生成器が対象と同じ CPU を食います。** 高い並列数では、測定側がボトルネックに
   なって「サーバーが遅い」ように見えることがあります。
3. **GitHub hosted runner は実行ごとに性能がばらつきます。** 他の利用者と資源を共有して
   いるため、同じコード・同じ引数でも数値は一致しません。CI の結果は絶対値の比較には
   使えません。飽和点と p95 の**傾向**を見るためのものです。
4. **監視系を止めた状態で測ります。** `compose.perf.yaml` は Prometheus / Grafana / Loki
   などに `profiles` を付けて起動しません。本番ではこれらが同居するため、その分の
   資源消費は含まれていません。
5. **`/healthz` は最も軽いエンドポイントです。** `/stats` や `/processes` はもっと重い
   処理をします。`/healthz` の数字を、アプリ全体の性能と読み替えないでください。
6. **実利用者のアクセス分布を再現していません。** データ量、キャッシュの温まり方、
   複数のエンドポイントが混ざる実際のアクセスパターンは含まれていません。
7. **closed-loop の過小評価があります。**（[3 章](#3-closed-loop-と-open-loop-の違い)）
8. **したがって、この結果は参考値であり、本番環境の性能保証値ではありません。**
   `load.py` は同じ趣旨の文章を、出力 JSON の `scope_note` に必ず入れます。
   値だけを抜き出して引用しないための作りです。

## 10. 既知の制約

実行する前に知っておくべき点です。**どちらも実行して分かったことではなく、
コードを読んで分かったこと**です。

### 10.1 `--workers` が効くのは compose を起動する場合だけです

`run-perf.sh --workers N` は `GUNICORN_WORKERS` を export し、`compose.perf.yaml` が
`app` の起動コマンドごと差し替えて worker 数を反映します。

環境変数を渡すだけでは足りません。`Dockerfile` の `CMD` が

```text
gunicorn --workers 2 --bind 0.0.0.0:5000 ... app:app
```

と worker 数を直接書いており、Gunicorn は**コマンドライン引数を環境変数
（`GUNICORN_CMD_ARGS`）より優先する**ためです。そこで `compose.perf.yaml` は
この `CMD` を worker 数だけ変えて写し、`command` として上書きしています。

写している以上、`Dockerfile` を変えたときに片方だけ古くなる危険があります。
そのずれは `tests/test_perf.py` の
`test_compose_perf_command_matches_dockerfile_cmd` が CI で照合します。

**`--no-compose` を付けた場合は効きません。** 既に起動している環境をそのまま測る
モードなので、worker 数は起動時のままです。この場合、`summary.md` と `result.json`
には「渡したが未適用」と記録されます（`gunicorn_workers_applied: false`）。

### 10.2 CI は SLO 未達では落としません

`perf-test.yml` の `Run load test` ステップは、`run-perf.sh` の終了コードを
記録したうえで先へ進みます。`run-perf.sh` は「どの段も SLO を満たさなかった」ときに
終了コード 1 を返しますが、それは**測定が失敗したという意味ではなく、測った結果が
目標に届かなかったという意味**です。ここで打ち切ると `result.json` が書かれず、
いちばん見たい「届かなかった記録」が残りません。

そのため CI が落ちるのは次の場合だけです。

| 落ちる条件 | 理由 |
| --- | --- |
| `/healthz` が待受タイムアウト内に返らない | 測定が始められていない |
| `RESULT_JSON` 行が出力されない | 測定が完走していない |
| エラー率が `max_error_rate` を超えた | 負荷の問題ではなく壊れている疑いがある |

SLO 未達そのものは記録して先へ進みます。GitHub hosted runner は実行ごとに性能が
ばらつくため、絶対値で合否を決めると同じコードでも runner 次第で赤になり、
CI の赤信号が信用されなくなるからです。

## 11. 記録の残し方

- 実行したら、`summary.md` の末尾にある記入欄（実施日時 / 実施者 / 気づいたこと /
  改善アクション）を埋めます。
- **数値は手で書き換えません。** スクリプトが出力した JSON と `summary.md` を
  そのまま証跡にします。手で PASS を書き込む余地を残さないための運用です。
- 日付付きの記録として残す場合は、[検証証跡台帳](evidence/README.md)の運用に従います。
  この文書（原本）には実測値を書きません。
- 状態の呼び方は、リポジトリ共通の 4 段階を使います。

| 状態 | 意味 | この試験の現在地 |
| --- | --- | --- |
| 文書化済み | 手順を書いた | ✅ |
| 実装済み | 動くコードがある | ✅ |
| 実測済み | 実際に走らせて結果が残っている | — |
| 未実施（NOT RUN） | まだ走らせていない | **← いまここ** |

試験項目と結果の記入先は[試験仕様書・結果票の性能試験](build-package/06-test-specification.md#性能試験)です。
