# 失敗から学んだ代表事例

詳細と全件数の正本は[欠陥台帳](evidence/defects-found.md)である。このページは採用担当者と
初学者が、代表例から「現象 → 切り分け → 修正 → 再発防止」を短時間で追うための要約である。

## 1. ディスクを空と誤認する安全装置

| 観点 | 内容 |
| --- | --- |
| 当初の想定 | `lsblk`のFSTYPEが空なら未使用ディスクとして扱える |
| 現象 | udev cacheにより署名済みext4でもnullになり、既存データを破壊する可能性があった |
| 切り分け | `storage-guard-test.sh`で署名ありdiskをnegative testした |
| 根本原因 | 表示用のcache値を破壊的操作の判定根拠に使った |
| 修正 | `wipefs`の実読みを安全装置にした |
| 再発防止 | 正常系だけでなく、拒否すべき7ケースを試験する |
| 学び | 破壊的操作は「使えること」より「危険な入力を拒否すること」を先に試す |

## 2. 層分離試験が別の理由で偽PASSになった

| 観点 | 内容 |
| --- | --- |
| 当初の想定 | webからDBへの`nc -z`失敗ならnetwork分離が成立している |
| 現象 | container内BusyBoxの`nc`が`-z`非対応で、到達可能でもcommand errorによりPASSした |
| 切り分け | 実image内でcommandのavailabilityと終了コードを確認した |
| 根本原因 | 「接続拒否」と「toolの使い方が不正」を同じ非ゼロ終了として扱った |
| 修正 | imageで利用可能な方法へ変え、stderrと期待する失敗理由を検証した |
| 再発防止 | test自身が正しく失敗できるか、意図的に分離を壊してnegative controlを行う |
| 学び | exit codeだけでなく、何が原因でそのcodeになったかを観測する |

## 3. 対象OSとCIのAnsible版が違った

| 観点 | 内容 |
| --- | --- |
| 当初の想定 | ansible-lint、syntax check、Molecule成功ならUbuntu 24.04でもroleを実行できる |
| 現象 | `meta: end_role`はansible-core 2.18以降だが、Ubuntu 24.04標準は2.16系で失敗した |
| 切り分け | qemu上の対象OSでB-1を実行し、tool versionと失敗taskを比較した |
| 根本原因 | CIの新しいpip版と配備先の標準版が一致していなかった |
| 修正 | 対象versionで使えるtask構造へ変更した |
| 再発防止 | 対応matrixへtool versionを含め、対象OS相当のruntime試験を残す |
| 学び | 静的検査の成功範囲と、配備対象での実行成功は別物である |

## 面接での説明方法

1. 最初の仮説を隠さない。
2. 事実確認に使ったcommandと観測値を示す。
3. 暫定対応と根本修正を分ける。
4. 同じ欠陥を防ぐtestを説明する。
5. AIや外部情報を利用した範囲と、本人が実行・判断した範囲を区別する。
